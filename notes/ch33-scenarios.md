# 第 33 章 · 场景设计：基准、负载、压力、稳定性

上一章讲指标，这一章讲「怎么压」。同一套代码，压法不同，结论完全不同：基准测试告诉你「一个请求多快」，负载测试告诉你「多少并发还稳」，压力测试告诉你「从哪开始崩」，稳定性测试告诉你「连续跑八小时会不会漏」。

## 1. 四类场景，一个问题一个场景

| 场景 | 加压方式 | 回答的问题 | 典型时长 |
| --- | --- | --- | --- |
| 基准 | 单用户，跑 N 次 | 这个接口本身多快 | 秒级 |
| 负载 | 逐步加到预期并发 | 预期压力下是否达标 | 分钟级 |
| 压力 | 一直加到崩溃 | 极限在哪、先崩哪个 | 分钟级 |
| 稳定性 | 70%–80% 压力跑 8–24h | 会不会内存泄漏、连接不释放 | 小时级 |

新手常把「压力测试」当默认。实际上日常回归只跑基准 + 负载，压力与稳定性是里程碑前才做。

## 2. 阶梯加压：一档一档往上抬

`labs/ch33-scenarios/scenario.py` 里的执行器只做三件事：

```python
scenario = Scenario(name="连接池按压", levels=[2, 4, 6, 8, 12], duration_s=1.5)
run_stages(scenario, target_factory, on_stage=print_stage)
```

- `levels` 是并发档位，从小往大；`duration_s` 是每档时长。
- `target_factory(level)` 每档新建一个 target，避免上一档的连接被复用——否则第一档建立的连接会一直吃满池子，后面几档的数字全是假的。
- `on_stage` 回调拿得到每档的 `StageResult`（`tps`、`p95_ms`、`error_rate` 自动算好）。

每档的统计口径必须先想清楚：**预热要不要算进 TPS**。这一章的实现里 `LoadGen` 只统计发送期间的样本，预热靠外部控制（先打几秒再开始计数）。

## 3. 拐点判定：三条规则，先命中先算

`find_knee(results, rt_ratio=1.5, error_rate=0.01)` 按顺序检查：

1. **错误率越界**：这一档错误率 > 阈值 → 判 `error_rate`。错误率优先，因为服务已经开始拒绝了，RT 再好看也没意义。
2. **P95 相对上一档翻倍**：`当前 P95 / 上一档 P95 >= 1.5` → 判 `latency`。
3. 都不命中 → `none`，说明还没压到极限，可以继续加档。

注意两点：

- 第一档没有「上一档」，只能靠错误率判定。
- 用相对倍数而不是绝对阈值（比如「P95 > 500ms」），因为同一个服务在不同机器上绝对值差很多，倍数才是可比的。

```bash
python -m pytest labs/ch33-scenarios -q
```

实测输出（本机，池上限 5）：

```
并发  2  TPS    7.86  P95  260.25ms  错误率 0.00%
并发  4  TPS   15.79  P95  254.12ms  错误率 0.00%
并发  6  TPS   17.65  P95  495.22ms  错误率 0.00%
并发  8  TPS   18.75  P95  499.78ms  错误率 0.00%
并发 12  TPS   18.42  P95  748.07ms  错误率 0.00%

拐点判定： {'concurrency': 6, 'reason': 'latency', 'value': 1.95}
结论： 在并发 6 时 P95 翻 1.95 倍，容量上限大约在这一档之前
```

这一组数字值得多看一眼：并发从 4 加到 6，TPS 只从 15.8 涨到 17.6，P95 却翻倍——这就是「吞吐到顶、延迟换来的排队」。再往上加并发，TPS 反而略降（18.75 → 18.42），说明多出来的线程只是在池子外面等锁。

## 5. 常见坑

1. **每档复用同一个 session**：连接被前一档占着，后面档位的数字不可信。
2. **档位跨度太大**：2、4、6、8、12 已经算粗，2 直接跳 32 会错过拐点。
3. **每档时长太短**：小于 5 秒时，GC、连接建立、预热都还没走完，噪声比信号大。
4. **只看 TPS 不看错误率**：池子满了返回 503 时，TPS 会被拉高（快速失败也算完成），看起来「性能变好了」。
5. **压测机自己成为瓶颈**：施压端与被测端同机时，CPU 是共享的，拐点可能出现在压测工具身上。

## 6. 自测

1. 为什么每一档都要新建 target，而不是复用上一档的 session？
2. 拐点判定为什么优先看错误率，而不是先看 P95？
3. 为什么用「P95 相对上一档的倍数」而不是「P95 > 500ms」？
4. 并发 4 到 6 时 TPS 只涨 11%，P95 翻倍，这说明什么？
5. 稳定性测试为什么要跑 8 小时以上，而不是压 30 分钟？

## 附：自测答案

1. 连接是池化资源，前档建立的连接会占住池子，后档的排队时间会被算进 RT，数字失真；新建 target 才能让每档从同一初始状态开始。
2. 错误率越界意味着服务已经在拒绝请求，此时 RT 再低也没有意义；而且错误响应往往更快，会把平均值「美化」，先看错误率能避免误判为「性能很好」。
3. 绝对阈值跟机器、数据量、部署形态强相关，换个环境就失效；相对倍数衡量的是「这一档相对上一档劣化了多少」，可跨环境比较。
4. 吞吐已到平台区（瓶颈在池子），新增并发只是在池外排队，于是 TPS 几乎不涨、P95 线性上升——这是典型的排队饱和信号。
5. 内存泄漏、连接不释放、日志堆积、定时任务冲突这些问题是「随时间累积」的，30 分钟看不出趋势；8 小时能覆盖多个业务高峰与至少一次缓存过期周期。

## 学生常问

Q：压力测试一定要压到崩吗？

A：不一定。压到「明显劣化」就够定位容量上限了；真压到崩可能触发熔断、把测试环境打挂。生产前的压力测试更推荐「压到拐点 + 再往上两档」就收手。

Q：稳定性测试的 70%–80% 压力怎么定？

A：用负载测试测出的容量上限（拐点并发）乘 0.7–0.8。如果连负载测试都没做，就把「日常峰值并发 × 1.5」当起点。

Q：同一份脚本能同时做基准和压力吗？

A：可以，差别只在档位与时长。基准是 `levels=[1]`、`duration_s=10`；压力是 `levels=[2,4,8,16,32]`。真正的区别是**判定规则**：基准看单个请求的绝对耗时，压力看拐点。

## 面试题

Q：给你一个新服务，你怎么设计性能测试方案？

A：四步。一、定目标：按业务给出并发与 RT 的 SLA（例如 200 并发、P95 < 300ms）。二、选场景：先基准摸单请求耗时，再负载验证 SLA，再压力找拐点，最后稳定性跑长时。三、准备数据与隔离：独立环境、独立库、造数脚本可重复。四、看结果：拐点、错误类型分布、资源曲线三者对齐，输出容量结论而不是一张 RT 图。

Q：拐点之后你还会继续加压吗？为什么？

A：会再加一到两档，用来确认「是缓慢劣化还是断崖」。断崖说明有硬上限（连接池、线程池、文件句柄），缓慢劣化说明是排队累积，两者的修复方向不同。

Q：压测结果和线上监控对不上，先信谁？

A：先信线上监控的「趋势」，再查压测的「口径」。常见原因是压测数据量小（走缓存）、压测流量单一（没有长尾接口）、或者压测机与线上网络路径不同。对不上时优先复现线上流量比例。

## 延伸知识

- 档位设计常用「1、2、4、8、16」的等比数列，便于看翻倍劣化；业务型场景可以用「日常峰值、峰值 ×2、峰值 ×5」。
- 每档之间留 10–30 秒静默期，让连接池、GC、线程池回到基线，否则上一档的「尾巴」会污染下一档。
- 判定阈值要写进配置（`rt_ratio`、`error_rate`），而不是散在代码里，方便不同服务用不同标准。
- 压力测试的产出应该是一张「并发 → TPS/P95/错误率」的表，而不是一句「能扛 1000 并发」。
- 稳定性测试要同时盯内存 RSS、连接数、线程数、日志文件大小，四个指标任一持续上涨都算不通过。
