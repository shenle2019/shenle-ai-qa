# 第 34 章 · 压测脚本与参数化

上一章的阶梯加压只压一个接口。真实业务是「登录 → 浏览 → 下单」混着来，而且每个虚拟用户用的账号、商品都不一样。这一章把「压什么」和「用什么数据压」拆开：脚本描述步骤与权重，数据集描述行，运行器负责让同一个用户始终拿到同一行。

## 1. 脚本 = 步骤 + 权重 + 思考时间

`labs/ch34-scripts/script.yaml` 就是脚本本体：

```yaml
name: 登录下单混合场景
users: 2
loops: 3
steps:
  - { name: 登录,   weight: 1, think_s: 0 }
  - { name: 查列表, weight: 3, think_s: 0.01 }
  - { name: 下单,   weight: 1, think_s: 0 }
```

- `weight` 决定比例。查列表权重 3，意味着每 5 次请求里大约 3 次是查列表——这比「所有接口等比例压」更接近真实流量。
- `think_s` 是用户停顿。没有停顿的压测等于把接口当 CPU 跑分，测出来的 TPS 是理论上限，不是业务吞吐。
- `users × loops` 是总请求基数，不是并发。并发由上一章的 `LoadGen` 控制，这一章先保证「请求组成」是对的。

## 2. 数据集：同一个用户永远同一行

`DataSet.for_user(user)` 用 `user % len(rows)` 取行，而不是共享游标。原因很实际：

- 用例要稳定。如果第 3 轮才第一次下某个商品，失败日志里就说不清是「这个商品有问题」还是「第一次下单」。
- 参数化要可复现。同一个 `seed` + 同一份数据集，跑两次结果应当一模一样。

`DataSet.next()` 是另一种用法：单线程顺序跑时轮转取行，适合造数脚本。

## 3. 判定通过：expect 优先，其次看 2xx/3xx

`Step.run()` 返回 `(状态码, 耗时, 是否通过)`：

```python
ok = self.expect(status) if self.expect else 200 <= status < 400
```

`expect` 一定要显式写。登录用例里 401 是**预期结果**（密码错），不写 `expect` 就会被算成失败，错误率虚高。这一章的演示脚本给登录写了 `expect=lambda s: s in (200, 401)`。

## 5. 常见坑

1. **数据集按行轮转但当并发用户数大于行数**：多个用户会撞同一行，唯一性断言必挂。行数要 ≥ 并发数。
2. **`expect` 写成 `status == 200`**：创建接口返回 201 就全被判失败。
3. **思考时间放在请求之后**：每次都会睡（含最后一次），总时长多出一段尾部空转、TPS 被压低；要贴近真实节奏，停顿应放在两次请求之间。
4. **把登录写在每个步骤里**：token 一秒就过期了，还多压了登录接口。登录应该做一次，token 注入后续步骤。
5. **yaml 里写死账号密码**：脚本要进仓库，密钥走环境变量。

## 附：自测答案

1. 让用例可复现：同一用户固定商品/账号，失败时能确定是数据问题还是代码问题；也避免同一行被并发写坏导致随机失败。
2. 无关。`weight` 决定请求**比例**，并发决定**同时有多少人在发**；两者正交，混在一起调会让结论无法归因。
3. 给这个步骤写 `expect`（例如 `status in (200, 401)`），通过与否按 expect 判；否则用默认的 2xx/3xx 判定。
4. `user % len(rows)` 会重复，导致多个用户拿到同一行、撞唯一约束，出现大量 409/422，错误率虚高且不可复现。
5. 不能。思考时间为 0 测的是接口的理论上限，真实用户有阅读、点击间隔，实际吞吐会低很多；容量结论要按带思考时间的负载测试给。

## 学生常问

Q：脚本用 yaml 还是直接写 Python？

A：步骤与比例放 yaml（改起来不用动代码），`call/pick/expect` 这类逻辑放 Python（yaml 表达不了）。这一章的 `load_script` 只读结构与参数，行为由调用方注入。

Q：为什么不在 yaml 里写 URL 和断言？

A：URL 依赖环境（本地/预发/线上），断言依赖业务（这个接口 401 算不算通过）。两者都会随环境变，写进 yaml 就会分叉出多份脚本，维护成本高于收益。

Q：混合场景要不要按真实流量比例？

A：要，至少按「核心链路」的比例。全接口等比例压出来的瓶颈，往往不是真实流量下的瓶颈。

## 面试题

Q：你怎么设计一个混合场景压测？

A：三步。一、拉真实访问日志，算出各接口的请求占比与 P95，作为权重与目标。二、把占比高的接口做成脚本步骤，每步配独立数据（唯一账号/唯一商品）。三、按占比分配并发，跑阶梯加压，观察是哪个步骤先劣化。

Q：参数化数据怎么准备？

A：优先调接口造（可重复、跟业务一致），其次从库里抽样（要注意脱敏与唯一性），最后才是固定文件（只读场景）。造出来的数据要带唯一前缀，跑完能批量清理。

Q：脚本里怎么处理登录态？

A：一次登录、复用 token（或 cookie），token 过期前刷新；不要把登录塞进每个步骤。并发压测时按用户维度各登录一次，不要所有用户共用一个 token。

## 延伸知识

- 权重之外还有「链路顺序」：下单前必须查过商品，这种前置关系用 `pick` 传上下文，而不是靠随机顺序碰巧满足。
- 思考时间可以按分布取（正态/指数），比固定值更接近真人；压测工具里通常叫 `pacing`。
- 数据隔离：压测账号统一 `qa_` 前缀、商品统一 `SKU-QA-` 前缀，跑完按前缀清理。
- 请求占比会随大促变化，脚本的权重应当从配置中心读，而不是硬编码。
