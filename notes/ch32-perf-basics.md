# 第 32 章 · 性能测试基础与指标

性能测试最容易犯的错不是「压不上去」，而是**压上去了却读不懂数字**。这一章只解决一件事：把四个指标算对、读对。

## 1. 四个指标与一条公式

| 指标 | 定义 | 常见误读 |
| --- | --- | --- |
| 并发数 | 同一时刻正在处理请求的数量 | 把它当成「线程数」或「用户数」 |
| 响应时间 RT | 从发出请求到收到完整响应 | 只看平均值 |
| 吞吐 TPS | 每秒完成的请求数 | 用「总请求数 / 计划时长」而不是实际窗口 |
| 错误率 | 非 2xx 的比例 | 把 4xx 业务拒绝也算成「服务挂了」 |

四个指标不是独立的，它们被一条公式绑住：

```
TPS ≈ 并发数 / 平均响应时间（秒）
```

并发 10、平均 RT 100ms → 理论上限 100 TPS。这条式子（Little's Law 的简化形式）有三个用处：估算容量、反推瓶颈、识别「数字造假」——如果报告里写并发 100、RT 50ms、TPS 只有 20，那一定有排队或错误被吃掉了。

## 2. 平均值为什么不能用

```python
samples = [10] * 95 + [200] * 5   # 95 个快请求 + 5 个慢请求
```

平均值是 19.5ms，看上去很健康；但 P99 是 200ms——**每 20 个用户里就有 1 个在等 0.2 秒**。平均值把尾部抹平了，而用户体验恰恰由尾部决定。

所以报告的标配是三个数：P50（中位体验）、P90（大多数人的上限）、P99（最差的那批人）。再加上最大值，用来抓「偶发但致命」的尖刺。

## 3. 分位值怎么算

```python
def percentile(values, p):
    ordered = sorted(values)
    rank = (len(ordered) - 1) * p / 100
    low = int(rank)
    high = min(low + 1, len(ordered) - 1)
    return ordered[low] + (ordered[high] - ordered[low]) * (rank - low)
```

两点要注意：

1. **样本量决定分辨率**。100 个样本算不出可信的 P99（第 99 个点只由 1 个样本决定），至少 1000 个样本再谈 P99。
2. **分位值不可加**。两个接口各自的 P99 不能平均成「整体 P99」，整体必须重新排序算。

## 4. 四类场景，目的不同

| 场景 | 加压方式 | 回答的问题 |
| --- | --- | --- |
| 基准测试 | 单用户，跑 N 次 | 这条链路本身多快 |
| 负载测试 | 逐步加到预期并发 | 预期压力下是否达标 |
| 压力测试 | 一直加到崩溃 | 极限在哪、先崩哪个 |
| 稳定性测试 | 70%~80% 压力跑 8~24 小时 | 会不会内存泄漏、连接不释放 |

新手常把「压力测试」当默认。实际上日常回归只跑基准 + 负载，压力与稳定性是里程碑前才做。

## 常见坑

1. **用计划时长算 TPS**：程序跑 3 秒但实际 3.13 秒，用 194/3 会把 TPS 算高。
2. **把 401/422 当故障**：接口测试的「错误率」通常只看 5xx 与超时，4xx 是业务预期。
3. **并发数写成线程数**：线程读一次数据要 5ms，其余时间都在等，能压出的并发远大于线程数。
4. **压测机和被测机同机**：两边抢 CPU，RT 会被自己拖长，数字只能横向比较。

## 附：自测答案

1. `20 / 0.25 = 80` TPS。这是上限，实际会被排队、GC、网络拉低。
2. 不可信。P99 落在第 99 个样本附近，一个抖动就能让它翻倍；至少 1000 个样本。
3. 分位值依赖整体分布，两个子集的 P99 平均后既不等于合并后的 P99，也没有物理意义。
4. 短时间压测看不出内存泄漏与连接未释放；8 小时能覆盖到定时任务、日志切分、缓存过期这些周期性事件。

## 学生常问

**Q：压测要跑多久？**

A：基准 30 秒够；负载 3~5 分钟看稳定值；稳定性 8 小时起。时间太短会把「预热阶段」当成结论。

**Q：TPS 上不去，先看什么？**

A：先看 RT 有没有一起涨。RT 平稳而 TPS 不涨 = 施压端到顶（线程/连接不够）；RT 一起涨 = 服务端有瓶颈。

**Q：错误率 0 就一定没问题吗？**

A：不一定。可能是超时被算成了成功（客户端没校验业务码），也可能是并发太低没压出问题。要看响应体里有没有业务错误码。

## 面试题

**Q：给你一个接口，怎么定性能目标？**

A：三步：查历史峰值（比如日常 200 QPS、活动 800 QPS）；按「峰值 × 1.5~2」定目标 TPS；按业务定 RT 上限（查询类 P95 < 300ms、写入类 P95 < 500ms）。没有历史就按容量测算反推。

**Q：怎么判断瓶颈在应用还是数据库？**

A：看三处对齐：应用侧线程池排队、DB 侧慢查询与连接数、系统侧 CPU/IO。应用线程都在等 DB 而 DB CPU 不高 → 慢查询或锁；DB CPU 打满 → 缺索引或数据量问题。

**Q：为什么 P99 比平均更适合做 SLA？**

A：SLA 约束的是「最差体验」，平均值掩盖长尾。真实事故几乎都先体现在 P99 上，而不是平均。

## 延伸知识

- `requests` 默认每次新建连接，压测前必须 `Session` + 连接池，否则测的是 TCP 握手。
- 压测客户端的 `timeout` 要小于服务端超时，否则你会把「服务端已返回但客户端已断开」误判成成功。
- 采集 RT 用 `time.perf_counter()`（单调时钟），不要用 `time.time()`（会被系统对时影响）。
- 同一份样本用不同分位算法（线性插值 vs 最近秩）结果会差几个百分点，报告里要写清口径。
