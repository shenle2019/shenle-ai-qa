# 第 35 章 · 结果分析与瓶颈定位

压测跑完，手上是一堆数字：并发、TPS、P95、错误率，还有服务端 `/stats` 里的 in_flight 与 pool_wait。这一章解决一个问题——**这些数字到底指向谁**。

## 1. 先找平台期，再谈瓶颈

判断「压到极限」不看单点数字，看**增量**：

```
并发  2 → 4：TPS 10 → 19，涨了 90%
并发  4 → 8：TPS 19 → 19.5，只涨 2.6%
```

第二段增量低于 10%，就是平台期（`plateau_at=8`）。平台期之后继续加并发，TPS 不涨而 P95 线性上升，说明请求在排队，不是在处理。

`diagnose()` 就是在算这个：逐档算 `gain`，第一个小于 0.1 的档位记为平台期，同时给出峰值 TPS、最差 P95、最高错误率。

## 2. 归因：四条证据链，按优先级

`attribute()` 按顺序检查，先命中先返回：

| 归因 | 证据 | 含义 |
| --- | --- | --- |
| `server_error` | 服务端 5xx 占比 > 1% | 服务已经在拒，先修错误 |
| `pool_queue` | `in_flight >= 并发数` 且 `pool_wait_ms > 0` | 连接池打满，请求在池外等 |
| `server_reject` | 平台期那一档客户端错误率 > 1% | 限流/熔断触发 |
| `server_slow` | 有平台期、无错误、池也没满 | 服务端自己慢（CPU/GC/锁） |
| `client_limited` | 一直在涨（没有平台期） | 还没压到服务，先怀疑施压端 |

顺序很重要。如果先看「P95 高」就归因于「服务慢」，可能完全搞反——池子满了 P95 也会高，但根因是连接数配置，不是代码。

## 3. 每一档都要有服务端快照

只看客户端数字分不清「服务端慢」还是「客户端排队」。所以每档跑完要抓一次服务端指标：

```python
Snapshot(concurrency=8, in_flight=8, pool_wait_ms=120, server_5xx=0, total=100)
```

`in_flight` 等于并发数，说明所有并发都在服务端「手上」，没有空闲；`pool_wait_ms` 大于 0 说明有等待。这两个一起出现，基本可以确定是池子。

## 5. 常见坑

1. **只给一张 RT 曲线就下结论**：没有并发-吞吐关系，看不出是服务慢还是排队。
2. **把客户端错误率当服务端错误率**：客户端 4xx 是业务预期（密码错），服务端 5xx 才是故障。
3. **平台期判定阈值写死 10%**：低并发段 10% 太严、高并发段太松，最好按业务 SLA 定。
4. **忽略施压端**：施压机 CPU 打满时，TPS 曲线也会「平台化」，看起来像服务端到顶。
5. **只看平均值**：平均 150ms 里可能藏着 5% 的 2s 请求。

## 6. 自测

1. 为什么用「增量小于 10%」而不是「TPS 不涨」判平台期？
2. `in_flight` 等于并发数意味着什么？
3. 为什么归因顺序里「5xx」排在「P95 高」前面？
4. 施压端受限时，曲线上有哪些特征？
5. 平台期那一档 P95 涨了 3 倍，但服务端 5xx 为 0、池也没满，最可能是什么？

## 附：自测答案

1. 完全「不涨」几乎不会出现（噪声、缓存抖动都会让 TPS 微涨），用相对增量才稳定；阈值可按业务调。
2. 所有并发线程都在服务端「处理中」，客户端没有排队等待，说明瓶颈已经在服务端内部（CPU/锁/IO），而不是连接层。
3. 5xx 是确定性故障，先修它才有意义；P95 高可能是排队、也可能是客户端，证据强度弱于 5xx。
4. TPS 曲线提前平台化、施压机 CPU 接近 100%、客户端 RT 分布里出现大量「等待发送」时间、服务端 in_flight 远小于并发数。
5. 服务端内部慢：CPU 打满、GC 停顿、锁竞争或慢查询，需要抓这一档的慢请求样本与线程栈。

## 学生常问

Q：平台期之后还要不要继续加并发？

A：加一到两档确认「是缓降还是断崖」。缓降多是排队，断崖多是硬上限（连接池、文件句柄、线程池）。

Q：服务端指标抓不到怎么办？

A：退化方案：看客户端的错误类型分布 + 同机 CPU 曲线 + 日志里的慢请求。证据弱一些，但比只看 TPS 强。

Q：TPS 达标但 P95 不达标，算通过吗？

A：不算。容量结论要同时满足吞吐与延迟两个门槛，只满足一个说明「能压进去但用户等不了」。

## 面试题

Q：压测报告怎么写才算有用？

A：四块。一、目标与场景（并发、时长、数据量）。二、结果（并发-TPS-P95-错误率表 + 拐点）。三、归因（瓶颈在哪层、证据是什么）。四、结论与建议（容量上限、需要改的配置/代码、复测计划）。

Q：同一个服务两次压测结果差很多，怎么排查？

A：先对齐条件：数据量、缓存状态、并发档位、施压机负载、部署版本。再看服务端：连接池、GC、慢查询。最后看外部依赖（DB、缓存、第三方）。差异往往来自「数据量不同导致缓存命中率不同」。

Q：怎么区分「服务端慢」和「网络慢」？

A：对比服务端处理耗时与客户端 RT。差值大且稳定 → 网络/排队；差值小 → 服务端自己慢。再抓一次同机直连（跳过网关）作对照。

## 延伸知识

- 平台期判定也可以看 P95 的斜率：P95 随并发线性上升，就是排队信号。
- 服务端快照最好每档抓两次（档中 + 档末），能看出是否在累积（连接泄漏会持续上涨）。
- 归因结论要写「证据 + 反证」：例如「池满，因为 in_flight=并发且 pool_wait>0；反证是 5xx=0、CPU 未打满」。
- 施压端与被测端同机时，先把施压端 CPU 限制在 1 核以内，避免它自己成为瓶颈。
- 报告里给「下一档建议」比给「当前结论」更有用。
