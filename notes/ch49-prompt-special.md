# 第 49 章 · Prompt 专项与回归

Prompt 专项测试不是「把提示词念一遍看顺不顺眼」，而是把它当成有版本、有变量、有输入分布的代码来测：同一意图换种写法是否还成立，同一输入跑十次是否还一致，改了一行之后哪些能力会掉。

## 1. 明确 vs 模糊：同一意图，两种写法

「退款」和「请用三句话说明退款流程，并列出需要的材料」是同一个意图，但后者把任务、长度、输出内容都说清了。专项测试要固定意图，只改提示词写法，看输出是否仍然满足验收标准。

| 要素 | 模糊写法 | 明确写法 | 测什么 |
| --- | --- | --- | --- |
| 任务 | 退款 | 说明退款流程 | 是否答到点上 |
| 输出格式 | 没说 | 三句话 | 结构是否可解析 |
| 必含内容 | 没说 | 所需材料 | 关键信息是否遗漏 |
| 边界 | 没说 | 只答流程 | 是否跑题 |
| 异常 | 没说 | 缺材料时怎么办 | 是否有兜底 |

语料把模糊 Prompt 的风险归为「模型自由发挥、输出不可控」（题目 65、66）。但要注意：本章的 `FakeLLM` 只按关键词命中作答，所以实跑里明确和模糊都是 `1.0`，**这个结果不能证明「明确更好」**；它只说明这组用例在假模型上没有区分度。真实模型上应改用输出结构、信息完整度、实体保留率来判定。

## 2. 口语化容错

用户不会按提示词模板说话。专项测试要准备同一意图的多种说法：错别字（「退宽」）、口语（「这钱能退不」）、语法松散（「退款 怎么弄」）、省略（「退一下」）、中英混输（「refund 怎么走」）。

语料把口语化容错拆成错别字、口语表达、语法松散三类，并建议模型在不确定时**主动确认**而不是硬猜（题目 67）。对应的测试点是：意图是否识别对、订单号等关键实体是否保留、该追问时是否追问。判定用「语义等价」而不是字符串相等，否则「退款流程」和「怎么退款」会被判成两个答案。

## 3. 稳定性：同输入重复 N 次

稳定性最直接的度量是一致率：同一 Prompt 跑 N 次，取出现次数最多的输出，看它占几成（`labs/ch49-prompt-regression/ch49_cases.py:47-49`）：

```python
def stability(llm, prompt, rounds=6):
    outs = [llm.answer(prompt, seed=i).text for i in range(rounds)]
    return round(outs.count(max(set(outs), key=outs.count)) / rounds, 2)
```

实跑：`jitter=0` 时稳定率 `1.0`；`jitter=0.5` 时 `0.83`，也就是 6 次里 5 次相同。测试还要求 `jitter=0.9`、跑 10 次时稳定率必须小于 1.0，证明这个指标确实能感知抖动。

两个坑：6 次样本太小，`0.83` 的置信区间很宽，只能筛出明显抖动；「稳定」不等于「正确」，一个每次都答错的模型稳定率也是 1.0，所以稳定性和正确率必须分开报。

## 4. 模板与缺变量

模板的价值是「结构固定、变量可替换」：`TEMPLATE = "你是{role}。用户问题：{question}。要求：{rule}"`（`ch49_cases.py:21`）。缺变量时绝不能把 `{question}` 原样带到线上，`render()` 用 `format_map` 加一个自定义 `__missing__` 直接抛错（`ch49_cases.py:24-30`）：

```python
raise KeyError(f"模板缺变量：{key}")
```

实跑报错是 `'模板缺变量：question'`。测试同时断言两件事：正常渲染后输出里不含 `{question}`，缺变量时必须抛错（`test_ch49_prompt.py:15-27`）。另外三类模板 bug 也要覆盖：变量名拼错（同样触发缺变量）、多传了值（通常无害但说明调用方有脏数据）、值类型不对（数字/None 被直接拼进提示词）。

还有一个隐蔽风险：如果模板渲染了两次，用户输入里的花括号可能被当成占位符。正确做法是「模板只渲染一次，用户内容作为值插入」，不要在已渲染结果上再 `format`。

## 5. A/B 分桶：同一用户稳定落桶

A/B 的前提是同一用户每次都进同一组，否则用户会看到两个版本来回跳。用 `sha1(user_id) % buckets` 做稳定分桶（`ch49_cases.py:52-55`）：

```python
h = int(hashlib.sha1(user_id.encode("utf-8")).hexdigest(), 16)
return h % buckets
```

200 个用户实跑分桶是 `{0: 106, 1: 94}`，接近对半，偏差 6 个用户。注意这不是「哈希均匀性证明」，只是小样本下的正常波动；真要验证均匀性得用更大样本加卡方检验。测试断言同一 `user_id` 永远同桶、200 人每桶在 60–140 之间（`test_ch49_prompt.py:45-52`）。

分桶键要选稳定的业务主键（user_id、租户 id），不要用 session_id、时间戳或随机数；加盐可以防「用户猜分组」，但换盐会让所有用户重新洗牌，必须当成一次实验重启。

## 6. 长度与成本

Prompt 过长和过短各有风险（题目 72）：过长会挤占上下文、抬高成本、稀释关键指令；过短则缺约束、输出不可控。测试要记录 Prompt 的 Token 数，并把它和成本、延迟一起看。

按示例价 0.002 元/千输入 Token，系统提示从 200 Token 涨到 800 Token，每天 10 万次调用：

```
(800 - 200) / 1000 × 0.002 × 100000 = 120 元/天
```

一年多花 4.38 万元。单价是示例值（`labs/_shared/eval_sim.py:138-140`），不是厂商报价；换成真实单价后结论方向不变，绝对数会变。所以 Prompt 评审要问一句：这句话值不值得每天多花这些钱？

## 7. 多语言

多语言不是「把中文 Prompt 翻译一遍」。要做平行测试：同一语义在中、英、日等语言下各准备一组用例，检查四件事——回答语种是否跟用户一致、术语是否统一、输出格式是否仍然可解析、安全策略是否同样生效（题目 73）。

常见坑：中英混输时模型可能整段切成英文；小语种分词更碎，同样内容 Token 数更多、成本更高；不支持的语言如果不显式兜底，模型可能编出一段「似懂非懂」的回答。测试要断言「不支持时明确说明」，而不是只断言「有返回」。

## 8. 版本管理与回归触发

Prompt 是代码，就要有版本号、变更记录、评审和回滚（题目 74）。本章用 `PromptVersion(version, body)` 承载版本（`ch49_cases.py:33-36`），回归函数比较新旧两版的逐条结果（`ch49_cases.py:65-69`）：

```
old = {"a": True, "b": True, "c": False}
new = {"a": True, "b": False, "c": True}
→ {'broke': ['b'], 'fixed': ['c'], 'passed': ['a']}
```

`broke` 是变坏的，`fixed` 是修好的，`passed` 是两版都过的。上线门槛：`broke` 必须为 0；`fixed` 要人工确认不是用例本身写错；`passed` 数量用于确认没有大范围失效。

哪些变更必须重跑回归（题目 52）：

| 变更 | 回归范围 |
| --- | --- |
| Prompt 文本、变量、模板结构 | 全量用例 + 稳定性 |
| 模型版本或供应商 | 全量用例 + 长上下文 + 安全集 |
| 温度、top_p、max_tokens | 稳定性 + 格式用例 |
| 上下文策略、记忆窗口 | 多轮 + 长文用例 |
| 工具/函数描述、RAG 切片 | 工具调用 + 检索相关用例 |
| 安全策略、系统提示 | 注入集 + 越狱集 |
| 依赖库升级、定期（如每周） | 全量 smoke |

## 附：自测答案

1. 不能。`FakeLLM` 只按关键词命中，两种写法都命中了「退款」，所以都是 1.0；这个 demo 只能验证「明确不差于模糊」（测试也只断言 `clear >= vague`）。要证明明确更好，得在真实模型上比较输出结构、信息完整度和实体保留率。
2. 跑 6 次，取出现次数最多的那个输出，`5 / 6 = 0.833...`，四舍五入为 `0.83`。`jitter` 给输出加随机扰动，扰动越大，6 次里出现相同输出的次数越少，稳定率越低。
3. 因为 `{question}` 漏到线上会变成一句字面上的占位符，用户看到的是坏结果而不是报错。`render()` 用 `format_map` 配一个 `__missing__` 会抛 `KeyError` 的 dict，错误信息里带上缺失的 key，所以能报出 `'模板缺变量：question'`。
4. `session_id` 会随会话变化，同一用户刷新就可能换组；`user_id` 稳定，才能保证体验一致和实验可复现。106/94 只是接近对半，偏差 6 个用户属于小样本波动，不能据此判断哈希不均匀。
5. 多出的 600 Token × 100000 次 = 6000 万 Token = 60000 千 Token；`60000 × 0.002 = 120 元/天`。
6. Prompt 文本或变量改动、模型版本/供应商切换、温度等采样参数改动、上下文或记忆策略改动、工具描述或 RAG 切片改动、安全策略改动；另外依赖升级和定期 smoke 也要跑（题目 52）。

## 学生常问

**Q：用例通过率 100%，是不是可以直接上线？**

A：只说明「这组用例」过了。要看用例覆盖了哪些意图、有没有注入和多语言、稳定性是否达标、线上分布是否和用例一致。本章的明确/模糊都是 1.0，就是覆盖不足导致指标失真的例子。

**Q：温度调到 0，稳定性就一定是 1.0 吗？**

A：不一定。温度 0 只是降低采样随机性，批处理顺序、硬件差异、模型版本更新仍可能带来差异；而且本章的 `jitter` 是模拟输出扰动，和真实温度不是一回事。稳定率要靠重复实测，不能靠参数推断。

**Q：A/B 分桶 106/94，需要重新分吗？**

A：不需要。200 个样本分成两桶，出现 6 个偏差很正常；重新分桶反而会破坏「同一用户稳定落桶」。如果担心比例失衡，应该增大样本或按分层抽样，而不是换哈希。

## 面试题

**Q：怎么设计一套 Prompt 回归测试？**

A：先建用例库，按意图/边界/异常/安全分组，每条带期望结果；再给 Prompt 建版本号和基线结果；每次变更跑新旧对比，输出 `broke/fixed/passed`；`broke` 必须为 0，`fixed` 人工复核；最后接进 CI，并定期跑 smoke。

**Q：Prompt 的稳定性怎么测、阈值怎么定？**

A：同一输入重复 N 次算众数占比，再补微小扰动（同义改写、标点、空格）看语义是否漂移；阈值按业务定，面向用户的场景通常要求很高，内部工具可以放宽。关键是把稳定性和正确率分开报，避免「稳定地答错」。

**Q：A/B 实验怎么保证同一用户稳定进组？**

A：用稳定主键做哈希取模，比如 `sha1(user_id + salt) % N`，不要用随机数或 session；记录每个用户的曝光组别；换盐等于重启实验，要重新评估样本量。

**Q：Prompt 版本管理要管什么？**

A：版本编号、变更记录（改了什么、为什么）、分支与评审、发布权限和回滚路径；线上请求要能追溯到具体版本，出问题时才能定位是哪次改动引入的。

## 延伸知识

- Prompt 专项的四个目标是有效性、一致性、鲁棒性、安全性，四类用例要分开建（语料题目 64）。
- 口语化容错至少要覆盖错别字、口语表达、语法松散，并验证模型会主动确认而不是硬猜（语料题目 67）。
- Prompt、模型、参数、上下文策略、工具描述、安全策略变更都应触发回归，不能只盯 Prompt 文本（语料题目 52）。
- 稳定率就是众数占比，实现只有三行：重复采样、计数、除以轮数（`labs/ch49-prompt-regression/ch49_cases.py:47-49`）；分桶则是 `sha1 % buckets`（同文件 `:52-55`）。
