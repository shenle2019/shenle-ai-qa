# 第 42 章 · 接口资产与一致性校验

平台的接口资产不是「一份文档」，而是**可被程序消费的数据**：能生成清单、能校验、能驱动调试与用例生成。

## 1. 从 spec 到接口清单

parse_spec() 只认精简结构：{base_url, paths: {path: {method: {summary, params, body}}}}。产出的 Endpoint 带 method/path/summary/params/body_required，key 形如 GET /api/users。

OpenAPI 差异交给适配层：真实 OpenAPI 先降维成本章结构，再进入平台。

## 2. 四条校验规则

| 规则 | 为什么 |
| --- | --- |
| 重复接口 | 同名同路径两条，执行时只跑其中一条 |
| 写接口没有 body | 用例生成器造不出请求体 |
| 路径带 {} 却没声明 params | 调试时无法填参 |
| 缺 summary | 界面上只能显示路径，人看不懂 |

alidate() 返回问题清单，空列表才算通过——这与 CI 里「退出码 0」同一思路：**校验要有可判定的结果**。

## 4. 常见坑

1. 直接存原始 spec：查询与展示都要现解析，慢且易错。
2. 校验只在导入时做一次，后续手改资产没人管。
3. 路径参数用贪婪的 `.+`，会把 `/b` 一起吃进参数，`/a/{id}/b` 就匹配错；应当用 `[^/]+`。
4. 方法大小写混用，列表里出现 get 与 GET 两份。
5. base_url 相对路径，调试时拼不出完整地址。

## 5. 自测

1. 为什么要先把 spec 降维成 Endpoint？
2. 「写接口没有 body」为什么算问题？
3. 校验结果为什么用列表而不是布尔？
4. 方法为什么要统一大写？
5. 导入之后的资产还需要校验吗？

## 附：自测答案

1. 平台需要的是可查询、可校验、可驱动的数据结构；原始 spec 是交换格式，不是内部模型。
2. 用例生成与调试都需要请求体；缺 body 定义意味着这条写接口无法自动造请求。
3. 列表能给出「哪几条、为什么」，布尔只能告诉「有问题」，无法指导修复。
4. 统一大小写才能去重与比较；否则 get 与 GET 会被当成两条。
5. 需要。资产会被人工编辑，导入后应在保存时再校验一次。

## 学生常问

Q：直接用 swagger-ui 不行吗？

A：swagger-ui 解决「看文档」，平台要解决「用资产」：生成用例、驱动调试、跑回归。两者用途不同。

Q：校验太严会不会挡住导入？

A：把规则分级：重复接口与缺 path 是 error，缺 summary 是 warning，允许带着 warning 导入。

## 面试题

Q：接口资产怎么和用例关联？

A：用例记录 endpoint_key（方法 + 路径），资产变更时能反查受影响用例；路径改名要同步更新，否则用例失效。

Q：怎么保证资产与真实服务一致？

A：定期用资产跑一次「探活」：对每个接口发最小合法请求，404 说明路径不存在、405 说明方法没实现，两类分别标出来——405 恰恰说明路径是存在的。

## 延伸知识

- 	o_markdown() 生成的清单可以直接贴进评审文档。
- 校验规则建议做成可配置开关，不同团队严格程度不同。
- 路径参数声明 params 时同时记录类型，后续可自动生成边界值用例。
