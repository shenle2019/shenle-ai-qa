# 第 36 章 · 中间件性能要点

压到瓶颈时，问题经常不在你自己的代码里，而在网关、连接池、消息队列这些「中间那一层」。这一章给三个可以直接算的模型。

## 1. 访问日志：最便宜的性能数据源

一行访问日志里有六个有用字段：状态码、请求大小、总耗时、上游耗时。`parse_line()` 用一条正则把它们取出来，`summarise()` 算 TPS、P95、5xx 占比、上游耗时占比。

```
... "GET /api/orders HTTP/1.1" 200 512 0.012 0.010
                                 ↑   ↑   ↑     ↑
                               状态 大小 总耗时 上游耗时
```

两个比值最有诊断价值：

- **错误率** = 5xx / 总数。客户端 4xx 是业务，服务端 5xx 是故障。
- **上游占比** = 上游耗时 / 总耗时。接近 1 说明时间全花在后端，网关本身很快；明显小于 1 说明有排队或网关自身慢。

## 2. 连接池：并发超过上限后是线性排队

```python
pool_wait(concurrency, pool_size, hold_ms)
# (并发 / 池大小 - 1) × 持有时长
```

池上限 5、持有 200ms 时：并发 10 → 等 200ms，并发 20 → 等 600ms。这个模型解释了两件事：

- 为什么「加并发 TPS 不涨」：新增并发没有可用连接，只能在池外等。
- 为什么 P95 会突然翻倍：只要并发超过池子，等待时间就跟并发数成正比。

所以看到「TPS 平台 + P95 线性上升 + in_flight 等于并发数」这组信号，先查池子，不要先怀疑代码。

## 3. 消息队列：积压 = 速率差 × 时间

```python
backlog_after(produce_per_s=100, consume_per_s=80, seconds=10)  # 200
```

生产 100/s、消费 80/s，10 秒积 200 条。这个式子用在两个地方：

- 估算多久会打满（积压上限 / 速率差）。
- 判断「扩容消费者」要加几个才追得上：差 20/s，单个消费者 20/s，就要多一个。

注意消费速率本身会随积压变化（积压多时批量更大、反而更快），所以这个模型只适合做量级估算。

## 5. 常见坑

1. **把 4xx 算进错误率**：用户输错密码不该触发告警，5xx 才是。
2. **用平均值看网关耗时**：均值被大量快请求稀释，P95 才反映排队。
3. **只看总耗时**：不拆上游耗时，就分不清是网关慢还是后端慢。
4. **池子调大就完事**：池子超过数据库连接上限，只是把排队从应用挪到数据库。
5. **用「积压条数」判断健康**：要看「积压增长速率」，稳定在某个值说明消费追平了。

## 6. 自测

1. 上游耗时占比接近 1 说明什么？接近 0.3 又说明什么？
2. 池上限 10、持有 50ms，并发 30 时平均排队多久？
3. 生产 200/s、消费 150/s，积压上限 3000，多久打满？
4. 为什么池子不能无限调大？
5. 积压稳定在 500 条，健康吗？

## 附：自测答案

1. 接近 1：时间几乎全在后端，网关/代理开销小，优化要去后端找。接近 0.3：大量时间花在网关或排队上，先查网关并发、TLS、限流。
2. `(30/10 - 1) × 50 = 100ms`。
3. 速率差 50/s，3000 / 50 = 60 秒。
4. 池子上限最终受数据库 `max_connections`、文件句柄、内存限制；应用侧调大只是把排队转移到数据库，可能引发更严重的雪崩。
5. 看趋势：稳定在 500 且不增长，说明消费能力与生产持平（有缓冲）；持续增长才是问题。

## 学生常问

Q：日志里没有上游耗时字段怎么办？

A：至少能算状态码、总数、总耗时。上游耗时可以退化为「应用日志里的接口耗时」对比，或者加一个 header 透传。

Q：网关层该关注哪些指标？

A：连接数、QPS、P95、5xx 率、上游耗时、TLS 握手耗时、限流命中数。前四个是基础盘。

Q：MQ 积压报警阈值怎么定？

A：按「可接受延迟」反推：积压 / 消费速率 = 延迟。要求延迟 < 5 分钟、消费 100/s，阈值就是 30000。

## 面试题

Q：加机器后 TPS 没涨，可能是什么原因？

A：三类。一、共享瓶颈没动：数据库、缓存、MQ、网关。二、连接池/线程池还在原值，新机器拿不到资源。三、负载不均衡（会话粘滞、DNS 缓存、只有一台在接流量）。先看各实例的 QPS 分布，再看共享资源的连接数与 CPU。

Q：网关 P95 高，但后端 P95 正常，怎么查？

A：拆时间：TLS 握手、排队等待、上游耗时。先看上游占比，再看连接复用率与限流命中，最后看网关自身 CPU 与 GC。

Q：MQ 消费慢怎么定位？

A：先看消费速率是否稳定（是否在降），再看单条处理耗时分布（是否长尾），再看是否有重试/死信堆积。批量大小与并发消费者数是两个最常调的旋钮。

## 延伸知识

- 访问日志按分钟聚合，比按小时更能看出尖刺。
- 池子监控要看「等待获取连接的次数」和「等待时长」，只有使用率看不出排队。
- 网关与后端之间的 keep-alive 复用率低，会凭空多出大量 TCP 握手时间。
- 队列积压的「增长速率」比绝对值更适合做告警。
- 任何中间件调优前，先确认它不是共享瓶颈——否则只是把压力挪个位置。
