# 第 37 章 · 全链路压测与数据隔离

单接口压测只回答「这个接口能扛多少」。全链路压测要回答「这条业务链路能扛多少」——从网关进来，经过若干个服务、缓存、数据库、队列，再出去。链路一长，两件事必须先解决：**流量要能认出来**、**数据不能污染真实用户**。

## 1. 打标：让压测流量一路可识别

```python
Traffic(shadow=True, prefix="qa_20251120_")
traffic.tag()  # {"X-Shadow": "1", "X-Data-Prefix": "qa_20251120_"}
```

约定几个 header 任一命中就算压测流量（`is_shadow` 大小写不敏感）：`x-shadow`、`x-pressure-test`、`x-env: perf`。

打标的三个用途：

- **限流分流**：网关识别到压测流量，走独立的限流规则，不影响真实用户。
- **影子库/影子表**：下游按 header 决定写哪套存储。
- **清理**：跑完按 header 或前缀找到这批数据，批量删除。

打标必须**透传**。任何一层丢了 header，下游就当真实流量处理——这是全链路压测最常见的事故来源。

## 2. 隔离：数据前缀是最后一道保险

即使打标丢了，前缀还在。`make_prefix("run_id")` 生成 `qa_<run_id>_`，所有造出来的数据都带这个前缀：

```python
check_isolation(["qa_r1_a", "qa_r1_b", "alice"], "qa_r1_")
# {'total': 3, 'isolated': 2, 'leaked': ['alice']}
```

这条检查应该跑在压测**开始前**（确认造数脚本都带前缀）和**结束后**（确认没有漏网数据留在库里）。

## 3. 计划校验：先确认压测真的在压

`Plan.validate()` 拦三种低级错误：

| 检查 | 原因 |
| --- | --- |
| 没有步骤 | 空计划跑起来只会报错 |
| 缺 run_id | 没有 run_id 就没有前缀，无法隔离与清理 |
| 影子模式但没有写步骤 | 只读压测算不出写链路容量 |

第三条容易被忽略：一个「全链路压测」如果只有查询，测出来的是读容量，下单链路的锁竞争、事务开销完全没覆盖。

## 5. 常见坑

1. **只在入口打标**：中间件、异步任务、MQ 消费端拿不到 header，写库时就成了真实数据。
2. **前缀只加在用户名上**：订单号、商品 SKU、文件名也要加，否则清理不干净。
3. **压测数据没清理**：下次压测撞唯一约束，错误率虚高。
4. **用真实用户 ID 压写链路**：可能改坏真实用户数据，线上压测必须用影子数据。
5. **影子库与真实库共用连接池**：隔离了存储，没隔离连接，压测照样能把真实请求拖死。

## 附：自测答案

1. 打标让下游能识别压测流量，从而走独立限流、写影子存储、支持批量清理；不打标就会把压测数据写进真实库，甚至触发真实用户的通知/扣款。
2. 因为 header 在跨服务、异步、MQ 场景很容易丢；前缀直接写在数据里，丢不掉，能兜底做隔离与清理。
3. 只读压测只覆盖查询路径，写路径的事务、锁、唯一约束、消息投递都没测到，容量结论不完整。
4. 漏网数据（`check_isolation` 的 `leaked` 为空）、积压是否清空、临时表/影子表是否回收、监控告警是否已恢复。
5. 压测流量会占满连接池，真实请求排队甚至超时；隔离必须做到「存储 + 连接 + 线程池」三层。

## 学生常问

Q：线上能做全链路压测吗？

A：能，但前提是打标 + 影子存储 + 独立限流三件都到位，并且有随时熔断的开关。没有这三件就只在预发做。

Q：header 丢了怎么排查？

A：在每一跳打日志（服务名 + 是否带 shadow header），跑一条请求看日志链路，缺在哪一跳一目了然。常见是异步线程池、MQ 消息属性、HTTP 客户端没透传。

Q：压测数据怎么清理最稳？

A：按前缀删除，并先跑一次 `check_isolation` 统计；删除脚本要支持 `--dry-run`，先看数量再执行。

## 面试题

Q：全链路压测的难点在哪？

A：不在压，在隔离。流量识别、数据隔离、依赖隔离（第三方 mock/挡板）、限流熔断、清理回收，五件事任一没做好都可能伤到真实用户。

Q：怎么保证压测不触发真实业务副作用？

A：三道闸：入口识别压测流量走影子链路；写操作只写影子库；对外依赖（短信、支付、推送）在压测环境统一 mock。再加一个总开关，异常时一键切断。

Q：压测报告里怎么体现「全链路」？

A：给出每一跳的耗时占比与瓶颈点（网关/服务/DB/缓存/MQ），以及链路整体的容量上限，而不是单个接口的 TPS。

## 延伸知识

- 打标 header 建议统一在网关注入，业务代码只读不写，避免各服务实现不一致。
- 影子表用同库不同表（`orders_shadow`）比独立库更容易保证 schema 一致。
- 异步链路（MQ、定时任务）也要消费 shadow 标记，否则消费端会把压测数据当真实数据处理。
- 压测计划的 `run_id` 建议带日期与批次，便于按批清理与回溯。
- 全链路压测的「容量」取各跳容量的最小值（瓶颈跳），不能按延迟最慢的那一跳或平均值算。
