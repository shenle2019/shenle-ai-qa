# 第 48 章 · AI 性能：TTFT、TPOT 与并发

AI 接口的「快」不是一个数：用户先等首字，再等后续每个字，最后才拿到完整回答；只报 QPS，等于把这三段时间揉成一个平均数。

## 1. 为什么 AI 性能不等于 QPS

传统接口一个请求就是一份固定工作，QPS 高通常意味着处理能力强。AI 接口不是：一次请求可能只生成 10 个 Token，也可能生成 1000 个，QPS 相同，算力消耗差两个数量级。

| 对比项 | 传统接口 | AI 接口 |
| --- | --- | --- |
| 工作量单位 | 请求 | 请求 × 输出 Token 数 |
| 用户等待 | 一个总时长 | TTFT + 逐 Token 输出 |
| 主要瓶颈 | CPU、I/O、数据库 | GPU 算力、显存带宽、批处理 |
| 结果确定性 | 同输入同输出 | 同输入也可能不同输出 |

所以 AI 压测至少要同时报四个数：TTFT、TPOT、成功率、Token 吞吐。`QPS × 平均输出 Token` 才是 Token 吞吐；100 QPS × 20 Token = 2000 Token/s，10 QPS × 500 Token = 5000 Token/s，后者更「慢」但实际吞吐更高。

## 2. 四个指标与一条公式

| 指标 | 定义 | 本章实跑值 |
| --- | --- | --- |
| TTFT | 从发请求到第一个 Token 到达 | 120ms |
| TPOT | 第一个之后，平均每个 Token 的间隔 | 18ms |
| 总时长 | 首字等待 + 剩余 Token 的输出时间 | 318ms（12 Token） |
| 成功率 | 在超时阈值内完成的请求占比 | 并发 8 为 1.0，并发 16 为 0.5 |

四个数被一条公式绑住：

```
total = ttft + tpot × (n - 1)
```

`n` 是输出 Token 数，减 1 是因为第一个 Token 只花 TTFT、不花 TPOT。12 个 Token 时：`120 + 18 × 11 = 318ms`，与 `one_request()` 的输出完全一致（`labs/ch48-token-perf/ch48_cases.py:39-46`）。`n=1` 时 total 就等于 TTFT，这条边界要单独测，否则公式里的 `n-1` 很容易写成 `n`。

流式时间线还能验证同一件事：`stream_tokens()` 返回 `(相对时间, token)`，第一个点在 100ms，最后一个点在 `100 + 20 × (len-1)`（`test_ch48_perf.py:23-28`）。

## 3. 并发与排队：容量 4 跑 8 和 16

`simulate_load()` 把服务建模成「每批最多 `capacity` 个同时处理，后到的等前一批」；单请求 318ms，超时 800ms。

```python
load = simulate_load(n=8, capacity=4)
# latencies: [318, 318, 318, 318, 636, 636, 636, 636]
# avg 477.0  p95 636.0  成功率 1.0
```

8 个请求分两批：第一批 318ms，第二批等 318ms 再加自己 318ms，共 636ms。全部在 800ms 内，成功率 1.0。

16 个请求分四批，延迟变成 318 / 636 / 954 / 1272ms；后两批超过 800ms，实跑 `p95 1272.0、成功率 0.5`。

| 并发 | 批次数 | P95 | 成功率 | 名义 QPS | 有效 QPS |
| --- | --- | --- | --- | --- | --- |
| 8 | 2 | 636ms | 1.0 | 12.58 | 12.58 |
| 16 | 4 | 1272ms | 0.5 | 12.58 | 6.29 |

关键结论：并发翻倍，**吞吐没涨**（容量 4 / 0.318s ≈ 12.58 QPS 就是上限），涨的是排队时间和超时率。这就是「QPS 上去了但 P95 崩了」的算术解释；有效 QPS 只算成功请求，16 并发时直接腰斩。

## 4. 长上下文退化曲线

上下文越长，prefill 阶段越久，TTFT 随之上涨。本章用线性系数演示（`base_ttft=100`、每 1k Token 加 25ms）：

```
    500 tokens -> TTFT 112.5 ms
   4000 tokens -> TTFT 200.0 ms
  32000 tokens -> TTFT 900.0 ms
 128000 tokens -> TTFT 3300.0 ms
```

这组系数是**示例值，不是厂商实测**（`ch48_cases.py:75-76` 的 docstring 已注明）。真实曲线不是直线：先是平稳期，接近拐点后缓慢下降，越过拐点（Knee Point）急剧恶化，因为注意力的计算量随长度呈 O(n²) 增长、KV 缓存又挤占显存（语料题目 30、31）。测试要做的不是背一条公式，而是**按业务真实长度采样，找出自己服务的拐点**。

## 5. 冷启动

模型服务刚启动或从休眠恢复时，要把权重加载进显存、初始化推理引擎，第一个请求会明显变慢。实跑对比：

```python
cold_start(first=950, warm=130)
# {'first': 950, 'warm': 130, 'penalty': 820}
```

冷启动比热启动多 820ms，是热启动的 7 倍多。压测时如果把这个请求混进样本，P95 会被一个点拉高；正确做法是先发预热请求（或等健康检查通过），再开始计时，并**单独**记录冷启动耗时。

## 6. 成本公式

成本按输入、输出分别计价，因为输出通常更贵：

```
cost = prompt_tokens / 1000 × price_in + completion_tokens / 1000 × price_out
```

按示例价 `price_in=0.002`、`price_out=0.008` 元/千 Token，3200 输入 + 800 输出：

```
3200/1000 × 0.002 + 800/1000 × 0.008 = 0.0064 + 0.0064 = 0.0128 元
```

单次 1.28 分钱，1000 次就是 12.8 元。这两个单价是**示例值，不是任何厂商的真实报价**（`labs/_shared/eval_sim.py:138-140`）；换模型必须换单价重算，不能把 0.0128 当常数。

## 自测

1. 为什么 AI 接口不能只报 QPS？
2. `ttft=120`、`tpot=18`、输出 12 个 Token，总时长是多少？
3. 容量 4、单请求 318ms、超时 800ms，16 并发时第 3 批的延迟是多少？为什么失败？
4. 并发从 8 加到 16，名义 QPS 和有效 QPS 各是多少？
5. 冷启动 950ms、热启动 130ms，压测时应该怎么处理这个冷请求？
6. 3200 输入 + 800 输出，按 0.002/0.008 元每千 Token，单次成本是多少？

## 附：自测答案

1. 因为一个请求的工作量随输出 Token 数变化，QPS 相同不代表算力消耗相同；要同时报 TTFT、TPOT、成功率和 Token 吞吐。
2. `120 + 18 × (12 - 1) = 318ms`；第一个 Token 只算 TTFT，所以乘的是 n-1。
3. 第 3 批要等前两批，`2 × 318 + 318 = 954ms`，超过 800ms 超时线，所以记失败。
4. 名义 QPS 都是 `4 / 0.318 ≈ 12.58`；有效 QPS 只算成功请求，16 并发时 8 个成功、总窗口 1.272s，约 6.29。
5. 先预热再计时，把冷启动请求单独统计；混进样本会把 P95 拉高，掩盖真实的稳态延迟。
6. `3.2 × 0.002 + 0.8 × 0.008 = 0.0064 + 0.0064 = 0.0128 元`。

## 学生常问

**Q：压测报告写「QPS 1200」，为什么面试官说没意义？**

A：没写每次输出多少 Token、成功率多少、TTFT 多少。1200 QPS 可能只是 10 Token 的短回答，换成 500 Token 的长回答，同样的机器可能只剩几十 QPS。至少要补 Token 吞吐和 P95。

**Q：SLA 应该卡 TTFT 还是总时长？**

A：流式场景卡 TTFT（用户先看到字）加 TPOT（后续是否卡顿）；非流式场景卡总时长。两个都写清口径，别只写「响应时间 < 2s」——那既可能是首字 2s，也可能是全部生成完 2s。

**Q：并发上不去，加机器还是调大超时？**

A：先看是不是排队。排队导致 P95 上涨时，调大超时只是把「失败」改成「慢成功」，吞吐不变；要么加容量，要么降单请求 Token 数。加机器前先用 `capacity / 单请求耗时` 算一下上限，确认瓶颈在服务端而不是施压端。

## 面试题

**Q：给你一个 LLM 接口，怎么设计压测方案？**

A：先分场景（短问答、长文生成、多轮），每种场景定输入/输出 Token 分布；再定指标（TTFT、TPOT、P95、成功率、Token 吞吐）；然后按容量梯度加压找拐点；最后单独测冷启动和长上下文，并把成本按 Token 单价折算进去。

**Q：为什么 P95 比平均延迟更适合 AI 服务？**

A：AI 请求的耗时分布长尾很重，少数长输出或排队请求会把平均拉得看似正常；P95 描述「最慢的那 5%」的真实体验，而事故和投诉几乎都从尾部开始。

**Q：长上下文为什么会让 TTFT 变高？**

A：prefill 要处理全部输入 Token，注意力计算随长度呈 O(n²) 增长，KV 缓存又占显存；超过拐点后还会触发换页或降批，延迟从线性转指数。所以要在业务真实长度上采样，而不是只测短 Prompt。

**Q：TTFT 高和 TPOT 高，排查方向有什么不同？**

A：TTFT 高优先看排队、冷启动、prefill 长度和首包链路；TPOT 高优先看 decode 阶段的显存带宽、批大小和输出长度。用流式时间线把两段拆开，比只看总时长有用。

## 延伸知识

- TTFT 的体验阈值常被引为 1 秒，超过 1 秒用户会明显感到等待（语料题目 28）；这是经验口径，不是物理定律。
- TPOT 的常见参考区间是 50–150ms，具体取决于模型大小和生成策略（语料题目 29）。
- 长上下文先经历平稳期，再缓慢下降，越过 Knee Point 后急剧恶化；测试应记录拐点而不是只报一个平均值（语料题目 31）。
- JMeter 默认把整个流式响应当一个事务，测不到首包时间，需要用 JSR223 监听器或 TCP Sampler 单独记首个数据块（`corpus/yuque/md/159-lkac52hhug20psgv.md:33-44`）。
