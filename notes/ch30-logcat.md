# 第 30 章 · 用 logcat 定位崩溃与 ANR

界面只能告诉你「现在长什么样」，日志才能告诉你「刚才发生了什么」。

## 1. logcat 的四种读法

| 命令 | 拿到什么 | 典型用途 |
| --- | --- | --- |
| `adb logcat -d` | 当前缓冲区全部 | 一次性抓取 |
| `adb logcat -d -t 200` | 最近 200 行 | 失败后快速取证 |
| `adb logcat -d -s <tag>` | 只该 tag | 只看应用自己的日志 |
| `adb logcat -d -b crash` | 崩溃缓冲区 | 只看崩溃 |

`-d` 是「打印后退出」，不加它会一直阻塞——脚本里忘了加就会卡住。

## 2. 三条特征行

| 特征 | 含义 | 后续怎么看 |
| --- | --- | --- |
| `FATAL EXCEPTION` | Java 层崩溃 | 后面几行的 `at com.xxx` 是调用栈 |
| `ANR in <pkg>` | 主线程卡死 | 看 `Reason:` 与 `CPU usage` |
| `E/AndroidRuntime` | 通常与崩溃同现 | 用别的 tag 交叉验证 |

崩溃行本身信息很少，价值在紧随其后的堆栈；所以「抓崩溃」要连带抓上下文 N 行。

## 3. 按包名过滤，但别只信它

```python
errors = applog.errors_related_to(lines, package="com.shenjiahang.logindemo")
```

应用自己的错误通常带包名或类名；但系统级问题（OOM、系统服务崩）可能不带。所以过滤结果为空时，要退回看全量 `E` 行——这条是踩过的坑：某次「日志里没有异常」其实是过滤太狠。

## 4. 摘要比全文好用

一次执行几千行日志，人不会读。`digest()` 只输出：崩溃条数、首个 ANR 原因、前三条错误行。报告里放摘要，原始日志落文件。

## 常见坑

1. **没加 `-d` 导致阻塞**：脚本挂住，看起来像设备卡了。
2. **缓冲区被冲掉**：日志滚动很快，失败后要立刻抓，别等跑完十条再抓。
3. **用例之间不清空**：上一条的崩溃算到这一条，误判率极高。
4. **只看 `FATAL`**：ANR 不一定有 FATAL，会漏。

## 附：自测答案

1. 不带 `-d` 会持续输出并阻塞，`-d` 打印当前缓冲区后退出。
2. `FATAL EXCEPTION` 之后的堆栈行（`at 包名.类名.方法`），它指出崩溃位置。
3. 清空缓冲区，保证日志只属于本条用例，避免张冠李戴。
4. `FATAL EXCEPTION`、`ANR in`、`E/AndroidRuntime`。

## 学生常问

**Q：日志里全是系统噪音怎么办？**

A：先按包名或 tag 过滤，再按等级 `E`/`F` 收窄；仍然太多就只取最近 N 行。

**Q：ANR 一定要复现才能修吗？**

A：不一定。ANR 日志里有 `Reason:`（比如输入事件超时）与主线程堆栈，很多问题看日志就能定位到具体调用。

**Q：崩溃日志要进仓库吗？**

A：不进。日志属于运行产物，落到 `out/` 并写进 `.gitignore`，报告里留路径与摘要。

## 面试题

**Q：线上崩溃和测试环境崩溃的排查差异？**

A：测试环境能随时抓 logcat 与截图；线上要靠崩溃上报（堆栈 + 设备信息 + 版本），所以测试阶段就要养成「崩了立刻留三样证据」的习惯。

**Q：怎么判断一个失败是应用崩溃还是断言写错？**

A：先看前台 Activity 是否还在、界面是否还是预期页面，再看 logcat 有没有 FATAL/ANR。都没有，多半是断言或数据问题。

**Q：日志级别怎么用才不乱？**

A：约定清楚：`E` 只给真实错误、`W` 给可恢复异常、`I` 给关键流程节点。级别用错，过滤就失效。

## 延伸知识

- `adb logcat -d --pid=<pid>`：只看某个进程。
- `adb shell dumpsys activity processes | grep <pkg>`：确认进程是否还活着。
- `-b crash` 与主缓冲区可以分别抓，互不干扰。
- 给日志加统一前缀（如 `[QA]`），过滤时最省事。
