# 第 39 章 · 性能平台收口

前七章是零件：指标、场景、脚本、分析、中间件、全链路、AI 辅助。这一章把它们拼成一台机器：一条命令、一份配置、一份报告、一个能进 CI 的退出码。

## 1. 交付标准

| 标准 | 怎么满足 |
| --- | --- |
| 不依赖特定环境 | `config.yaml` 的 `envs` 里写地址，命令行 `--env` 切换 |
| 不改代码就能调场景 | 场景、档位、门槛全在 `scenarios` 里 |
| 跑完有可读结论 | Markdown 报告（人看）+ 退出码（CI 看） |
| 退出码正确 | 0 全通过 / 1 有未达标 / 2 配置错误 |

## 2. 分层

```
config.yaml → perf_platform.main → runner（真实压测或假 runner）
                        ↓
                   Report → gate → Markdown
```

- **配置**：环境、场景、阈值。校验放在最前面：缺 `default_env`、没有场景、场景名重复、场景缺 `levels`，都在起压之前报错退出。
- **门槛**：`gate()` 逐条比对 `p95_limit_ms` 与 `error_limit`，不达标的写进 `failures`。
- **报告**：只负责渲染，不做判断。

## 3. 命令行

```bash
python labs/ch39-perf-platform/perf_platform.py
python labs/ch39-perf-platform/perf_platform.py --env staging --only 健康检查 --report out/report.md
```

实测（无真实 runner 时会把场景记为失败，这是预期行为，用来验证门槛链路）：

```
# 性能测试报告（local）

- 场景数：0
- 通过：0
- 失败：2
```

接上真实 runner 后，`--only` 可以只跑一个场景；`--report` 落盘 Markdown 并打印到终端。

`labs/ch39-perf-platform/`：`perf_platform.py`（`ConfigError` / `ScenarioSpec` / `Result` / `Report` / `load_config` / `gate` / `to_markdown` / `main`）、`config.yaml`、`test_perf_platform.py`（9 条）。


九条测试用假 runner 覆盖：配置校验三类错误、阈值判定、门槛收集、报告渲染、三种退出码。

## 5. 常见坑

1. **门槛写死在一个全局常量里**：不同场景的 SLA 不同，阈值必须跟着场景走。
2. **配置校验放在起压之后**：环境名写错要等十秒建连接才报错，浪费时间且容易误判为性能问题。
3. **退出码永远 0**：CI 里等于没有门槛，报告再漂亮也没人看。
4. **报告只给平均值**：评审要看 P95 与错误率，平均值会掩盖长尾。
5. **runner 与平台耦合**：`main()` 通过参数接收 runner，才能在测试里用假实现，也才能换压测引擎。

## 附：自测答案

1. 配置错是「还没开始跑就能知道」的错误，先校验能避免每次压测白等一轮连接与预热，也让错误信息更准确。
2. 0 全部通过；1 有用例未达标；2 配置或环境错误（没跑起来）。
3. 可测试性 + 可替换性：测试用假 runner 才能离线验证门槛与报告；生产可以换成本机 LoadGen 或外部压测引擎。
4. 环境标识、逐条结果（并发、TPS、P95、错误率）、未达标原因（越了哪个阈值）。
5. 配置里。同一套代码要给不同服务用不同 SLA，写死就意味着每次改代码。

## 学生常问

Q：为什么还要自己写平台，直接用 JMeter/Locust 不行吗？

A：工具解决「压」，平台解决「统一口径 + 门槛 + 报告 + 归档」。这一章的代码量很小，价值在于把口径固定下来，CI 能稳定判断通过与否。

Q：报告为什么要 Markdown？

A：GitHub、Jenkins、飞书都能渲染，且能直接进 PR 评论；JUnit XML 留给 CI 消费，两者不冲突。

Q：多环境怎么管？

A：`envs` 里一段一个环境，`--env` 切换；密钥走环境变量，不写进 yaml。

## 面试题

Q：给你一套压测平台，你怎么验收它？

A：四件事。一、命令能在三行内跑起来（装依赖、改配置、运行）。二、失败信息能说人话（哪个场景、哪一档、越了哪个阈值）。三、报告能直接贴给别人（环境、逐条结果、结论）。四、退出码能被 CI 用。

Q：平台化的收益是什么？

A：口径统一（所有服务用同一套指标与门槛）、可回归（每次发版跑同一套场景）、可追责（报告留档，性能退化能被发现）。

Q：压测平台和监控平台怎么分工？

A：压测平台回答「能不能扛住预期压力」，监控回答「线上现在怎么样」。前者在发布前，后者在运行时；两者共享指标口径才有意义。

## 延伸知识

- `--only` 支持子串匹配就够日常用，复杂筛选可以加 `--tag`。
- 报告里给「与上次对比」比给绝对值更有价值，需要落一份历史结果。
- 门槛可以分级：warning 只提醒、error 卡 CI。
- 平台自身的日志要记录「本次用的配置快照」，否则复现不了。
- 真正交给别人前，把 `--help` 补上，比写十页文档有用。
