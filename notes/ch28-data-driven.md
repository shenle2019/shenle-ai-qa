# 第 28 章 · 数据驱动与多用例

一条用例用三个账号跑，不该复制三份；一条挂了，不该拖垮后面九条。

## 1. 用例写成数据

```yaml
- id: login-correct
  title: 正确账号密码能登录成功
  action: login
  params: {username: justin, password: "123"}
  expect: {text_contains: '"code": 100'}
```

四个字段就够了：`id`（唯一、用于 `--only`）、`title`（报告里给人看）、`action`（对应一个函数）、`params` + `expect`（输入与预期）。

## 2. 动作表：数据到函数的桥

```python
HANDLERS = {
    "login": lambda page, p: page.set_credentials(p["username"], p["password"]).tap_correct(),
    "login_wrong": lambda page, p: page.set_credentials(p["username"], p["password"]).tap_wrong(),
    "load_photo": lambda page, p: page.tap_photo(),
}
```

新增一种操作就是加一行，不用改 runner。动作名写错要在**加载阶段**报错，别等到执行到一半才发现。

## 3. 失败不中断

`run_case` 里把异常收进 `Result(ok=False, detail=...)`，`run_all` 继续跑下一条。这一条看起来简单，但它决定了报告的价值：一次跑完能看到「哪几条挂了」，而不是「第一条挂了，剩下的没跑」。

循环里每条之前 `force-stop` + 重新打开，保证用例之间不残留状态；代价是慢（每条 2~5 秒），收益是可单独重跑。

## 4. 汇总要能给人看

`summary()` 输出「共 N 条，通过 X，失败 Y」+ 失败名单。失败名单比总数更重要：它就是第二天的待办列表。

## 常见坑

1. **yaml 里 `password: 123` 读成整数**：加引号，或加载时统一 `str()`。
2. **用例之间互相污染**：上一条登录了，下一条 `title-visible` 就直接在首页。每条前重启 App。
3. **`expect` 写太死**：断言整段 JSON 会在字段顺序变化时挂，断 `"code": 100` 这种关键片段更稳。
4. **`id` 重名**：加载时校验唯一性，否则 `--only` 会跑两条。

## 自测

1. 为什么 `action` 要在加载阶段校验，而不是执行时？
2. 一条用例失败后，为什么还要继续跑后面的？
3. 每条用例前都重启 App，代价是什么？收益是什么？
4. `expect` 里为什么建议用「片段包含」而不是「全等」？

## 附：自测答案

1. 加载阶段校验能在跑之前就告诉你有几条配错，避免「跑了一半才发现 action 拼错」。
2. 失败不中断能一次拿到全部问题；否则修一个跑一次，迭代成本高。
3. 代价是时间（每条多 2~5 秒），收益是隔离（不吃上一条的登录态、滚动位置）。
4. 全等对格式敏感（空格、字段顺序），片段包含更能反映「业务上要看到什么」。

## 学生常问

**Q：数据驱动和参数化有什么区别？**

A：本质一样，粒度不同。`@pytest.mark.parametrize` 是「一个函数多组数据」；数据驱动是「一个 yaml 描述整个流程」，更适合跨界面、跨动作的长链路。

**Q：用例数据放仓库里安全吗？**

A：账号密码这类敏感值放环境变量或用测试专用账号；yaml 里只放不敏感的参数。

**Q：要不要给每条用例加前置条件？**

A：要，但要简单。这里用「重启 App」统一处理；如果某条需要特殊前置（比如已登录），就单独写一个 `action`。

## 面试题

**Q：怎么设计一个可扩展的用例引擎？**

A：三个组件：用例数据（yaml）、动作表（name → 函数）、执行器（循环 + 结果收集）。新增能力只加动作，不改执行器。

**Q：批量执行时怎么定位失败原因？**

A：每条结果带 `detail`（异常信息 + 当前界面摘要），失败的用例附截图。只有「通过了」才算过，其它都要有可追的证据。

**Q：几十条用例跑 10 分钟，怎么提速？**

A：能并行的按设备分组；不能并行的去掉不必要的重启（只在改状态的用例前后重启）；把等待改成条件轮询。

## 延伸知识

- `--only login` 支持前缀匹配，可以先只跑一遍失败的。
- 结果对象序列化成 JSON，后面接 CI 就能直接解析。
- 用例 `id` 用「场景-变体」命名，报告里一眼能看出覆盖了哪些分支。
- 数据驱动天然适合做「同一流程多组数据」的冒烟集。
