# 第 31 章 · 框架收口：一个能交给别人的 APP CLI

前面七章是零件，这一章把它们装成一台机器：一条命令、一份配置、一份报告。

## 1. 交付标准

一个 APP 自动化框架能不能交给别人，看四件事：

| 标准 | 本章怎么满足 |
| --- | --- |
| 不依赖特定环境 | `config.yaml` 里写包名/Activity/用例路径，不写死个人路径 |
| 不靠改代码跑用例 | `--only` 过滤、yaml 加用例 |
| 跑完有可读结论 | Markdown 报告（给人）+ 结果对象（给程序） |
| 退出码正确 | 0 全通过 / 1 有失败 / 2 配置或设备问题 |

最后一条经常被忽略：CI 只看退出码，退出码永远是 0 的框架等于没有门禁。

## 2. 分层

```
config.yaml → app_framework.py → login_page.py → 设备
                    ↓
              cases.yaml（ch28）
```

- **配置**：包名、Activity、用例文件路径、设备超时；
- **框架**：读配置、起后端、连设备、跑用例、出报告；
- **页面**：业务动作；
- **报告**：只格式化，不做判断。

## 3. 命令行

```bash
# 跑全部
.\.venv\Scripts\python.exe labs/ch31-framework/app_framework.py

# 只跑某组
.\.venv\Scripts\python.exe labs/ch31-framework/app_framework.py --only login --report out/r.md
```

输出长这样：

```
[PASS] login-correct   5.6s  正确账号密码能登录成功
[PASS] load-photo      5.4s  网络图片能下载并渲染
共 4 条，通过 4，失败 0（设备 FA7B11A03073）
报告已写入：out/r.md
```

## 4. 三个容易做错的地方

1. **配置校验放在启动设备之前**。配置错（比如 `default_env` 写错、`cases` 路径不存在）应该秒报错，不要先花 10 秒连设备再崩。
2. **后端要自己起**。CLI 是给别人用的，不能假设「你先手动开一个服务」。`LoginServer` + `adb reverse` 由入口负责。
3. **CLI 的测试要用子进程**。在 pytest 里直接调 `main()` 会和已经启动的 adb/设备会话打架；用 `subprocess.run([sys.executable, ...])` 才是真正验证「别人拿到能不能跑」。

## 5. 本章实操

`labs/ch31-framework/`：`config.yaml`、`app_framework.py`（`load_config` / `run` / `Report` / `main`）、`test_app_framework.py`。

```bash
.\.venv\Scripts\python.exe -m pytest labs/ch31-framework -q
.\.venv\Scripts\python.exe labs/ch31-framework/app_framework.py --report out/report.md
```

报告含：设备号、开始时间、总通过数、逐条耗时与失败说明。

## 常见坑

1. **模块路径**：直接 `python xxx.py` 跑时，`labs` 包不在 `sys.path` 里，要在入口把仓库根和需要的章目录插进去。
2. **退出码不设**：跑挂也返回 0，CI 永远绿。
3. **报告写相对路径**：从别的目录调用就写错地方，应基于脚本位置解析。
4. **用例与设备耦合**：用例里写死 serial，换机器就跑不了；serial 由入口传入。

## 自测

1. 为什么配置校验要放在连设备之前？
2. CLI 退出码 0/1/2 分别代表什么？
3. 为什么测试 CLI 要用子进程而不是直接调 `main()`？
4. 报告里最该有哪三样信息？

## 附：自测答案

1. 配置错是「还没开始就能知道」的错误，先报错能省掉一次设备连接与一次误导性的失败。
2. 0 = 全部通过；1 = 有用例失败；2 = 配置/设备/环境问题（没跑起来）。
3. 同进程里已经存在 adb 与设备会话，直接调 `main()` 会互相干扰；子进程才是「别人拿来用」的真实场景。
4. 设备标识、逐条结果（含耗时与失败原因）、总通过率。没有设备号就无法复现。

## 学生常问

**Q：为什么不直接用 pytest 当框架？**

A：可以，而且 CI 里更常见。本章的 CLI 是「生产化」视角：配置驱动、可传参、退出码、给人看的报告。两者不冲突，pytest 负责断言，CLI 负责编排。

**Q：报告为什么要两种格式？**

A：Markdown 给人看（贴到 PR 或工单），JSON/对象给程序看（接钉钉、接看板）。生成时共用同一个结果对象。

**Q：多设备怎么扩展？**

A：把「设备」变成循环变量：每台设备一个 `App`，用例按设备并行；报告按 serial 分组。配置里加一个 `devices:` 列表就够了。

## 面试题

**Q：一个自动化框架，你最先保证哪件事？**

A：可重复。同一条命令在同一环境下结果稳定，否则后面的报告、门禁都不可信。

**Q：怎么让别人愿意用你的框架？**

A：三条命令能跑起来（装依赖、改配置、运行），失败信息说人话，报告能直接贴给别人。

**Q：框架里的「配置」应该包含什么、不该包含什么？**

A：包含环境相关（包名、Activity、设备、路径、超时）；不包含业务断言与账号密码（前者属用例，后者属密钥管理）。

## 延伸知识

- 退出码 2 与 1 分开，CI 才能区分「环境坏了」和「用例挂了」。
- 报告文件名带时间戳，历史结果可对比。
- 配置支持环境变量覆盖（`APP_PACKAGE=...`），同一条命令切环境。
- 把「重试后通过」单独计数，能看出哪些用例长期不稳。
