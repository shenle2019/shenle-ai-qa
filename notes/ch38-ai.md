# 第 38 章 · AI 辅助性能分析

这一章不吹「AI 帮你调性能」。真实可用的分工是：**机器做结构性工作（找异常、聚类日志），模型做表达性工作（把证据写成结论）**。顺序反了，就会得到一段听起来专业但抓不住重点的话。

## 1. 异常检测：滚动 z-score

```python
detect_anomalies([100, 102, 99, 101, 100, 103, 100, 400], window=5, threshold=3.0)
# [Anomaly(index=7, value=400, score=..., kind='spike')]
```

用最近 5 个点算均值与标准差，当前点偏离 3 个标准差以上就算异常。两个细节：

- **窗口内标准差为 0 时跳过**，否则任何常数序列都会除零或误报。
- 能识别双向异常：`spike`（突增，通常是超时/重试）和 `drop`（突降，通常是服务挂了被熔断）。

这比「P95 超过阈值就报警」好在：阈值是相对的，能自适应不同量级的接口。

## 2. 日志聚类：把「一万行」压成「五个模板」

```python
normalise("user 12345 order 9f8e7d6c-1111-2222-3333-444455556666 took 250ms")
# 'user <n> order <uuid> took <n>ms'
```

规则很简单：UUID → `<uuid>`，长十六进制 → `<hex>`，数字 → `<n>`。相同的模板归一类，按数量倒序取 Top N，再各留一条样本。

这是性能分析里性价比最高的一步：报错日志往往 90% 是同一个模板，看模板比看原文快得多。

## 3. 提示词：只喂结构化证据

`build_prompt()` 只放四类数字：平台期并发、峰值 TPS、最差 P95、最高错误率，外加异常点列表。并且写死输出格式：**一句结论 + 两条引用数字的依据 + 一条下一步动作，不超过 120 字**。

为什么要限制这么死：

- 不限制就会输出「建议优化数据库、加缓存、扩容」这种正确但没用的话。
- 要求「引用具体数字」能逼模型对齐证据，减少编造。
- 限长能放进报告的一行里。

## 5. 常见坑

1. **把原始日志整段丢给模型**：又慢又贵，还会因为噪声给出错误结论。先聚类、再摘要。
2. **让模型「猜」瓶颈**：没有 in_flight/pool_wait 这类证据，模型只能编。
3. **不看模型输出的数字**：模型引用的数字如果与报告不符，整段结论都要作废。
4. **用模型替代判定**：拐点、错误率这些该算的必须自己算，模型只负责解释。
5. **没有 fallback**：模型超时/限流时，报告要能退化成本地模板文案。

## 6. 自测

1. 为什么 z-score 要跳过「窗口标准差为 0」的情况？
2. 日志聚类为什么先归一化再统计，而不是直接按原文分组？
3. 提示词里为什么要求「引用具体数字」？
4. AI 结论与本地判定冲突时，信谁？
5. 没有模型可用时，这一章的功能还能用吗？

## 附：自测答案

1. 常数窗标准差为 0，除法会报错或产生无穷大分数；而且常数序列里出现任何变化都不该按 z-score 判异常。
2. 原文里带用户 ID、订单号、耗时，几乎每行都不同；归一化后同一类问题才会落到同一个模板上，统计才有意义。
3. 强制模型对齐证据，减少「泛泛而谈」与编造；同时让读者能核对数字。
4. 信本地的判定（拐点、错误率是算出来的），模型结论只当表达层；冲突时以数字为准并检查提示词是否漏了关键证据。
5. 能。异常检测、聚类、模板化结论都是纯本地逻辑；`explain` 支持传入任意 callable，可退化成规则模板。

## 学生常问

Q：一定要用大模型吗？

A：不一定。这一章的三个能力里，前两个完全不依赖模型；只有「写成自然语言」这一步需要。很多团队用模板拼句子就够了。

Q：模型会不会把结论说反？

A：会，尤其在证据缺失时。所以提示词要限定「只能用给定数据」，并在输出后做一次数字核对（引用的数字必须出现在报告里）。

Q：压测报告里 AI 结论放在哪？

A：放摘要区，一段话，后面紧跟证据表。评审的人先看结论，再核对表格。

## 面试题

Q：你怎么把 AI 用到性能测试里？

A：三处。一、异常检测：滚动统计找毛刺，替代固定阈值。二、日志聚类：把海量错误压成模板 Top N。三、报告生成：把结构化结果写成一段结论，并强制引用数字。核心原则是「机器算证据、模型写表达」，不让模型做判定。

Q：AI 分析的结论不可信怎么办？

A：两个手段：证据约束（提示词只喂结构化数据、要求引用数字）与结果校验（引用数字必须能在报告里找到；找不到就丢弃该段）。再加本地兜底文案。

Q：日志聚类用什么算法？

A：简单场景正则归一化 + 计数就够；复杂场景可以用 Drain 这类模板挖掘算法，或者在归一化后用相似度聚类。关键是先把变量（ID、时间、耗时）抽掉。

## 延伸知识

- 滚动窗口的大小决定灵敏度：窗口越大越稳、越迟钝，压测场景一般 5–10 个点。
- 异常分数要保留原始值，方便在报告里给出「第 7 个点 400ms，偏离 3.2σ」。
- 聚类结果可以按「模板 + 首次出现时间」排序，快速看出「从哪一档开始出现新错误」。
- 提示词里给出「反例」（不要说什么）比只给「正例」更有效。
- 模型输出要落盘存档，便于复盘时对比「当时的结论 vs 后来的事实」。
