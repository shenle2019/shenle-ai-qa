# 第 13 章 · 业务链路与数据准备

单接口测的是「这个口对不对」，链路测的是「这条业务能不能走通」。这一章解决三件事：怎么串、数据哪来、跑完怎么收。

## 1. 链路用例的骨架

```
登录 → 建单 → 支付 → 查订单 → 断言状态与金额 → 清理
```

写成代码就是一个函数，**不要拆成四条互相依赖的用例**：

```python
def test_order_flow(client):
    token = login(client)
    order = create_order(client, token)
    pay(client, order["id"], token)
    got = get_order(client, order["id"], token)
    assert got["status"] == "paid"
```

拆成四条会让「支付失败」时前三条都绿，第四条才红，定位反而变慢。

## 2. 数据从哪来

三种来源，优先级从高到低：

| 来源 | 适用 | 风险 |
| --- | --- | --- |
| 接口自己造（推荐） | 大部分场景 | 造数接口本身可能有 bug |
| 数据库直插 | 造数接口缺失、需要脏数据 | 绕过业务校验，数据可能不合法 |
| 固定夹具数据 | 只读查询、字典表 | 多轮跑会互相污染 |

造数要带**唯一标识**，否则第二轮就撞 409：

```python
def unique_phone(seed: int) -> str:
    # 11 位只装得下 10^9 个号：seed 超出范围按模回绕（格式恒对），
    # 「同一个号绝不重复」得靠已用集合 + 重试，seed 本身保证不了。
    return "13" + f"{seed % 10**9:09d}"
```

## 3. 清理必须自动

```python
@pytest.fixture
def order(client, token):
    created = create_order(client, token)
    yield created
    try:
        client.delete(f"/api/orders/{created['id']}")
    except ApiError:
        pass          # 已删除 / 不可删都算正常
```

三条规矩：

1. **不要放用例末尾**，用例一失败就漏；
2. **清理失败不要盖住原错误**，`except` 吞掉即可；
3. **造的数据带前缀**（如 `qa_`），方便定期批量清理。

## 4. 幂等与重试

链路里最贵的 bug 是「重复提交」。接口有 `Idempotency-Key` 时，用例要同时验两件事：

```python
first = post("/api/orders", json=payload, headers={"Idempotency-Key": "k1"})
second = post("/api/orders", json=payload, headers={"Idempotency-Key": "k1"})
assert first["id"] == second["id"]     # 同单
assert second.status_code == 200       # 第二次不是 201
```

没有幂等键的系统，客户端要自己保证：重试只对 GET/PUT/DELETE。

## 5. 并发不是「多跑几次」

真正要验的是「同时到达」：

```python
with ThreadPoolExecutor(max_workers=2) as pool:
    results = list(pool.map(lambda _: pay(order_id), range(2)))
statuses = sorted(r.status_code for r in results)
assert statuses == [200, 409]
```

断言的是**状态组合**，不是「谁赢」。否则用例会随机红。

## 7. 自测

1. 为什么链路用例不该拆成四条依赖用例？
2. 造数接口本身有 bug 时，怎么保证用例不背锅？
3. 清理为什么放在 fixture 的 `yield` 之后，而不是用例最后一行？
4. 幂等键重复提交，第二次应该返回 200 还是 201？为什么？
5. 并发用例断言「状态组合」而不是「谁赢」，好处是什么？

## 附：自测答案

1. 拆成四条后，每条都要自己准备前置（登录、造单），失败点分散、排查要跨用例；链路用例的价值是「一次走完、失败即停在断点」，能直接指出是第几步断的。
2. 造数走独立接口并断言造数结果；造数失败直接 `pytest.skip` 或标为环境错误，不要算成业务失败。这样「接口坏了」和「造数坏了」在报告里能分开。
3. `yield` 之后的代码在用例结束后一定执行（即使用例抛异常）；写在用例最后一行则异常时被跳过，脏数据残留，下次跑就撞车。
4. 200，且 body 里的 id 与首次相同。201 的语义是「新建了资源」，重复键并没有新建，返回 201 会误导客户端。
5. 并发结果本身不确定，断言「状态组合」表达的是「要么成功、要么被正确拒绝」，这既覆盖了业务规则，又不会因为线程调度随机变红。

## 学生常问

**Q：链路用例太长，失败不好定位怎么办？**

A：每一步都断言，并在断言消息里写清步骤号；或者用「步骤记录器」把每步的请求/响应存下来，失败时直接看断点前那一步。

**Q：并发用例怎么造？**

A：用线程池同时发同一个请求，收集所有结果再断言集合。注意服务端可能限流，数量别太大（2–4 个并发足够验证规则）。

**Q：数据清理失败会不会影响后面的用例？**

A：会。清理失败要记警告并继续，同时数据名带唯一前缀，方便事后批量清理；不要因为清理失败把用例判红，那会掩盖真正的业务问题。

## 面试题

**Q：业务链路测试和单接口测试的分工？**

A：单接口测「这个口对不对」（参数、状态码、边界），链路测「这条业务能不能走通」（状态流转、数据一致性、权限）。两者都要有，比例大概单接口多、链路少而关键。

**Q：怎么保证链路用例可重复执行？**

A：每次跑都造新数据（唯一标识）、用完即清理、不依赖历史数据、不依赖执行顺序；对不可清理的资源（真实支付）就别自动化。

**Q：接口有幂等键，测试要覆盖什么？**

A：同一键重复提交返回同一结果（200 + 同 id）、不同键创建不同资源、无键重复提交按业务规则处理（409 或新建）。还要验证幂等键过期/复用的边界。

## 延伸知识

- 状态机要测「非法流转」：已取消的订单不能再支付，已支付的不能再取消，这类用例最容易漏。
- 断言数据一致性：下单后查订单详情、查列表、查库存，三处应一致。
- 链路里任何一步的 id 都要用变量传递，不要写死；写死就是一次性用例。
- 失败重试只加在「环境抖动」可能发生的地方（建连、读超时），不要给业务断言加重试。
