# 第 9 章 · 用 AI 生成接口用例（以及为什么不能全信）

AI 能在几分钟内产出一百条用例，也能在几分钟内产出一百条**看起来对、其实跑不了**的用例。差别不在模型，在你喂进去的东西和接出来的流程。

这一章讲三件事：怎么把接口文档变成用例矩阵、怎么写出能用的提示词、生成之后怎么审。

## 1. 先把文档变成矩阵，再让 AI 填

不要一上来就让模型「给这个接口写 30 条用例」。先自己列维度，模型只负责在每个格子里填内容：

| 维度 | 取值 |
| --- | --- |
| 参数 | 必填缺失、类型错、超长、越界、非法枚举、多余字段 |
| 位置 | query / path / body / header 放错 |
| 鉴权 | 无 token、过期 token、他人资源、低权限 |
| 业务状态 | 初始态、进行中、终态、非法流转 |
| 幂等/并发 | 重复提交、同 key、并发两次 |
| 数据量 | 0 条、1 条、边界条数、超上限 |
| 兼容 | 新增字段、字段改名、空值语义 |

一个接口 7 个维度、每维 2–3 个取值，就是 15–20 条用例，**覆盖是设计出来的，不是模型想出来的**。

## 2. 提示词的四段结构

```
【角色】你是接口测试工程师，服务端是 FastAPI + SQLite。
【输入】以下是接口契约（OpenAPI 片段）+ 业务规则（3 条）。
【任务】按给定的维度矩阵，为每个接口生成用例；每个格子至少 1 条。
【输出】严格输出 JSON 数组，字段固定：id/title/priority/type/precondition/steps/request/expected/asserts。
   约束：expected 必须可判定（状态码 + 字段 + 值），禁止出现「正常返回」这类描述。
```

四个要点：

1. **给契约，不给截图**。OpenAPI / JSON Schema 比「接口文档截图」准确得多。
2. **给维度，不给形容词**。「覆盖全面」没有信息量，「必填缺失 / 类型错 / 越界各一条」才有。
3. **给输出 schema**。字段固定，后面才能自动化校验。
4. **给硬约束**。`expected` 必须可判定，这条能过滤掉大半废话。

## 3. 生成之后必须过的五道审

| 检查 | 不通过的典型样子 | 处理 |
| --- | --- | --- |
| 可执行 | 「验证系统稳定运行」 | 删或改写 |
| 可判定 | 「返回正确的数据」 | 补状态码与字段断言 |
| 不重复 | 同一维度 8 条，另一维度 0 条 | 按矩阵补缺口 |
| 前置清楚 | 没说要不要登录、用哪个账号 | 补 precondition |
| 数据可造 | 要求一个不存在的「已退款订单」 | 标依赖，交给数据准备 |

审完再进用例库。**AI 负责产量，人负责覆盖与判定**——这条分工不能反。

## 4. 用覆盖矩阵验收「生成得好不好」

生成 30 条不代表覆盖 7 个维度。跑一遍矩阵统计：

```
接口              参数  位置  鉴权  状态  幂等  数据量  兼容
POST /api/users    5     1     3     2     2     3      0   ← 兼容维度是空的
GET  /api/users    4     1     2     0     0     3      1
```

空格子就是下一轮的输入。这个矩阵可以脚本化（本章实验就做了一个）。

## 5. AI 在接口测试里真正擅长的四件事

1. **从文档抄成用例骨架**：把 OpenAPI 的字段约束翻译成边界值。
2. **补异常分支**：人容易漏 409/422/429 这类错误码。
3. **写断言**：把「返回正确」翻译成「`status==201` 且 `id` 是正整数且 `Location` 匹配 `/api/users/\d+`」。
4. **解释失败**：把响应体和请求体一起给它，让它判断是断言写错还是服务端错（第 14 章做）。

不擅长的：判断业务规则对不对、决定优先级、知道哪些用例值得自动化。

## 6. 本章实操

`labs/ch09-ai-cases/`：

- `spec.py`：一份手写的接口契约（三个接口，带字段约束），模拟 OpenAPI 的子集；
- `matrix.py`：按维度矩阵生成用例，输出覆盖统计；
- `prompt.py`：把契约 + 矩阵拼成提示词（含 JSON schema 与硬约束）；
- `review.py`：对「模型产出的用例」做五道审，输出可执行/需修改/丢弃三档。

```powershell
.venv\Scripts\python.exe labs\ch09-ai-cases\run_demo.py
.venv\Scripts\python.exe -m pytest labs\ch09-ai-cases -q
```

实验里不调用真实模型：`review.py` 审的是一份**故意写坏的样例**（含「返回正确」「验证稳定性」这类），你能直观看到五道审怎么把它们筛掉。

## 7. 自测

1. 为什么先列维度再让 AI 填，比直接让 AI「写 30 条」更好？
2. 你的提示词里如果漏了输出 schema，会在哪一步付出代价？
3. 「期望结果必须可判定」这条约束，能过滤掉哪三类用例？
4. 覆盖矩阵里某一格是 0，你应该补用例还是删维度？判断依据是什么？
5. 举一个「AI 生成得很对，但你不该自动化」的用例。

## 附：自测答案

1. 维度先定等于先划好搜索空间：每个格子都必须有交代，缺了能看见；直接让 AI「写 30 条」它会在容易的地方堆量、难的地方跳过，你拿到一堆重复用例还没法判断覆盖率。
2. 会在「解析结果」这一步付出代价：字段名漂移、结构化失败、要写一堆兜底和重试，最后还是要人工整理，等于白让 AI 干一遍。
3. 这条约束筛掉三类：只写「功能正常 / 返回正确」没有可观测结果的、只断状态码不写字段与值的、多个期望混成一句没法判成败的。
4. 先判断这一格对该接口是否适用：比如「文件上传」维度对纯 JSON 接口就不适用，标注 N/A 即可；适用却为 0，就必须补用例。
5. 例子：一次性运营活动的报名接口——数据不可重复造、名额有限、牵涉真实业务资源；或涉及真实支付扣款、不可回滚的场景。这类适合人工验证 + 监控，不适合进自动化。

## 学生常问

**Q：AI 生成的用例能直接用吗？**

A：不能。它是草稿，必须过五道审：可执行、可判定、不重复、前置清楚、数据可造。审完通常要删掉三分之一、改写三分之一，剩下的才是能进仓库的。

**Q：提示词要写多长？**

A：够用就行，但四段不能少：角色、输入（接口定义/字段/规则）、任务（按维度补哪些格子）、输出（JSON schema + 硬约束）。约束越具体，返工越少。

**Q：怎么让 AI 生成的期望结果可判定？**

A：要求它写「状态码 + 关键字段 + 字段值或格式」，例如「返回 201，body.id 为非空整数，body.name 等于入参 name」。禁止出现「正常」「成功」这类词。

## 面试题

**Q：你怎么评估一组接口用例的覆盖度？**

A：接口 × 维度矩阵：行是接口，列是参数/位置/鉴权/状态/幂等/数据量/兼容，逐格填数量，空格即为缺口；再叠加业务链路（跨接口的场景）和异常路径的比例。覆盖率不追求 100%，但每个高风险接口的关键维度不能为空。

**Q：AI 生成用例的准确率怎么量化？**

A：用一批人工标好的样本做基准：生成 N 条，统计「可直接采纳 / 需修改 / 丢弃」的比例，再看漏报（人工有而 AI 没有的）。只看生成数量没有意义。

**Q：用例设计里「等价类 + 边界值」为什么仍然重要？**

A：它们决定了抽样是否合理。AI 容易在中间值上堆用例，边界（0、1、最大值、超一位、空串）才是 bug 高发区，这一层必须人工把关。

## 延伸知识

- 覆盖矩阵要跟着接口变化更新，否则半年后没人知道哪些格子是「没测」还是「不需要测」。
- 用例的「前置」写不清楚，自动化就一定不稳；前置里出现「先手动登录」的，等于还没设计完。
- 期望结果里避免写死自增 id 和时间戳，用范围、格式或相对断言。
- 把「不该自动化的用例」明确列出来（一次性活动、真实支付、需要人工判断的视觉验收），比硬塞进 CI 更专业。
