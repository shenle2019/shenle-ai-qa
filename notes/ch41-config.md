# 第 41 章 · 项目配置与环境上下文

一个平台的配置只有一个来源：config.yaml 管结构，环境变量管密钥。读的时候展开 ${VAR}，取不到就报错；打印与接口返回时按键名脱敏。

## 1. 结构

| 层 | 内容 |
| --- | --- |
| default_env | 不指定 --env 时用哪个 |
| `envs.<name>.base_url` | 每个环境一个地址，必填 |
| `envs.<name>.variables` | 变量表，支持 `${VAR}` 展开 |
| settings | 超时、重试这类全局参数 |

## 2. 三条铁律

1. **不静默**：${QA_TOKEN} 取不到直接 ConfigError，不允许变空串——空 token 打出去的请求会得到 401，然后被误判成权限问题。
2. **加载即展开**：读进内存时就替换完，后续代码只使用最终值，避免「有的地方展开了、有的没展开」。
3. **输出即脱敏**：mask() 按键名含 	oken/password/secret/api_key 替换成 ***，日志与接口共用。

## 4. 常见坑

1. 把密钥写进 yaml 并提交——一旦进 Git 历史就清不掉。
2. 默认环境写错，起服务才发现。
3. 变量只展开一层，${A} 里再嵌 ${B} 就不管了。
4. 脱敏按值匹配，导致 lice 也被打星。
5. 每个环境复制一整份配置——改为「公共段 + 覆盖段」更好维护。

## 5. 自测

1. 为什么取不到环境变量要抛错而不是给空串？
2. 加载即展开比「用的时候再展开」好在哪？
3. 脱敏为什么按键名而不是按值？
4. default_env 不在 envs 里应该怎么处理？
5. 密钥应该放在哪？

## 附：自测答案

1. 空串会让请求带一个无效值，错误在更远的地方爆发，排查成本高；早失败能定位到配置。
2. 展开只做一次，避免多处重复实现与遗漏；也让 Config 拿到的是可直接使用的最终值。
3. 按值匹配会把恰好等于密钥的普通字段也打码，且无法发现新增的敏感字段；按键名是白名单式规则。
4. 启动即报错，不允许「有一个默认环境但不存在」的模糊状态。
5. 环境变量或密钥管理服务；yaml 里只写占位符。

## 学生常问

Q：多环境要复制几份 yaml 吗？

A：不要。一份 yaml 里 envs 分段即可；公共参数放 settings，环境只覆盖差异。

Q：本地开发也要配密钥吗？

A：本地用 .env 注入同名变量，.env 进 .gitignore；CI 里用平台密钥变量。

## 面试题

Q：配置中心与本地 yaml 怎么分工？

A：本地 yaml 管结构（有哪些配置项），配置中心管值（不同环境不同值）。结构变更走代码评审，值变更走配置中心发布。

Q：配置错误怎么快速定位？

A：启动时校验并打印「环境 + 缺失项」，不打印值；启动即失败，而不是运行到一半才失败。

## 延伸知识

- 默认值写法 `${VAR:-dev}` 能省本地配置，但本章的 `expand` 只认 `${VAR}`，还没实现默认值语法，会原样保留字面量；要用得先改正则。
- 配置快照要落盘，复现问题时能确认「当时用的是哪份配置」。
- mask() 递归处理列表与嵌套字典，避免数组里的密钥漏掉。
