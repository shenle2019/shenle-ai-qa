# 第 47 章 · AI 应用功能测试：把 Prompt 当接口

AI 应用的「接口」不是 URL 加 JSON Schema，而是一段自然语言 Prompt；测它，就是测这份没有固定 schema 的契约在各种输入下还成不成立。

## 1. Prompt 是接口，但没有固定 schema

传统接口的契约写在文档里：参数名、类型、必填项、返回码。Prompt 的契约写在模型行为里：同样的意图可以有一百种说法，返回的也是自然语言。测试目标因此从「字段对不对」变成「在一组表达下，意图命中率够不够、边界守不守得住」。

| 维度 | HTTP 接口 | Prompt 接口 |
| --- | --- | --- |
| 入参 | 名称、类型、枚举值固定 | 自然语言，同义改写都合法 |
| 出参 | JSON Schema 可校验 | 文本，只能做包含/结构/语义断言 |
| 错误 | 4xx/5xx 有明确语义 | 可能不报错，只给一个跑偏的答案 |
| 版本 | URL 或 header 带版本号 | Prompt 文本本身就是版本 |

所以功能用例要写成「输入 + 可判定的期望」，期望优先用**必须出现的字段/关键词/格式**，不要写「回答合理」。本章的 `Case(name, prompt, expect, kind)` 就是这个最小结构（`labs/ch47-prompt-cases/ch47_cases.py:21-28`）。

## 2. 参数全景：能调的都要能测

Prompt 的行为不只由文字决定，下面七个参数任何一个变了，输出都可能变：

| 参数 | 控制什么 | 至少测什么 |
| --- | --- | --- |
| system | 角色、边界、拒答规则 | 被用户输入覆盖时是否还守得住 |
| user | 本次任务与数据 | 空、超长、乱码、注入 |
| temperature | 随机性，低温严谨、高温发散 | 0 / 0.7 / 1.0 三档的稳定性与跑偏率 |
| top_p | 核采样范围 | 与 temperature 组合时的边界 |
| max_tokens | 输出上限 | 截断后是否给 `finish_reason=length` |
| history | 模型能看到的对话历史 | 轮次增加后是否串台、是否遗忘 |
| response_format | 结构化输出 | JSON 能否解析、缺字段时是否报错 |

注意本章的 `FakeLLM` 没有 temperature 字段，它用 `jitter` 模拟随机性：`jitter=0` 完全确定，`jitter=0.6` 时有 60% 概率换一个候选答案（`labs/_shared/llm_sim.py:86-92`）。`jitter` 不是 `temperature`，只能演示「不确定性怎么测」，不能拿来标定线上温度。

## 3. 上下文窗口与三种截断策略

上下文窗口是 Token 上限，不是字符上限。本章的假模型按「单字 + 标点」切 Token，所以一段 64 Token 的输入塞进 `context_limit=20` 就会溢出。三种策略的差别不在「有没有截断」，而在「怎么失败」：

```python
long_prompt = "把" + "退款" * 30 + "处理掉"   # 64 token
for policy in ("truncate_head", "silent", "error"):
    m = FakeLLM(context_limit=20, overflow_policy=policy)
    reply = m.answer(long_prompt)
```

实跑结果：

```
truncate_head: truncated=True 前 12 字=关于退款：可以退款。
silent: truncated=True 前 12 字=关于退款：可以退款。
error: 抛错 上下文溢出：64 > 20
```

前两种都返回了文本，光看回答看不出区别；区别在保留的是哪一端。`truncate_head` 留开头，`silent` 留结尾（名字和实现不要凭字面猜，以 `fit_context` 为准，`labs/_shared/llm_sim.py:71-83`）。测试必须断言 `truncated` 字段，并用带「头部标记 / 尾部标记」的输入验证保留方向（`test_ch47_prompt.py:43-53`）。`error` 策略最安全：调用方立刻知道失败，而不是拿到一个被悄悄改过的 Prompt。

## 4. 多轮一致性与记忆窗口

多轮不是「把历史全塞回去」这么简单，至少要验证三件事：指代能不能消解、主题能不能保持、记忆窗口满了以后先丢谁。`multiround()` 每轮把 `问题->答案` 拼回 Prompt，`memory_turns` 控制保留几轮：

```python
llm = FakeLLM(memory_turns=1)
multiround(llm, ["查一下订单", "那退款呢", "再查一次订单"])
len(llm.history())   # 1，最早的订单轮已被挤掉
```

窗口越小，越容易出现「你刚才说的那个订单」答不上来。用例要专门造**跨轮指代**：第一轮给订单号，第三轮只问「它到哪了」，看回答里有没有那个订单号。只测单轮，永远测不出记忆窗口的边界。

## 5. 角色错乱

角色错乱有三种典型形态：忘了人设（客服突然自称通用助手）、人称混乱（把「您」说成「我」）、多轮后逐渐漂移。检测方法很朴素：每轮回答都必须带人设关键词，缺一次就算漂移。

```python
for t in turns:
    text = llm.answer(f"你是{persona}。{t}").text
    if persona not in text and "客服" not in text:
        return True   # 任一轮缺人设关键词即判漂移
```

假模型不会自称客服，所以 `persona_drift(FakeLLM(), "客服", ["我想退款"])` 实跑返回 `True`。这证明**检测器能发现漂移**，不代表线上一定漂移；换成真模型后，这条用例的期望要改成「回答里出现客服话术或工单编号」，而不是硬编码某个词。

## 6. 空、异常、超长输入

异常输入的目标不是「不崩」就完事，而是「崩得可控、提示得有用」。四类必测：

| 输入 | 观察点 | 合格表现 |
| --- | --- | --- |
| 空字符串 | 是否抛异常、是否计 Token | 返回引导语，`used_prompt_tokens=0` |
| 纯符号 / emoji | 解析是否报错 | 识别为无效输入并请用户补充 |
| 无意义字符串 | 是否硬答 | 追问意图，而不是编一个答案 |
| 超长文本 | 截断策略、延迟 | `truncated=True` 且有明确提示 |

空输入在 `FakeLLM` 里返回「我理解你的问题是：」，Token 计数为 0（`test_ch47_prompt.py:29-33`）。这个断言比「不报错」强：它同时锁住了「有回复」和「没把空串算成 Token」两件事。

## 7. 注入基础与功能测试 checklist

注入的本质是让模型把「数据」当成「指令」。直接注入写在用户输入里（「忽略以上指令」），间接注入藏在模型要读的文档、网页、图片元数据里。本章的护栏只是关键词子串匹配：

```
注入识别: True
PII 打码: 联系 138****8000 或 s***@example.com
```

`looks_like_injection()` 命中七个固定短语（`labs/_shared/llm_sim.py:154-167`），「忽略 以上」中间加一个空格就不命中——所以注入用例必须同时测**已知模式**和**变形绕过**，不能把 `True` 当成「防住了」。

功能测试 checklist（每条都要能判定）：

| 检查项 | 判定标准 |
| --- | --- |
| 意图覆盖 | 每个功能点至少 1 条用例，`coverage` 计数不为 0 |
| 参数边界 | temperature 三档、max_tokens 截断各 1 条 |
| 上下文 | 窗口边界 ±1 Token，三种策略各 1 条 |
| 多轮 | 跨轮指代、记忆窗口溢出各 1 条 |
| 角色 | 连续 5 轮人设关键词命中 |
| 异常 | 空、符号、乱码、超长各 1 条 |
| 安全 | 直接注入、间接注入、PII 各 1 条 |
| 输出 | 格式可解析、必填字段齐全、长度在范围内 |

`coverage()` 实跑给出 `{'退款': 2, '订单': 1, '优惠券': 0}`：优惠券功能一条用例都没有，这就是覆盖率缺口，不是「通过率 100%」。

## 自测

1. 为什么 Prompt 不能像 HTTP 接口那样用固定 schema 断言？
2. `context_limit=20`、输入 64 Token，三种策略各是什么表现？
3. `truncate_head` 和 `silent` 都返回 `truncated=True`，测试怎么区分它们？
4. `memory_turns=1` 跑完三轮后 `history()` 有几条？为什么？
5. `coverage` 里「优惠券」计数为 0 说明什么？

## 附：自测答案

1. 因为入参是自然语言，同义表达都合法，出参也没有固定字段；只能断言「必须包含的信息 / 结构 / 语义」，再把多种表达组成用例集看通过率。
2. `truncate_head` 保留开头 20 Token 并置 `truncated=True`；`silent` 保留结尾 20 Token、同样置 `truncated=True` 但不报错；`error` 直接抛 `上下文溢出：64 > 20`。
3. 用带「头部标记…尾部标记」的输入，断言前者 `startswith("头部标记")`、后者 `endswith("尾部标记")`，再断言两者文本不相等；只看 `truncated` 分不出来。
4. 1 条。`memory_turns=1` 每次只保留最后一轮，第三轮写入后前两轮都被挤掉。
5. 说明「优惠券」这个功能点没有任何用例覆盖，是覆盖缺口；通过率高只代表已测的部分没问题，不代表功能测全了。

## 学生常问

**Q：同一条用例跑三次结果不一样，怎么判？**

A：先固定 seed 复现（`FakeLLM(jitter=0)`），确认是模型随机性还是会话状态污染；再对同一输入跑 5–10 次算稳定率，低于约定阈值（例如 0.8）就判不稳定，而不是拿某一次的输出当结论。

**Q：temperature 设 0 就完全确定了吗？**

A：本章只能证明模拟器里 `jitter=0` 时稳定率 1.0。线上温度 0 仍可能因批次调度、模型版本、并发顺序产生抖动——经验判断，未验证；前提是同一模型版本、同一参数、同一会话状态。

**Q：注入测试跑几条「忽略以上指令」就够了吗？**

A：不够。至少覆盖直接注入、间接注入（文档/网页里埋指令）、角色扮演诱导、加空格或编码的变形。本章护栏是关键词子串匹配，变形样本正好用来证明它会漏。

## 面试题

**Q：让你负责一个 AI 客服的功能测试，你从哪几块拆？**

A：六块：意图覆盖（每个业务功能至少一条）、参数（温度/长度/格式）、上下文（窗口边界与截断）、多轮（指代、记忆窗口、角色）、异常输入（空/符号/乱码/超长）、安全（注入与 PII）。每块都给可判定标准，最后用覆盖率表检查缺口。

**Q：Prompt 改了一版，怎么证明没把老功能改坏？**

A：维护一组固定输入和期望的基准用例，改前跑一遍存基线，改后跑同一组做 diff；把「变坏 / 修好 / 稳定通过」分开统计，变坏的必须逐条解释。只看总通过率会掩盖「一条坏一条好」的互换。

**Q：一个用例失败了，你怎么判断是模型问题还是用例问题？**

A：固定 seed 重跑排除随机性；换一种同义表达看是否仍失败；检查 `used_prompt_tokens` 和 `truncated` 排除输入被截断；最后对比基线版本。四步走完还失败，才归到模型或 Prompt。

## 延伸知识

- 间接注入把指令藏在模型要读的文档或网页里，比直接写在输入框里更难防（语料题目 38）。
- 上下文溢出还有「静默忽略新输入」这种形态，现象是答非所问而不是报错，测试要单独造「只问最新一句」的用例（语料题目 18）。
- FIFO 截断先丢最早的历史，长会话里最先崩的往往是系统人设和最初约束（语料题目 19）。
- 假模型的 `jitter` 只改候选答案、不改 Token 数，所以「稳定性」和「输出长度」要分成两条断言，不能用一个指标代替（`labs/_shared/llm_sim.py:86-92`）。
