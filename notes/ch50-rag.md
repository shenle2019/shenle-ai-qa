# 第 50 章 · RAG：检索层和生成层分别怎么测

RAG 答错时人第一反应是换大模型，但坏掉的多半是检索层。这一章把链路拆成五段，每段一条能断言的判据——**检索层测「有没有找到」，生成层测「有没有用找到的东西」**。

## 1. 一条链路，五个可测点

| 环节 | 输入 → 输出 | 典型失败 | 判据 |
| --- | --- | --- | --- |
| 分块 | 文档 → chunk | 答案被切在块缝里 | 相邻块首尾重叠 |
| 嵌入 | chunk → 向量 | 同义不同词匹配不上 | 同义改写命中同一 doc |
| 检索 | query → topK | 阈值高低各错一边 | 召回随阈值单调不升 |
| 重排 | 候选 → 候选 | 把好结果挤出去 | 前后条数一致 |
| 生成 | 候选 → 答案+引用 | 没命中还硬编 | 无命中 `grounded=False` |

`labs/_shared/rag_sim.py` 里五个函数一一对应：`chunk_text`（52 行）、`embed`/`cosine`（25–37 行）、`VectorStore.search`（84 行）、`rerank`（146 行）、`answer_with_citations`（157 行）。语料题目 75 把检索层目标概括成召回、精确、效率、鲁棒——本章断言全落在这四条上，没有一条在测「模型聪不聪明」。

## 2. 分块：先定 size，再用 overlap 补边界

```python
def chunk_text(text, size=120, overlap=20):
    if size <= overlap:
        raise ValueError("overlap 必须小于 size")
    ...
    start += size - overlap        # 步长 = size - overlap
```

`rag_sim.py:52-67`。100 字文本、`size=20`、`overlap=5`，步长 15，起点 0/15/…/90：

```text
块数: 7 首块: 一二三四五六七八九十一二 尾块: 一二三四五六七八九十
```

首块完整 20 字，尾块只有 10 字——`:61-65` 的循环不做尾部合并，最后一块永远偏短；要每块都够长就得在收尾时并进前一块，本仓库没做。overlap 的唯一作用是「答案横跨切点时两块都拿到一部分」，`test_chunk_overlap_keeps_boundary_text` 断言 `parts[0][-4:] == parts[1][:4]`。`size <= overlap` 直接抛 `ValueError`，测试断言消息含 `overlap`（`test_ch50_rag.py:26-32`）——**参数校验的报错文案也是契约**。

## 3. 阈值：唯一必须用真实语料标定的参数

```text
threshold=0.0: recall=1.0     threshold=0.3: recall=0.75
threshold=0.15: recall=1.0    threshold=0.5: recall=0.25
```

方向与题目 76 一致：阈值高则精确率高、召回低。0.0 与 0.15 都是 1.0，这一段**信息量为零**（期望文档本来就排第一）；有区分度的只有 0.3 到 0.5。更难的是负样本——同一个库、阈值 0.3，问一句库里根本没有的问题：

```text
无关问题 top3: [(0.38, 'policy'), (0.252, 'shipping'), (0.153, 'invoice')]
阈值 0.3 时仍会命中 -> ['policy#0']
阈值 0.7 时才拒答 -> {'answer': '知识库里没有相关资料。', 'citations': [], 'grounded': False}
```

0.38 大于 0.3，所以「今天天气怎么样」会拿到一条退款政策当答案。**这就是阈值必须用真实语料标定的原因**：0.3 在别人的语料上可能刚好，在你的语料上就是答非所问。做法是拿一批「库里确实没有」的问题跑一遍，取最高分上沿再加余量；本仓库只有 1 条负样本、最高 0.38，所以拒答用例用的是 0.9（`test_no_hit_stays_ungrounded`）。

## 4. TopK：召回上去了，噪声和成本也上去了

```text
top_k=1: recall=1.0    top_k=2: recall=1.0    top_k=3: recall=1.0
```

三档一样，**不能得出「TopK 不影响召回」**。原因在语料：3 篇文档、每篇不足 60 字（47/41/36），各成 1 块，全库只有 3 块，期望文档在 top1 就已命中，调大没有可捞的东西。要真测 TopK，语料得让「一个问题的答案分散在多块」：把退款政策拆成条件、时限、例外三块，问「生鲜退款要几天」，必须三块都拿到才算完整召回——这时 TopK 从 1 提到 3 才会出现差别。题目 77 的取舍是 K 大覆盖多但噪声与成本高、K 小快但易漏；测的时候同时记召回、生成质量、耗时三个数，只记召回一定得出「越大越好」。

## 5. 三种检索：三组分数不能直接比大小

同一个 query「生鲜类商品退款」：

```text
向量: [(0.648, 'policy', 0), (0.273, 'shipping', 0), (0.203, 'invoice', 0)]
关键词: [(13.933, 'policy', 0)]
混合: [(1.0, 'policy', 0), (0.211, 'shipping', 0), (0.157, 'invoice', 0)]
```

两个量纲不能比：余弦落在 `[-1, 1]`，BM25 无上界，13.933 不代表比 0.648 相关 20 倍。关键词召回天然少，因为 `bm25_search` 只给命中过 query 词的块打分（`rag_sim.py:113` 的 `if score > 0`），没命中的块根本不出现。混合的 1.0 是「0.5×归一化向量 + 0.5×归一化关键词」（`rag_sim.py:119-143`，`alpha=0.5`），policy 两项都第一，正好 1.0——混合的价值不是分数高，是「向量漏掉的关键词精确匹配能被捞回来」。选型与用例绑在一起：专有名词、订单号、型号用关键词；口语改写用向量；两者都有用混合。测试要给每种检索准备**它擅长的那类 query**，否则测出来的是语料偏向（`test_ch50_rag.py:55-64`）。

## 6. 重排：把「分高但字面不沾」的候选压下去

```text
重排前: [(0.462, 'invoice'), (0.145, 'shipping'), (0.105, 'policy')]
重排后: [(1.319, 'invoice'), (0.288, 'shipping'), (0.105, 'policy')]
```

算法是「原分 + query 与 chunk 的 token 重叠率」（`rag_sim.py:146-154`）。invoice 从 0.462 涨到 1.319，policy 一分没涨——它跟「发票下载」一个字都不重合，那 0.105 纯属哈希空间里的巧合。但这次重排**没有改变顺序**，只把差距拉大：它只证明了「重排不丢结果」（`test_rerank_keeps_same_number_of_hits`），证明不了「重排提升了排序」。后者需要构造「向量 top1 但字面不重合」的样本看它是否掉出 top1——当前用例的空白。

## 7. 生成层：幻觉的判据是「有没有命中」，不是「答案像不像」

```python
if not hits:
    return {"answer": "知识库里没有相关资料。", "citations": [], "grounded": False}
```

`answer_with_citations`（`rag_sim.py:157-167`）只有两条分支：命中就拼引用，不命中就明说查不到。**拒答是返回值，不是文案**——前端可以据此不渲染、不落库、不计入满意度。三步可断言：无命中必须 `grounded=False` 且 `citations=[]`；有命中每条 citation 都是 `doc_id#chunk_id`（`test_hit_is_grounded_with_citations` 断言含 `#`）；citation 指向的 chunk 必须真的还在库里——第三条本仓库只查了格式，**删文档后旧引用仍能通过格式断言**，这是漏测。题目 79 给了三种手段：人工评测准但慢、自动事实核查快但依赖判分模型、检索增强检测能把回答里的事实再拿去检索，定位「哪个事实没来源」。冲突文档方面，`test_conflicting_docs_both_retrieved` 建了 old/new 两篇矛盾的退货政策，断言两篇都能召回——但它只断言「都能召回」，没断言「选了新的」。题目 80 的期望行为（识别冲突、按可信度选、告知用户）本仓库没实现，排序只看分数。

## 8. 更新、删除与降级

删掉 policy 后再问「退款要几天」：

```text
删除块数: 1 剩余命中: [(0.232, 'shipping')]
```

仍有一条 0.232 来自物流文档。**这不是幻觉，是检索变弱**：库里还有「发货」「时效」这些相关词，模型会拿物流文档回答退款问题。所以删除测试只断言「policy 不在结果里」（`test_delete_document_removes_it_from_results`）不够，还要断言「删完之后这个问题应该变成拒答」——后半句没测。题目 81 列的挑战是索引延迟、多层缓存、向量残留、模型记忆，任一层没清用户就还能问出旧答案；可测检查点三个：删完立刻问、隔一个缓存周期再问、用旧文档原句问。降级（题目 82）四级：混合检索 → 关键词 → 缓存 → 纯 LLM。测试靠故障注入，清空 `store.chunks` 或让 `bm25_search` 抛异常，看走哪条分支。本仓库 `answer_with_citations` 没有降级分支，命中为空直接拒答——这算一种安全降级（宁可说不知道），代价是检索层一挂，所有问题都变成「没有相关资料」，用户分不清「库里没有」和「系统坏了」。

## 学生常问

**Q：阈值到底设多少？**

A：没有通用值。拿 20 条以上「库里确实没有」的问题跑一遍，看最高分的分布，阈值取上沿再加 0.05~0.1 余量。本仓库负样本最高 0.38，任何低于 0.4 的阈值都会答非所问。

**Q：为什么不用大模型打分替代 BM25？**

A：成本和延迟。每次检索都调模型，QPS 和账单都扛不住。本仓库用「中文 2-gram + 固定哈希」做嵌入（`rag_sim.py:16-33`），不依赖模型和网络，同一文本永远同一向量——这是为了让阈值和召回能在测试里精确断言，不代表线上该这么干。

**Q：分块大小怎么定？**

A：先量语料里「一个答案有多长」，块要装得下最短的完整答案再留上下文。常见起点是 120~300 字一块、20% 重叠（经验判断，未验证；前提是语料为客服问答这类短答案，长文档要按标题层级切）。定完必须回测：把答案跨块的用例挑出来看召回有没有掉。

**Q：`grounded=False` 之后前端怎么显示？**

A：不要只显示「没有相关资料」。用户能接受查不到，但不能接受「查不到」和「系统坏了」长得一样。至少区分三种：无命中、检索超时、引用失效（引用的 chunk 已被删）。本仓库只实现了第一种。

## 面试题

**Q：RAG 答错了，怎么判断是检索的问题还是生成的问题？**

A：固定 query，把 topK 的块打出来人工看。块里有能回答的内容 → 生成层（没按要求引用、或答歪了）；块里没有 → 检索层（阈值、TopK、分块、嵌入）。本仓库把这一步固化成返回值：`grounded` 由「有没有命中」决定，不经过模型，所以能当唯一判据。

**Q：阈值和 TopK 要一起调，实验怎么设计？**

A：二维网格，阈值取 0/0.15/0.3/0.5/0.7、TopK 取 1/3/5/10，每格记召回、拒答率、平均引用数、耗时。选点时先满足拒答率（负样本不能被答），再在剩下的格子里挑召回最高的。只调一个参数，一定会把另一个的副作用记到它头上。

**Q：知识库更新后，回归要跑哪些用例？**

A：三类。新增：新文档能被召回、引用指向新 doc_id；修改：老答案不再出现、新答案答得对；删除：该问题变成拒答、旧引用全部失效。外加不常写的一条——**更新后负样本仍然拒答**，新增文档最容易把无关问题的分数抬过阈值（题目 81）。混合检索的权重则应扫 0/0.25/0.5/0.75/1 五档、按 query 类型分层看召回，本仓库默认 0.5（`rag_sim.py:124`）。

## 延伸知识

- BM25 的两个参数 `k1=1.5`、`b=0.75` 是本仓库取值（`rag_sim.py:92`），`b` 控制长文档是否占优。测试没锁这两个值，换个默认值召回就会变，所以对比实验要连参数一起记录。
- 题目 81 提到「向量残留与模型记忆导致信息无法彻底清除」：删索引只删了当前库，缓存里的旧答案、上下文里的旧 chunk 都还在。删除用例要覆盖「删完立刻问」和「隔一个缓存周期再问」两次。
- 关键词检索的解释性优势（题目 78）在排查时很值钱：BM25 能指出命中了哪个词，向量分不能。线上出现「为什么召回这条」时，前者能定位，后者只能重跑。
- 归一化是混合检索的前置条件（`rag_sim.py:129-140`）：不做归一化，BM25 的 13.9 会把余弦的 0.6 完全压掉，混合退化成纯关键词，而排序看起来「很正常」——这类 bug 只有把两种分单独打出来才看得见。
