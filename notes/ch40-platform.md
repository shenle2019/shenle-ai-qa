# 第 40 章 · 平台架构与最小可用

测试平台和测试脚本的区别，不在于功能多少，而在于**它得能长期被人改**。这一章先立骨架：路由层、仓储层、服务层，三层各管一件事；骨架立对了，后面加接口管理、用例、计划都只是往里加表。

## 1. 三层与一条判据

| 层 | 只做 | 不做 |
| --- | --- | --- |
| 路由层（`miniweb.py`） | 解析方法/路径/参数，找到 handler | 业务判断、SQL |
| 仓储层（`ProjectRepo`） | SQL 与事务 | HTTP 状态码、JSON |
| 服务层（`build_app`） | 参数校验、异常→状态码 | 直接写 SQL |

判据只有一条：**换掉框架或换掉存储，另一层不用改**。本章的 `test_repo_is_framework_agnostic` 就在验证这一点——仓储可以脱离 HTTP 单独跑、单独落盘。

## 2. 为什么自己写一个迷你 Web 层

不是造轮子，是为了让「框架」变成可以替换的适配层。`miniweb.App` 的用法和 FastAPI 一致：

```python
app = App()

@app.get("/projects")
def list_projects(req):
    return json_response({"items": repo.list()})
```

换成 FastAPI 时，把 `Request/Response` 换成框架的对象、把 `app.handle` 换成 `TestClient`，业务函数几乎原样保留。

## 3. 错误码要有语义

| 情况 | 状态码 | 为什么 |
| --- | --- | --- |
| name 为空 | 400 | 请求本身不合法 |
| name 重复 | 409 | 请求合法，与现有资源冲突 |
| id 不存在 | 404 | 目标资源不存在 |
| 路由不存在 | 404 | 与「资源不存在」区分靠 body 里的 message |

区分 400 与 409 的价值在于：前端能据此决定「提示用户改输入」还是「提示重名」，而不是统一弹「操作失败」。

## 4. 本章实操

`labs/ch40-platform/`：`miniweb.py`（`Request/Response/Route/App`，支持 `{param}` 路径参数）、`projects.py`（`ProjectRepo` + `build_app`，SQLite 内存或落盘）、`test_app.py`（12 条）。

```bash
python -m pytest labs/ch40-platform -q
```

12 条覆盖：健康检查、创建返回 201、空名 400、重名 409、列表有序、取不存在 404、改名成功/重名 409、删除后 404、未知路由 404、仓储脱离 HTTP 可落盘、路径参数与查询参数合并。

## 5. 常见坑

1. **把 SQL 写在 handler 里**：加一个字段要改十几个地方，而且没法单测。
2. **异常直接 500**：`ValueError` 一路冒到框架层，前端只看到「服务器错误」。
3. **状态码全用 200**：靠 body 里的 `code` 区分，HTTP 语义全丢，网关与监控都没法用。
4. **用 `:memory:` 做唯一存储**：进程重启就没了。测试用内存、线上用文件/库，靠参数切换。
5. **路径参数与查询参数同名**：本章选择「查询参数优先」，换框架时要注意签名行为不同。

## 6. 自测

1. 三层里哪一层该负责「重名返回 409」？
2. 为什么仓储层要能脱离 HTTP 单独跑？
3. 400、409、404 分别对应什么情况？
4. 用 `:memory:` 的测试为什么不能替代集成测试？
5. 换成 FastAPI 时，哪一层需要改？

## 附：自测答案

1. 服务层。仓储只抛 `ValueError("项目名已存在")`，由服务层翻译成 409；这样换存储实现时状态码逻辑不变。
2. 一是可单测（不用起 HTTP），二是证明仓储不依赖框架，换框架时它不用动。
3. 400 请求参数不合法；409 与现有资源冲突（重名）；404 目标资源不存在。
4. 内存库不校验落盘、并发、真实约束与迁移，重启即失，无法覆盖真实数据库行为。
5. 只改路由层（`miniweb.py` 与入口的适配），服务层函数签名基本不变，仓储层完全不动。

## 学生常问

Q：为什么不用 Django 一把梭？

A：Django 的 ORM 与路由耦合更深，小平台改起来反而重。分层清晰的小框架更容易讲清「哪一层出问题」。

Q：SQLite 能上生产吗？

A：单机、低并发、读多的内部平台可以；一旦要多实例部署就要换 PostgreSQL，这也是为什么仓储层要独立。

Q：平台第一天就该有权限吗？

A：不需要完整 RBAC，但至少要有「一个 API key 或登录态」，否则内网谁都能删项目。

## 面试题

Q：设计一个测试平台，你怎么分层？

A：接入层（路由/鉴权）、服务层（校验与编排）、领域层（项目/用例/计划）、仓储层（SQL）、执行层（跑用例、发通知）。层间单向依赖，执行层通过接口回调，避免与 Web 层耦合。

Q：接口为什么要有语义化状态码？

A：网关、监控、前端都依赖状态码做判断；全用 200 会让重试、告警、缓存全部失效。

Q：怎么保证平台的改动不破坏已有功能？

A：三件事：服务层纯函数化便于单测；仓储可替换（内存/文件）便于集成测试；每次改动跑全量 `pytest` 并用同一套 HTTP 用例回归。

## 延伸知识

- 表结构变更用「启动时 `CREATE TABLE IF NOT EXISTS` + 增量 ALTER」就够内部平台用，但要记版本号。
- 仓储层方法命名用领域语言（`rename` 而不是 `update_name`），换存储时语义不变。
- 路由参数校验可以抽成装饰器，避免每个 handler 重复写。
- 统一响应体 `{items: [...]}` 比裸数组好扩展（加分页、加 total）。
- 204 响应不能带 body，这个坑在第 40 章就踩一次，后面所有删除接口都照此写。
