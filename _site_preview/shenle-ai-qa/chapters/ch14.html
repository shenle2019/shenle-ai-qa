第 14 章 · 报告与智能断言 ​

用例跑完只有一行 23 passed，对团队没用。这一章解决两件事：结果怎么给人看，断言怎么既严格又不脆。

1. 报告的三层 ​

层给谁看内容
终端摘要写代码的人-q 的点和 F，--tb=short 的栈
JUnit XMLCI / 平台机器可读的用例、耗时、失败原因
HTML团队 / 汇报通过率、耗时分布、失败详情、环境信息

pytest 自带前两层（--junitxml=report.xml），HTML 用插件或自己渲染。本章用 stdlib 写一个 40 行的渲染器，不引依赖也能出报告。

2. JUnit XML 里有什么 ​

xml
<testsuite name="pytest" tests="23" failures="1" errors="0" time="0.57">
  <testcase classname="labs.ch12.test_users" name="test_crud_roundtrip" time="0.05">
    <failure message="期望 200，实际 422">...栈...</failure>
  </testcase>
</testsuite>

渲染时最该突出的是 failures 与 time，不是用例总数。

3. 断言为什么会脆 ​

脆的写法为什么脆改法
assert body == {...} 全等服务端加字段就挂断言子集
assert ts == "2026-11-16"日期一变就挂断言格式/范围
assert id == 1依赖自增断言 isinstance(int) and > 0
assert "成功" in text文案改字就挂断言 code 枚举
只断 200业务错误也 200断状态 + 关键字段

一句话：断言契约，不断言实现。

4. 断言工具箱 ​

python
def assert_subset(actual, expected, path=""): ...      # 只要求包含这些键
def assert_schema(obj, schema): ...                    # 类型与必填
def assert_iso8601(value): ...                         # 时间格式而非具体值
def assert_in_range(value, low, high): ...            # 数值范围
def soft_assert(collector, cond, msg): ...             # 收集多条失败，一次报完

soft_assert 的价值：一个响应体有 5 个字段要验，硬断言只能看到第一个失败，软断言能一次列全。

5. 「智能断言」到底是什么 ​

不是让模型随口说「看起来对」，而是三步：

  1. 规则先生成候选：从响应体里抽出字段、类型、枚举，生成「可判定」的断言草稿；
  2. 人审：把 status: paid 这类业务语义补进断言，去掉 elapsed < 3ms 这种环境相关的；
  3. 回归固化：审过的断言写回测试文件，之后不再让模型介入。

模型擅长的是「从一份响应里看出该断言哪些字段」，不擅长「知道这个业务的正确值」。

6. 本章实操 ​

labs/ch14-report-assert/：

  • assertkit.py：assert_subset / assert_schema / assert_iso8601 / assert_in_range / SoftAssert / suggest_assertions（从响应体推断言草稿）；
  • report.py：读 JUnit XML → 生成自包含 HTML（通过率环、失败列表、慢用例 Top 5）；
  • test_assertkit.py：断言工具箱自身的测试（用坏数据证明它会报错）。
powershell

7. 自测 ​

  1. 为什么「全等断言」在接口测试里几乎总是错的？
  2. soft_assert 适合什么场景？什么时候反而该用硬断言立即中断？
  3. JUnit XML 里哪两个字段最能反映质量趋势？
  4. 「智能断言」的三步里，哪一步不能交给模型？
  5. 一个 elapsed_ms < 50 的断言，为什么在 CI 上会随机失败？

附：自测答案 ​

  1. 响应里几乎总有时间戳、自增 id、随机串、字段顺序，全等断言必然失败；而且字段一多，任何无关的新增字段都会让用例红。正确做法是断言关键字段与结构。
  2. 软断言适合一次收集多个字段的错误（表单校验、多个必填项），让报告一次给出全部问题；硬断言适合前置条件（登录失败、服务没起），继续跑没有意义还浪费时间和日志。
  3. tests 和 failures（含 errors），再叠加耗时。趋势看失败率变化和耗时漂移，单次结果只看通过数没意义。
  4. 第三步「下结论 / 归因」不能交给模型——它只能基于证据给候选原因，最终判断必须人来做，否则会把「断言写错」误判成「服务端 bug」。
  5. CI 机器有噪声：容器冷启动、GC、并发争抢、时钟精度，50ms 这种绝对阈值必然抖动。改成相对阈值（相对基线倍数）或看分位数，并留出裕量。

学生常问 ​

Q：报告里最该看什么？

A：先看失败的用例名和断言消息（是否可判定），再看失败分布（集中在哪个接口/哪个维度），最后看耗时趋势。通过率是结论，不是线索。

Q：JUnit XML 和 Allure 怎么选？

A：JUnit XML 是通用格式，Jenkins/GitLab 原生认，够用；Allure 好在步骤树、附件（请求/响应/截图）、历史趋势，团队要看「为什么失败」时值得上。

Q：软断言会不会掩盖严重问题？

A：会，如果全部用软断言，前置失败后后面还在跑，日志会很长。规则：前置用硬断言，字段校验用软断言，最后统一汇总。

面试题 ​

Q：接口断言你分几层？

A：协议层（状态码、Content-Type、响应时间）、结构层（字段存在、类型、数组长度）、业务层（关键字段值、状态流转）、数据层（落库/查询接口一致性）。层数按风险加，不是越多越好。

Q：「智能断言」你怎么落地？

A：三步：采集失败上下文（请求、响应、断言、历史同类结果）→ 与契约比对找出差异（字段缺失、类型变化、值越界）→ 给出候选归因与修复建议，人工确认。模型只做前两步的加速，不做最终判断。

Q：CI 上的偶发失败怎么治理？

A：先分类：环境（连接超时、端口未就绪）、数据（唯一性冲突、清理失败）、时序（异步未完成）、真 bug。分别用重试、等待策略、数据隔离解决；给用例打 flaky 标记并限期修复，不要长期靠重试掩盖。

延伸知识 ​

  • 断言消息里带「期望 / 实际 / 上下文」三样，失败时不用重跑就能判断。
  • 报告里保留请求和响应片段（截断 500 字符），排查效率提升最明显。
  • 给用例加 --junitxml=report.xml，CI 直接出趋势图，不用额外服务。
  • 通过率要按「接口 / 维度」拆开看，整体 95% 可能掩盖某个接口 0%。
