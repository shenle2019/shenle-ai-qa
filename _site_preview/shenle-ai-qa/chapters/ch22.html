第 22 章 · 用 AI 生成 Web 用例（生成 → 校验 → 真跑） ​

本章目标：把「让模型写用例」做成一条能落地的流水线，而不是复制一段 prompt 试运气。做完你能说清为什么中间必须有校验层。

1. 三步，一步都不能少 ​

页面快照  →  模型生成  →  结构校验  →  真跑  →  报告
步骤不做会怎样
快照模型靠猜元素名，生成一堆 #submit-btn 这种不存在的定位
校验语法错、动作乱写、编造 testid，直接进执行器炸在奇怪的地方
真跑校验通过但页面行为不符，问题留到上线

2. 快照：只给模型该看的 ​

python
{
  "url": "http://127.0.0.1:8000/login",
  "title": "登录",
  "headings": ["登录"],
  "controls": [
    {"tag": "input", "testid": "username", "name": "", "type": "text"},
    {"tag": "button", "testid": "login-submit", "name": "登录", "type": ""}
  ],
  "text": "用户名 密码 登录 ..."
}

不要把整页 HTML 丢进去：太长、噪声大、还容易让它照着 DOM 结构编造选择器。给控件清单 + 正文摘要，模型就能写出「人话版」的步骤。

3. 提示词的四段结构 ​

段落内容少了会怎样
角色你是 Web 自动化工程师模型开始写测试策略散文
输入上面那份快照它开始编元素
任务一句目标 + 覆盖成功与失败只给正常流，或给 10 条重复的
输出契约JSON schema + 硬约束收到一段「综上所述」

硬约束里最有用的一条：只能使用快照里出现过的 data-testid。这一条把「编造」从「常见」压到「偶发」。

4. 校验：宽松解析，严格校验 ​

python
data = extract_json(reply)              # 容忍 ```json 围栏、前后客套话
cases = validate_cases(reply, snap)     # 动作白名单 + 字段必填 + testid 存在

两条规则值得单独说：

  • 操作类动作（fill/click）要求 testid 在快照里出现过——编造的元素点不到；
  • 断言类动作（expect_*）允许指向「操作之后才出现的元素」——否则「密码错误后出现提示条」这种用例全被判非法。

这就是校验层的价值：它知道哪些约束是硬约束，哪些是「看起来严格但会误杀」。

6. 生成质量的验收标准 ​

  • 可执行：每个 testid 都能在页面里找到；
  • 可判定：断言是「某元素包含某文本」，不是「验证功能正常」；
  • 不重复：两条用例不是同一个断言换了个标题；
  • 覆盖到失败路径：至少一条异常输入/未登录/边界。

7. 自测 ​

  1. 为什么不能把整页 HTML 丢给模型？
  2. 校验层为什么对 fill/click 和 expect 用不同规则？
  3. 模型返回 ```json 围栏时该怎么办？
  4. 生成 20 条用例，只有 12 条能跑，说明什么？

附：自测答案 ​

  1. 三个原因：太长（超上下文、烧钱）、噪声多（脚本、样式会干扰）、诱导编造（模型会照着 DOM 结构生成看起来合理但页面里没有的选择器）。
  2. fill/click 作用在「当前页面上存在的元素」，编造就一定失败，属于可静态判断的错误；expect 常指向「操作后才出现的元素」（错误提示、toast），强制要求存在会把正确用例判错。
  3. 解析时剥掉围栏（正则取 ```json 块），并允许前后有客套话。模型加围栏是常态，为此报错等于自找麻烦。
  4. 说明约束不够或提示词缺信息：常见是没给控件清单、没限制动作白名单、或页面本身没有 testid。先看 8 条失败的原因分布，再决定补快照还是补约束。

学生常问 ​

Q：生成的用例要不要人工评审？

A：要，但评审方式变了：人不再逐条写，而是「看 diff + 跑一遍 + 抽查断言」。把「写得对不对」交给执行器，「覆盖够不够」留给人的判断。

Q：没有 testid 的老项目怎么办？

A：先补关键路径的 testid（成本低于长期维护 XPath）；补不了就用 role + name 定位，并在提示词里允许 role/label 两种方式——但要在校验里限制「只能选快照中出现过的可访问名」。

Q：怎么防止模型每次都生成一样的用例？

A：在提示词里给「已覆盖清单」，要求它补充未覆盖的维度（边界、异常、权限）。或者按维度分批提问：这一轮只要「权限相关」。

面试题 ​

Q：AI 生成用例，你怎么保证质量？

A：三道闸：结构校验（动作白名单、字段必填、testid 必须存在）、可执行校验（真跑一遍，失败率作为质量指标）、覆盖校验（对照维度矩阵看缺口）。只有第一道等于没验证，模型完全可能生成语法正确但跑不通的用例。

Q：AI 在 Web 自动化里真正擅长什么？

A：擅长把「页面结构」翻译成「操作步骤」，以及批量生成同一模式的变体（不同输入、不同角色）。不擅长判断「这个业务规则对不对」——那需要领域知识，模型只能猜。

Q：生成式用例会不会让用例数量爆炸、维护不动？

A：会，如果没有去重和分级。做法：生成时要求「与已有用例不重复」、按 smoke/regression 分级、定期清理长期不失败的生成用例。数量不是目标，覆盖才是。

Q：怎么评估这套流水线的收益？

A：三个数：生成到可执行的通过率、单条用例的人工耗时、以及「生成用例发现的真实缺陷数」。只看前两个会自欺——生成一堆跑得过但没价值的用例，指标很好看。

延伸知识 ​

  • 让模型输出「步骤」而不是「代码」：步骤能被校验、能被别的执行器复用；直接生成 Python 代码就只能跑，出错了很难定位是「生成错」还是「执行错」。
  • response_format={"type": "json_object"}：DeepSeek 与 OpenAI 都支持，能把「返回一段话」的概率压到很低，但仍要容错解析。
  • 提示词里给反例：附一条「错误示范」（用了不存在的 testid），比只说「不要编造」有效。
  • 成本控制：快照压到 1–2KB、只传控件清单、批量生成时复用同一次请求，单条用例成本能压到分币级。
