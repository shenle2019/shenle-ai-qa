第 8 章 · 接口与接口测试基础 ​

接口测试不是「把请求发出去看有没有 200」。它测的是一份契约：调用方按约定发什么，服务端就必须按约定回什么，出错时也要按约定报错。

这一章先把契约拆开看清楚，后面的 AI 生成用例、封装、报告都建立在这上面。

1. 一份接口契约包含什么 ​

要素说明测试时关心什么
方法与路径POST /api/users路径参数拼错、方法不支持（405）
参数位置query / path / header / body / form / cookie放错位置服务端收不到
参数约束必填、类型、长度、范围、枚举缺失、越界、类型错（422）
鉴权Bearer / Cookie / 签名无 token、过期 token、越权（401 / 403）
成功响应状态码 + 结构 + 字段类型结构变了前端就崩
失败响应状态码 + 错误码 + message报错要说清是哪一项错了
副作用创建、扣款、发消息重复提交会不会重复扣（幂等）

一份能测的文档，至少要有上表全部内容。缺哪一项，就在用例里标「待澄清」——这和需求分析时的「待澄清项」是同一件事。

2. 一次请求长什么样 ​

POST /api/orders HTTP/1.1
Host: 127.0.0.1:8010
Authorization: Bearer 2f9c...
Content-Type: application/json
Idempotency-Key: order-20261116-001

{"items":[{"sku":"A-1","qty":2}]}

响应：

HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/orders/1

{"id":1,"user":"alice","amount":20,"status":"created"}

requests 把这些细节都封装了，但测试时必须知道每个字段落在哪——尤其是 Authorization、Content-Type、Idempotency-Key 这类决定行为的头。

3. 方法与幂等性 ​

方法语义幂等常见误用
GET查询是用 GET 做删除，被浏览器预取
POST创建 / 动作否重复点击生成两笔订单
PUT整体替换是只传部分字段，把其余字段清空
PATCH局部更新通常否并发下互相覆盖
DELETE删除是删除不存在的资源返回 500

「幂等」是可测的：同一个请求发两次，资源数量不应变化。第 13 章会用 Idempotency-Key 专门验它。

4. 状态码：先看分组，再看具体 ​

分组含义测试里怎么用
2xx成功201 要带 Location；204 不能有 body
3xx重定向接口一般不跟随，allow_redirects=False 看真实响应
4xx调用方问题400 参数格式错、401 未认证、403 无权限、404 不存在、409 冲突、422 语义校验失败、429 限流
5xx服务端问题500 未捕获异常、502 上游错、503 过载、504 超时

三个最容易混的：

  • 401 vs 403：401 是「你是谁我不知道」，403 是「知道你是谁，但你不能做」。
  • 400 vs 422：400 通常指报文本身坏了（不是 JSON），422 指报文能解析但字段不合法。
  • 409 vs 422：409 是「和现有状态冲突」（重名、已支付），422 是「这一条数据本身不合法」。

断言时不要只断言 status_code == 200，要断言到「哪个字段、哪种错误」。

5. 参数该放哪 ​

位置适合放例子
query筛选、分页、排序?page=1&size=20
path资源标识/api/users/42
body(JSON)结构化数据{"name":"dave"}
form表单提交、文件上传multipart/form-data
header鉴权、幂等键、追踪号Authorization、Idempotency-Key、X-Request-Id
cookie会话SESSIONID=...

同一个值放错位置，服务端就收不到；这类 bug 在手工测试里极常见，所以用例要覆盖「必填参数缺失」和「参数放错位置」。

6. 鉴权：四种形态与测试点 ​

形态长什么样测试点
BasicAuthorization: Basic base64(user:pass)口令错、未编码
BearerAuthorization: Bearer <token>无 token、过期、签名被改
CookieCookie: SESSIONID=...会话固定、退出后是否失效
签名X-Sign: md5(params+secret)参数改一个字节签名是否失效

本章的 SUT 用 Bearer，token 有 1 小时有效期。写用例时，「无 token 返回 401」和「过期 token 返回 401」要分开测——实现里经常只判了前者。

7. 没有文档怎么办：抓包 ​

  1. 打开开发者工具 → Network → 勾选 Preserve log（防跳转丢失）。
  2. 触发一次操作，找到目标请求（按 URL 关键词过滤）。
  3. 看四处：Request Method + Request URL、Request Headers（尤其 Authorization、Content-Type）、Payload、Response。
  4. 右键 → Copy as cURL，可以直接改成 requests 代码。

Fiddler / Charles 的用处是「浏览器抓不到的请求」（App、HTTPS 双向认证场景）。

8. 接口测试的九个检查维度 ​

拿到一个接口，按这张表过一遍，用例就不会漏：

  1. 正常流：合法参数 → 期望状态码 + 关键字段。
  2. 必填缺失：逐个删必填字段。
  3. 类型/格式：数字传字符串、日期格式错、超长字符串。
  4. 边界：分页 size=0/1/100/101，金额 0 / 0.01 / 上限。
  5. 业务规则：重名、状态机非法流转（已支付再支付）。
  6. 鉴权与越权：无 token、他人资源、低权限角色。
  7. 幂等与并发：重复提交、同一秒两次请求。
  8. 错误信息质量：报错是否指明字段，是否泄漏堆栈。
  9. 兼容与性能：字段新增是否破坏老客户端、P95 延迟。

9. 本章实操 ​

labs/ch08-http-basics/：起一个只用标准库写的 SUT，用 requests 把上面九个维度里的六项真跑一遍。

powershell
.venv\Scripts\python.exe labs\ch08-http-basics\explore_api.py
.venv\Scripts\python.exe -m pytest labs\ch08-http-basics -q

实验里会看到：401、404、409、422 分别长什么样，Location 头怎么用，以及「同一个 POST 发两次」为什么必须靠 Idempotency-Key 才安全。

10. 自测 ​

  1. 401 和 403 的区别是什么？各举一个真实场景。
  2. 为什么 PUT 只传部分字段是危险操作？
  3. 一个创建接口返回 200 而不是 201，算 bug 吗？怎么判断？
  4. 接口返回 {"code":0,"msg":"ok","data":null}，data 为空时前端崩了——这算接口问题还是前端问题？
  5. 用 F12 抓一个带 token 的请求，说明 token 放在哪、怎么拼进 requests。

附：自测答案 ​

  1. 401 是「没认证」：没带 token、token 过期、签名错误；403 是「认证过了但没权限」：普通用户访问管理接口。真实场景：token 过期返回 401，普通账号调 /admin/users 返回 403。
  2. PUT 语义是「整体替换」，只传部分字段意味着其他字段被置空或删除——这是数据丢失级别的操作。只想改一两个字段用 PATCH。
  3. 不一定算 bug，先看契约：按 REST 惯例创建资源应返回 201 并带 Location；如果接口文档就写 200，那按文档断言，但要在评审里提出来，因为这会影响客户端缓存和幂等设计。
  4. 算接口契约问题，前端也有责任。接口应明确「空集合返回 []、无对象返回 null」，并在文档写死；前端不能假设 data 一定有内容。两边都要修，接口先定契约。
  5. token 通常在请求头 Authorization: Bearer <token>。抓包看 Request Headers，复制到代码里：headers = {"Authorization": f"Bearer {token}"}，别把 token 写死在代码里，从登录响应或环境变量取。

学生常问 ​

Q：接口测试要不要连真实数据库校验？

A：看目标。验证「接口返回对不对」只看响应就够；验证「数据真的落库了」要查库或再调一次查询接口。优先用查询接口验证，直连数据库的成本高、还会把测试绑死在表结构上。

Q：200 但业务失败，这种接口怎么测？

A：看响应体里的业务码或状态字段，断言业务码而不是 HTTP 码。这类接口要在用例里明确写「HTTP 200 + code=1001」两个断言，否则只断言 200 会一直绿。

Q：怎么测幂等？

A：同一个幂等键连续提交两次，断言第二次返回 200（不是 201）、且数据库只有一条记录、响应体里的 id 相同。没有幂等键的接口，测「重复提交会被拒绝（409）」。

面试题 ​

Q：一个接口的测试点你会从哪几个维度拆？

A：功能（正常/异常/边界）、参数（必填、类型、长度、枚举、位置）、鉴权（无 token、过期、越权）、状态（重复提交、并发、状态机非法流转）、数据（分页边界、大数据量、特殊字符）、协议（方法、Content-Type、状态码、响应头）、性能与兼容。

Q：HTTP 和 HTTPS 在测试上有什么区别？

A：HTTPS 多了 TLS 握手，测试要关注证书有效性、过期、域名不匹配、协议版本；抓包需要装证书或用代理；接口本身的行为应该和 HTTP 一致，出现差异通常是中间层（网关、WAF）造成的。

Q：为什么说「接口测试比 UI 测试更划算」？

A：接口层没有渲染和等待，执行快、稳定、定位准，一个 bug 在接口层暴露的成本远低于 UI 层；UI 用例只保留关键主流程，其余下沉到接口层。

延伸知识 ​

  • Content-Type 决定服务端怎么解析 body：application/json、application/x-www-form-urlencoded、multipart/form-data 三种最常见，传错就是 415 或参数收不到。
  • 状态码只是约定，真正的契约在文档里：同一个 422，有的项目表示参数错，有的表示业务规则不满足。
  • 分页要测三处：第 1 页、最后一页、越界页（返回空列表而不是报错）。
  • 时间字段统一用 ISO 8601 带时区，跨时区比较才不会错。
