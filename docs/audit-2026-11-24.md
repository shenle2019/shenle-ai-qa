# 2026-11-24 全库事实性排查台账

起因：用户发现 `chapters/ch32` 的「延伸知识」写着

> 压测客户端的 timeout 要小于服务端超时，否则你会把「服务端已返回但客户端已断开」误判成成功。

这句话方向反了、后果也反了。下面是溯源、排查方法与改动记录。

## 1. 溯源：那句话是怎么来的

- 提交 `50b2514`（2026-11-20 09:39，`feat(perf): add chapter 32 on the four core metrics`）把它写进 `notes/ch32-perf-basics.md` 的「延伸知识」。
- 在 `corpus/`（283 篇语料，175 万字）里检索 `客户端` + `超时`，只有两条无关命中。
- **结论：自产的经验句式，不是语料，也不是模型复述某篇文档。**当时为了把「延伸知识」凑满四条，按「听起来对」的直觉补了一句，没做反证。

正确的说法：客户端 `timeout` 要**大于**服务端的处理超时。反过来（客户端先断开），报告只会记一条客户端超时/失败，而请求可能仍在服务端跑完——于是把「服务端已成功」误判成**失败**，重试还会叠出重复数据。

## 2. 排查方法

1. **规则扫描**：`scripts/_audit_claims.py` 抽每章「延伸知识 / 常见坑 / 自测答案 / 学生常问 / 面试题」的句子，按方向词、绝对词、默认值词打标签 —— 全库 **1003 条断言，240 条命中风险词**。
2. **逐条人读**：`scripts/_dump_extra.py` 把 46 章的「延伸知识」全打出来逐条读。
3. **分批深审**：4 个 subagent 分头通读 ch01–15 / ch16–31 / ch32–46 / 站点 kb 与面试题，一律要求「行号 + 原句 + 问题 + 改法」，且只报有把握的、不改文件；Playwright / PyYAML / 正则行为这些能实跑的先实跑再下结论。
4. **改完做反证**：每条改动反问「如果它原来是对的，现象会是什么样」。

## 5. 这次犯错的根因（写进规矩）

1. 「延伸知识」当成凑数栏：为了四条凑满，凭直觉补话。
2. 没有反证习惯：方向词、时间顺序、上下游这类最容易反的句子，写完没反读。
3. 经验值没有前提：把「某次实验的现象」写成「通用规律」。
4. 单一来源：一句话只有我自己写过一遍，没有任何交叉核对。
