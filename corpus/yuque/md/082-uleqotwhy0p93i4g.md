## 数据库的事务机制详解

​

事务机制ACID : ACID 模型是一组数据库设计原则，对于事务型应用程序非常重要。

​

- Atomicity 原子性 : 事务通常由多个语句组成。原子性保证将每个事务视为一个“单元”，该事务要么完全成功，要么完全失败
- Consistency 一致性： 事务的执行不能破坏数据库数据的完整性和一致性，一个事务在执行之前和执行之后，数据库都必须处于一致性状态
- Isolation 隔离性： 通常数据库会有多个事务同时执行，隔离可确保事务的并发执行不会相互干扰。
- Durability 持久性 ： 持久性保证一旦事务被提交，即使在系统故障（例如，停电或崩溃）的情况下，事务也将保持提交状态

​

这个过程中，我们可以执行一个 或者 多个SQL的执行， 我们可以明确它的开始和结束.

- begin 表示开始这个事务
- commit 表示提交这个事务 (事务只有提交了，才会真正写入)
- rollback 表示回滚 ，即 这个事务操作下，哪怕SQL语句执行了，也不会正常写入。

我们可以举一个例子：比如，三丰老师给小明老师转100块钱。

那么正常的操作下，如果我们执行代码的时候报错了，这两个应当一起回滚.这就是事务的相关概念.

## 数据库锁机制

数据库的锁机制.

我们可以开启两个linux的操作客户端，模拟一下多人向数据库写入数据的情况:

用户1： 正在操作，要删除整张表数据

用户2：正在操作，要向数据库插入数据

这个时候，我们会发现，如果用户2先开启的事务，那么当用户1执行的时候，它会被锁住，在用户2提交前，无法正常执行SQL。 这就是Mysql的锁机制。

注意：锁是一个虚拟概念，它为了满足数据的一致性，只会允许一个人去操作。这种就如同把门锁住，不让人进来这样的。大家要注意好这个要点

上述这种情况，就是我们的表锁。

​

锁很明显会出现性能问题，也就意味着，我们需要在测试过程中重点关注这个操作。

​

除了表锁之外，还有行锁!

如果我们同时向小明 修改它的金额，我们会发现，这行数据会被锁住，我们无法继续执行。

1. 表结构设计问题

这个问题通常是开发设计的问题，我们可以适当提出建议，但是一般效果不大好

- 设计表的时候。就要考虑索引
- 表结构可以适当的做一些冗余
- 字段允许适当冗余，以提高查询性能，但必须考虑数据一致。冗余字段应遵循：

- 1）不是频繁修改的字段。
- 2）不是 varchar 超长字段，更不能是 text 字段。
- 正例：商品类目名称使用频率高，字段长度短，名称基本一成不变，可在相关联的表中冗余存
- 储类目名称，避免关联查询。

- 触发器、主外键，高并发下避免使用

触发器： 当我们执行数据操作的时候，触发数据库里面设定好的 存储过程的时候/用户自定义功能的执行

主外键: 当进行数据变更的时候， 数据库会去额外进行主外键检测。

主外键的目的：是为了确保数据的正确性 ，例如：员工表里面的 部门ID字段，和 部门表的ID字段 一一对应，数据的正确 应该交给 应用程序去维护（业务逻辑），而不是交给数据库，因为数据库的性能不高

1. 数据库索引机制

索引是什么：

怎么看索引?

SHOW INDEXES FROM 表名;

- Table：索引所在的表名。
- Non\_unique：索引是否唯一。0 表示唯一索引，1 表示非唯一索引。
- Key\_name：索引的名称。
- Seq\_in\_index：索引中的列序列号，从1开始。
- Column\_name：索引列的名称。
- Collation：列在索引中的排序顺序（A 表示升序，D 表示降序，NULL 表示无分类）。
- Cardinality：索引中不同值的数量估计。
- Sub\_part：如果列只是被部分索引，则为被索引的字符数；如果整列被编入索引，则为 NULL。
- Packed：指示关键字如何被压缩。
- Null：列是否可以包含 NULL 值。
- Index\_type：索引的类型（例如 BTREE、FULLTEXT、HASH、RTREE）。
- Comment：索引的备注信息。

怎么添加索引？

1. 添加主键索引（PRIMARY KEY）

ALTER TABLE 表名 ADD PRIMARY KEY (列名);

1. 添加唯一索引（UNIQUE INDEX）

ALTER TABLE 表名 ADD UNIQUE (列名);

3. 添加普通索引（INDEX）

ALTER TABLE 表名 ADD INDEX 索引名 (列名);

4. 添加全文索引（FULLTEXT INDEX）

ALTER TABLE 表名 ADD FULLTEXT (列名);

5. 添加多列索引（复合索引）

ALTER TABLE 表名 ADD INDEX 索引名 (列名1, 列名2, ...);

**索引的区别和应用场景**

|  |  |  |  |
| --- | --- | --- | --- |
| 索引类型 | 定义 | 特点 | 适用场景 |
| 主键索引 | 用于唯一标识表中的每一行数据 | 不允许重复、不允许为NULL，存储方式为聚簇索引 | 表的主键列 |
| 唯一索引 | 确保索引列中的所有值都是唯一的 | 不允许重复，但允许为NULL，一个表可以有多个唯一索引 | 需要保证某个列的值唯一的情况 |
| 普通索引 | 最基本的索引类型，没有唯一性约束 | 允许重复、允许为NULL，目的是提高查询速度 | 需要加速查询的列，但不需要保证唯一性 |
| 全文索引 | 针对文本类型的数据进行搜索的索引 | 允许对文本内容进行高效的模糊匹配 | 需要在大段文本中搜索关键词的情况 |
| 复合索引 | 包含两个或多个列的索引 | 多列组合，最左前缀原则，提高多列查询性能 | 多条件组合查询，排序和分组操作 |

### 1. ShardingSphere核心架构

Apache ShardingSphere是一套开源的分布式数据库中间件生态圈，包含JDBC/Proxy/Sidecar三形态组件，提供数据分片、分布式事务等能力。类似组件包括MyCat（配置简单）和Vitess（K8s原生）。其设计哲学为Database Plus，旨在构建异构数据库上层的标准和生态。

### 二、jvm中的GC原理与性能瓶颈

什么是自动垃圾收集 GC机制?

Java虚拟机（JVM）的垃圾回收（GC）机制是为了自动管理内存，它能够帮助开发者专注于业务逻辑，而无需手动进行内存分配和回收。

因为系统的内存不是无穷无尽的，每一个请求处理过程中，都会创建一些对象，占用一些内存。请求处理完毕， 占用内存应该被释放。【比如 定义的对象实例，定义的变量这些】 , 所以，这里的做了一个垃圾回收机制。

整个垃圾回收机制的工作就是： 标记、整理、清除垃圾

- 老年代与新生代

在Java虚拟机（JVM）的内存管理中，堆内存被划分为几个不同的区域，其中最常见的是新生代（Young Generation）和老年代（Old Generation）。这两个区域有不同的垃圾回收策略，以适应不同生命周期的对象。

新生代用于存放新创建的对象。大多数对象最初都会被分配在这里，因为它们很可能会在短时间内变得不可达并可以被回收 这里包含3个区域，按比例 8:1:1 分配

新生代 - eden 伊甸园的意思，也就是新创建的这些内容都会生成在这里面。但是如果满了就会被放到老年代中。

新生代-survivor 1 ，新生代-survivor 2 ： 这两个区域一定会有个区域被空置，后续复制的时候会来回复制。

​

老年代:

老年代用于存放长时间存活的对象。这些对象在多次新生代垃圾回收后仍然存活，因此被认为有更长的生命周期。

​

GC的回收机制，是一种复制，格式化的回收方式,它采用的方式就是从新生代复制还没有结束的数据，然后放入survivor中，剩下的直接格式化处理。

而如果一旦这里出现了多次GC后，依然没有被回收的内存，会放入老年代中。 这个足够多，是由 `-XX:MaxTenuringThreshold` 空置，默认是15, 当然，设计人员为了更加灵活的解决问题，它不是固定15次，也会根据实际的情况，来调整阈值。比如 新生代不足了，那么也会提前晋升.

如果老年代一旦满了，就会进入到full GC这个流程

STW概念 (STOP the world)

- GC的时候，它不会有任何操作，所以在程序运行的时候，一旦GC程序就会全部停止，等到GC完毕后再继续运行，所以这里就是 业务代码时间 = GC + 代码执行时间
- 新生代的GC一般都是小范围GC，时间比较短，但是如果老年代也满了，这时候就会触发 full GC， 它会导致程序中断时间长

GC机制是我们在性能测试中一定会注意并关注的机制，我们做测试的过程中，可以在这个角度向开发提出更多的意见，比如调整新生代，老年代的大小，以及晋升阈值等，合理的减少程序停顿时间，提升吞吐量。

### 三、常见的性能错误实操

- 实战：StackOverflowError-栈内存溢出

- 我们可以去访问一下地址 `http://192.168.1.111:8080/stack` 通过这里可以看到服务器明显报错：

这种场景，我们看到后只需要直接分析：

线程栈内存 默认大小1M，每个线程都会分配一个小内存区块，保存 线程执行的方法、局部变量的信息

这种错误发生的原因一般都是因为递归调用：

递归 --- 方法嵌套调用 自己 ， 栈-- 数据结构 -- 后进先出，每一次执行方法之前 ，把方法信息，压入栈，从上往下执行

递归： 方法调用没完毕，又调用自身.... 如果 长时间不结束，导致栈内存不够。

​

递归是编码中比较常用的调用方式：我们这里不可能说有递归就是不对的，一般情况下，开发的递归会有一个终止条件。很多情况下，是因为我们的中止条件没到，但是栈内存溢出了，所以优化的方式就是：

-Xss参数： Java每个线程的Stack大小

JDK5.0以后每个线程堆栈大小为1M，以前为 256K

但是注意：**在相同物理内存下，减小这个值能生成更多的线程** ！ 所以，我们要根据场景来实际分析，不存在说我们一定要调整栈大小。

实战：OutOfMemoryError

原因：持久性压力测试，程序内存占用逐步增高，最终挂掉 。突然大量并发，内存不够用

- 常见报错：`java.lang.OutOfMemoryError: unable to create new native thread` Java应用程序已经达到了它可以启动的线程数的限制

分析：这个问题通常来说，都是因为服务器内存资源不够，无法再创建线程了，否则就要关注，jvm的空间分配是否合理

- `java.lang.OutOfMemoryError: Metaspace 1.8+ java.lang.OutOfMemoryError: PermGen space` 元数据空间不足

分析： 这个报错见得比较少。

我们可以用参数调整 ：-XX:MaxPermSize=512m ，加大元数据空间的内存。或者检查元数据空间占用是否合理

元数据空间不足，一般都是因为代码中加载了太多的类,从而导致的不足

`java.lang.OutOfMemoryError: Java heap space` & `java.lang.OutOfMemoryError:GC overhead limit exceeded`

- 上面这两个错误比较常见， 这就是我们的堆内存不足，我们需要处理的方案就是加大堆内存，或者检查 内存占用了。

分析： 内存不足我们需要去定位内存问题，从而找到不足的点，所以我们可以采用内存快照来解决问题。让开发去进行修改和调优.

操作流程： 在启动命令生成快照,在jar包的启动命令下加入这个配置:

`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp`

启动命令: `java -javaagent:jmx_prometheus_javaagent-0.17.0.jar=12346:jmx_springboot.yaml -Dspring.jmx.enabled=true -Dserver.tomcat.mbeanregistry.enabled=true -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/u01/tmp -jar sys_perf_01-0.0.1-SNAPSHOT.jar`

生成了 hprof文件后，可以直接放到咱们的工具中去运行。

​

- 这种方式能够快速定位到我们的性能所在。

# 概念熟悉：服务器架构与中间件概念

## **. 服务器架构基础**

### **1.1 常见架构类型**

|  |  |  |
| --- | --- | --- |
| **架构类型** | **特点** | **适用场景** |
| **单体架构** | 所有功能集中在一个应用内 | 小型项目、快速验证阶段 |
| **垂直架构** | 按业务拆分为多个独立应用 | 中大型企业级系统 |
| **分布式架构** | 服务、数据、计算资源分散在多台服务器 | 高并发、高可用性需求场景 |
| **微服务架构** | 细粒度服务拆分，独立部署与扩展 | 复杂业务系统、云原生环境 |

**关键问题**：

- **数据一致性**：分布式环境下如何保证事务？
- **性能瓶颈**：单点数据库无法支撑高并发读写。
- **扩展性**：如何动态扩容存储与计算资源？

​

### **1.2 分布式架构的挑战**

**示例场景：电商平台订单表**

- **数据量爆炸**：每日百万级订单 → 单表查询性能下降。
- **硬件瓶颈**：单机磁盘 I/O、CPU 无法支撑。
- **可用性风险**：数据库宕机导致全站不可用。

**传统解决方案的不足**：

- 手动分表：业务代码侵入性强，维护成本高。
- 读写分离：主从同步延迟导致数据不一致。

​

## **2. 中间件核心概念**

### **2.1 什么是中间件？**

**定义**：

中间件（Middleware）是位于操作系统和应用程序之间的软件层，**封装通用功能**，简化分布式系统开发。

**核心作用**：

- **解耦**：隔离业务代码与底层技术细节（如分片、事务）。
- **复用**：提供通用能力（如路由、缓存、负载均衡）。
- **标准化**：统一接口，降低系统间交互复杂度。

​

### **2.2 中间件的分类**

|  |  |  |
| --- | --- | --- |
| **类别** | **典型产品** | **核心功能** |
| **数据中间件** | ShardingSphere、MyCAT | 数据库分片、读写分离、事务管理 |
| **消息中间件** | Kafka、RabbitMQ | 异步通信、削峰填谷 |
| **缓存中间件** | Redis、Memcached | 热点数据缓存、降低数据库压力 |
| **服务治理中间件** | Spring Cloud Alibaba | 服务注册发现、熔断限流  ​ |

### **2.3 中间件的核心价值**

**以 ShardingSphere 为例**：

1. **透明化分片**：

1. 业务代码无需感知分库分表逻辑。
2. 示例：`SELECT * FROM t_order` → 自动路由到物理表 `t_order_0`、`t_order_1`。

1. **负载均衡**：

1. 动态分配查询请求到多个数据源。

1. **弹性扩展**：

1. 动态添加数据节点，无需停机。

​

除此之外，我们还有很多常用中间件:

1. **缓存中间件：Redis**

1. 核心功能与数据结构
2. 高可用架构（主从、哨兵、集群）
3. 典型应用场景与实战案例

1. **消息中间件：MQ（以 RabbitMQ 为例）**

1. 消息队列的核心价值

1. **Web 中间件：Nginx**
