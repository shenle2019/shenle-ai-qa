# 性能测试的各大不同场景选择

问题： 性能测试各种不同的要求，我们应当怎么选择对应的场景线程组呢？

- 性能**测试类型**划分

|  |  |  |
| --- | --- | --- |
| 负载测试 | 举例：用户并发测试（通过递增并发用户数，查看系统性能指标变化） | 系统在不同负载下的性能表现，发现系统性能拐点，从而找出系统最佳性能 |
| 压力测试 | 评估系统处于或**超过预期**负载时系统的运行状况，关注点在于系峰值负载或超出最大载荷情况下的处理能力 | 同时也需要关注负载减小后，系统能否**自我恢复** |
| 稳定性测试 | 在特定的负载下（**略高**于正常负载）下，持续试压，验证系统能否**长期稳定**运行 | ​ |
| 配置测试 | 不断调整系统软硬件各种配置，系统性能达到最优时的最佳配置 | ​ |
| 基准测试 | 通过基准测试建立一个已知的性能水平（称为基准线），当系统的软硬件环境发生变化之后再进行一次基准测试以确定那些变化对性能的影响 | ​ |

​

- 性能场景

|  |  |  |
| --- | --- | --- |
| 业务峰值的稳定性 | 常规系统在日常正常运营期间，稳定性保证 | 负载测试 + 压力测试 |
| 新系统上线 | 准确探知站点的当前能力，防止系统一上线就被用户流量打垮 | 负载测试 + 压力测试+**稳定性测试** |
| 技术升级验证 | 技术架构升级，重新进行性能评估，验证新技术性能状况 | 负载测试 + 压力测试+**基准测试** |
| 容量规划 | 对系统做精细化的规划，主要服务于系统扩容，性能调优提供数据参考，节省成本投入 | 负载测试 + 配置测试 + **压力测试** |
| 大型活动瓶颈预估 | 针对于 秒杀，大促，抢票等瞬时大流量场景。目的就是提前评估风险 | 尖峰测试+负载测试 |

​

# 实操场景：最大人数探底测试(最大并发)

面试问题：TPS/吞吐量上不去，分析一下原因？

很简单原因： 压力不够，当前压力机无法再继续创建更多线程，或者说创建了更多线程也会报错了

- 在 2-3 GHZ CPU上 单个jmeter客户端，最多只能处理 1000-2000个线程。
- 不可能有场景，单机搞出上万并发。
- 概念：**分布式压测(多机器集群压测)**
- 通过远程运行Jmeter，可以在很多的低端机上复制测试，从而模拟服务器最大的负载.
- Jmeter的一个客户端实例，可以控制任意数量的远程Jmeter实例。集中将所有数据收集在控制机上.

# 实操场景：秒杀活动与抢票等高并发场景测试

问题：我们如果出现有大促活动，这种情况下我们应该如何完成我们的测试工作?

测试目标：性能测试过程必须考虑到用户行为与用户参与的过程.

秒杀，抢票，大促 都有同样的特点：

- 用户瞬时涌入服务器，在接近截止时间的时候达到最高峰
- 用户完成操作之后，瞬间全部退出，让服务器回到之前的压力

我们一般情况下会选择采用尖峰测试来进行本次场景模拟测试,需要考验在最高峰期间，用户对性能带来的影响。

- 秒杀活动面临的挑战：

- 服务器很容易被忽然爆发的并发瞬间击垮
- 高并发过程中很容易出现库存为负数【超卖问题】

- 检查最终库存是否为负数。
- 检查订单总数是否超过初始库存。

设置方式:

- 选择 Ultimate Thread Group

当然也可以采用梯度压测的方式进行对应的处理 .

​

- 测试流程：

接口1 被瞬时流量压垮 ，此时可以直接判定本接口不合格。

接口2 出现明显超卖问题，在测试结束后，需要开发提供接口判断，本次测试结束后库存大小

采用 tearDown线程组 ，进行库存断言与订单数量断言

接口3 正常行为，定义到本次并发的瓶颈所在

- 测试计划编写
- 测试报告编写

# 实操场景: 混合场景测试应用流程

提问：多场景之下，我们可能会有需求：当前系统下有场景A 场景B 场景C 三个不同场景。场景A有70%的用户访问，场景B有20%用户访问，场景C有10%用户访问。这种情况下，我们如何进行性能压测？

- 分析思路: 根据需求调研的业务模型和交易占比，设置不同并发用户数。
- 难点：用户的数量与范围在一个线程组中需要按比例设置。
- 注意：如果是简单场景，我们可以直接按数字多设置几个线程组处理，但是性能测试需要不断调整线程数，所以一般不采用这样的方式
- 如何按比例设置？
- 右键线程组 --> 添加 -->逻辑控制器-->吞吐量控制器

- 吞吐量控制器说明 ：吞吐量控制器用于 **控制其子元件的执行频率**，通常用于在负载测试中按比例分配不同业务逻辑的执行次数。

- **核心功能**：

- 按百分比或固定次数控制子元件的执行频率。
- 模拟真实场景中不同操作的占比（例如：20%用户登录，80%用户浏览）。

按照对应比例来进行压力测试.

- 测试计划怎么写？
- 测试报告怎么输出?
- 思考问题？如果比例设置加起来不到100%该怎么办？

# 实操场景：秒杀活动与抢票大促活动高并发场景探底测试

问题：如果出现了大促活动，顶流明星开办的对应活动，我们如何完成我们的测试工作？

- 场景分析:

- 用户行为：秒杀，抢票，大促都有同样的特点:

- 用户某一段时间，忽然大量涌入服务器，操作完毕之后，瞬间全部退出,在截止时间附近到达最高峰.
- 用户完成操作后，瞬间全部退出，服务器是否能够及时恢复正常，或者说服务器恢复时间是否达到预期

- 这样的用户行为，我们会采用尖峰测试，来模拟当前场景下服务器的指标和问题。
- 测试注意事项：

- 服务器是否会瞬间冲垮。性能明显降低且后续不会恢复。
- 高并发状态下很容易出现库存为负数，产生的订单数大于我们总库存数。【**超卖问题**】

​

模拟这个大促，和秒杀活动的场景.

设置方式：

- 选择 Ultimate Thread Group
- 拿到我们的jar包文件

启动命令  java -jar 包名

java -jar spike-demo2-0.0.1-SNAPSHOT.jar

访问地址 ： /performancetest 本接口会出现并发bug  **端口号 9092**

参数 ： **svg 1 count 1**

**在实际工作中，怎么样关注超卖问题，做检查。**

- 活动结束后，库存数量是否被减为负数。
- **秒杀订单总数**，大于商品库存总数

# 实操场景：数据修改与插入场景测试

问题：我们在日常的性能测试中，往往不仅仅是查询接口的压测，很多情况下，我们还要针对插入(修改)场景做性能测试。这种操作，就是事务操作。

**事务操作：引起数据变化的操作都是事务操作.**

**引起数据变化会导致什么问题？**

- 磁盘读写操作(写入磁盘),如果磁盘占用率比较高，会导致写入速度慢。从而引起响应速度慢.
- 因为数据一般是存放在数据库内的，我们去写数据，会引发数据库的锁机制

- 场景分析：

- 数据的修改和插入我们要注意什么东西？
- 难点1：数据从哪里来呢？ 【人工造数据】
- 要能够生成数据，让它能够在我们这里进行插入,生成的数据，我们还需要控制它的数量
- 难点2: 插入数据，势必需要权限。
- 权限问题怎么解决？
- 难点3：当数据被插入完毕之后，【脏数据】我们怎么把数据库恢复原状？

​

- 处理方案：

- 数据问题，我们一般会采用脚本去生成数据【脚本在随堂资料中】
- 先获取当前接口需要的参数,做一个示例。
- 把生成的数据，写入到一个CSV里面去，插入的时候，通过CSV来去读取数据插入
- 插入数据需要权限问题- 用户的token问题，我们只需要找到一个(多个)有权限的用户就行了。【实际工作中，尽量采用多用户的模式，学习期间，先用单用户解决问题.】
- 权限，跨线程传递给接口进行执行。
- 数据怎么清洗 ，根据我们生成的数据，给一个特别的名字归类。
- 最后准备一个 tearDown线程组，执行删除操作

setup线程组，准备登录。

CSV文件进行数据读取

tearDown线程组做数据清洗操作
