# SmartPerf Device性能工具使用指导

## 工具简介

SmartPerf Device是一款基于系统开发的性能功耗测试工具，操作简单易用。该工具可以监测性能、功耗相关指标，包括FPS、CPU、GPU、RAM、Temp等，通过量化的指标项了解应用、整机性能状况。

Device-daemon端支持shell命令行方式，同时适用于有屏和无屏设备。

### 指标说明

- CPU：每秒读取一次设备节点下CPU大中小核的频点和各核使用率，衡量应用占用CPU资源的情况，占用过多的CPU资源会导致芯片发烫。
- GPU：每秒读取一次设备节点下GPU的频点和负载信息，衡量应用占用GPU资源的情况，当GPU占用过多时，会导致性能下降，应用程序的运行速度变慢。
- FPS：应用界面每秒刷新次数，衡量应用画面的流畅度，FPS越高通常表示图像流畅度越好，用户体验也越好。
- TEMP：每秒读取一次设备节点下GPU温度、系统芯片温度信息。
- RAM：每秒读取一次应用进程的实际物理内存，衡量应用的内存占比情况。
- snapshot：每2秒截取一张应用界面截图。

## 实现原理

下图展示了SmartPerf Device工具的主要功能组成。Device-hap端设置好采集项和采集参数后，启动应用，FPS、RAM、Trace等指标通过消息发送给Device-daemon端，Device-daemon端进行数据采集、持久化和数据分析。

## 约束与限制

1. Device-daemon端在API 9版本开始预置使用。
2. Device-daemon端执行需连接硬件设备。
3. Device-daemon端执行前需完成[hdc环境配置](https://gitee.com/openharmony/developtools_hdc)。

### 参数说明

#### **采集控制参数**

- `-N <times>`  
  设置数据采集次数（默认值为 0，表示持续采集），范围为 `[1, 2147483647]`。例如：`-N 10` 表示采集 10 次数据后停止。
- `-start`**和**`-stop`  
  启动或停止数据采集（适用于需要手动控制采集过程的场景）。
- `-sections <time_period>`  
  设置采集时间段（与 `-profilerfps` 配合使用），例如 `-sections 10s` 表示采集 10 秒的帧率数据。

#### **必选参数**

- `-PKG <package_name>`  
  指定要测试的应用包名（例如：`ohos.samples.ecg`）。如果需要监控特定应用的性能，这个参数必须添加。

#### **数据采集类型（可组合使用）**

- **CPU 相关**

- `-c`：收集 CPU 频率、设备整体 CPU 使用率、特定进程 CPU 使用率、CPU 负载等。

- **GPU 相关**

- `-g`：收集 GPU 频率和 GPU 负载。

- **帧率相关**

- `-f`：收集应用的帧率（FPS）、帧率抖动和刷新率。
- `-profilerfps`：收集带时间戳的详细帧率数据（通常与 `-sections` 配合使用）。

- **电池相关**

- `-t`：收集电池剩余电量和温度。
- `-p`：收集电池功耗和电压。

- **内存相关**

- `-r`：收集进程内存占用和系统总内存使用情况。

- **网络相关**

- `-net`：收集应用的上行和下行网络流量。

- **其他**

- `-snapshot`：获取屏幕截图（用于可视化分析）。
- `-d`：获取设备 DDR（内存芯片）信息。
- `-nav`：获取应用页面导航信息（例如页面跳转时间）。
- `-screen`：获取屏幕分辨率信息。

#### **输出参数**

- `-OUT <path>`  
  设置 CSV 格式的输出文件路径，用于保存采集的性能数据。
- `-VIEW <layer>`  
  指定要监控的 UI 层（例如：`DisplayNode`），用于分析特定 UI 组件的性能。

### 场景化采集

场景化采集是对应用页面滑动、切换场景下的性能测试，针对不同操作场景执行相对应的采集命令，获取应用性能数据，包括页面的滑动帧率，页面切换或滑动的卡顿率、响应时延、完成时延以及最大连续丢帧，对采集数据进行输出打印，以便用户分析并优化应用性能。场景化采集结果不写入data.csv，采集结果直接在命令框显示。

|  |  |  |
| --- | --- | --- |
| 命令参数 | 必选 | 说明 |
| -editor | 是 | 场景化采集标识，后可添加参数配置项 |
| timeDelay | 否 | 页面切换（支持ArKUI子系统的router、navigation、tabs、swiper控件内的页面切换/内容切换） |
| slideList | 否 | 页面切换（支持ArKUI子系统的router、navigation、tabs、swiper控件内的页面切换/内容切换） |

采集输出各参数含义说明：

- ResponseTime（响应时延）

- **含义**：从触发页面切换或页面滑动操作开始，到系统开始响应这一操作所经历的时间，单位为毫秒（ms） 。比如，当用户点击一个按钮触发页面切换，从点击瞬间到系统开始处理这个切换请求的时间间隔就是 ResponseTime。
- **评估作用**：该参数反映了系统对用户操作的即时响应能力。数值越小，说明系统能越快感知并开始处理用户的页面切换或滑动操作，用户会感觉操作更流畅、更灵敏。如果这个时间较长，用户可能会觉得操作有延迟、不跟手。**优秀阈值：<100 ms，一般是 <=300 或>100**

- CompleteTime（完成时延）

- **含义**：从页面切换操作触发开始，到页面完全完成切换并稳定显示所需的时间，单位是毫秒（ms） 。它涵盖了从系统响应操作，到完成页面数据加载、渲染等一系列流程直至页面最终呈现给用户的整个时长。
- **评估作用**：用于衡量页面切换操作从开始到结束的整体耗时。可以帮助评估页面切换过程是否高效。当 CompleteTime 较长时，用户在等待页面切换完成的过程中会感到卡顿或等待时间过长，影响用户体验。通过分析这个参数，开发人员可以查找页面切换过程中是否存在数据加载缓慢、渲染效率低等问题。**理想 < 1000 ms**

- HitchTimeRate（卡顿率）

- **含义**：指在页面切换或页面滑动过程中，出现卡顿情况的时间比率，单位为毫秒每秒（ms/s） 。卡顿通常是由于帧率不稳定、资源加载不及时等原因，导致页面更新不连贯，给用户造成画面卡顿的感觉。该参数衡量了在单位时间内，这种卡顿情况所占用的时间比例。
- **评估作用**：是评估页面流畅度的关键指标之一。较低的 HitchTimeRate 表示页面切换或滑动过程中卡顿情况较少，用户体验更流畅；反之，较高的 HitchTimeRate 意味着卡顿频繁，会严重影响用户对应用的使用感受。通过监控这个参数，可以发现页面在交互过程中出现卡顿的时段，进而深入分析是哪些操作或资源引发了卡顿问题。**理想 < 100 ms/s**

- MAX\_RENDER\_SEQ\_MISSED\_FRAMES（最大连续丢帧）

- **含义**：在页面切换或页面滑动过程中，连续丢失的最大帧数 。在图形渲染过程中，每一帧都代表一个画面状态，如果在一段时间内连续丢失较多帧，就会导致画面出现明显的不连贯、卡顿甚至跳帧现象。
- **评估作用**：反映了页面渲染过程中的稳定性。连续丢帧情况严重时，会极大地破坏用户体验，尤其是在一些对画面流畅度要求较高的场景，如动画展示、游戏界面等。开发人员可以根据这个参数，排查渲染过程中是否存在资源不足（如 GPU 负载过高）、渲染算法不合理等问题。**-1 表示****无连续丢帧（正常）**

- FPS（页面滑动帧率）

- **含义**：即每秒显示的帧数，单位为 fps（frames per second） 。它表示在页面滑动过程中，屏幕每秒能够更新的画面数量。帧率越高，意味着页面在滑动过程中画面更新越频繁、越连贯，视觉上也就越流畅。
- **评估作用**：是衡量页面滑动流畅度的重要指标。一般来说，60fps 及以上的帧率能给用户带来较为流畅的体验；当帧率低于 30fps 时，用户就可能明显感觉到画面的卡顿。通过监测 FPS，可以评估页面在不同操作和场景下的流畅程度，帮助优化页面渲染性能，确保用户在滑动页面时获得良好的视觉感受。**理想值：≥60 fps**

> 说明
>
> - 时延计算受系统打点上报限制，开始时间为点击事件上报时间点，响应时延结束时间点为点击后系统响应首帧的上屏时间点，完成时延是切换后页面的首帧上屏时间点，与端到端用户感知时延存在差异。

> 说明
>

> - 页面滑动卡顿率：目前只支持Web、ArKUI子系统的List、grid、scroll、waterflow滚动组件。计算公式：页面滑动卡顿率=页面滑动动效时间内每一帧的累计丢帧时间（ms）/ 动效时长（s）。
> - 最大连续丢帧受系统打点上报限制，与端到端用户感知时延存在差异。
> - 页面滑动同时会抓取trace，文件路径：`data/local/tmp/sp_trace_fps.ftrace`，通过`hdc file recv`的方式导出查看trace。

# wukong稳定性工具使用指导

## 功能介绍

wukong是系统自带的一种命令行工具，支持Ability的随机事件注入、控件注入、异常捕获、报告生成和对Ability数据遍历截图等特性。通过模拟用户行为，对系统或应用进行稳定性压力测试。wukong分为随机测试、专项测试和专注测试。

- **随机测试**是指随机测试界面内容，支持的能力包括：shell启动、拉起整机应用、多种注入方式、设置随机种子、打印运行日志和生成报告。
- **专项测试**主要提供对指定应用控件进行测试，支持的能力包括：shell启动、顺序遍历及截图、测试休眠睡醒、录制回放、打印运行日志和生成报告。
- **专注测试**主要提供对指定控件的注入测试，支持的能力包括：shell启动、拉起整机应用、多种注入方式、设置随机种子、设置专注控件类型、设置注入控件次数、打印运行日志和生成报告。

## 实现原理

wukong部件架构图以及部件内子模块职责如下所述。

- 命令行解析：支持命令行获取参数并解析命令行参数。
- 运行环境管理：根据命令行初始化wukong整体运行环境。
- 系统接口管理：检查并获取指定的mgr，注册controller和dfx的faultlog的回调函数。
- 随机事件生成：通过random函数生成指定种子数的随机序列，生成事件。
- 事件注入：根据支持的事件类型向系统注入事件，依赖窗口、多模、安全等子系统。
- 异常捕获处理/报告生成：通过DFX子系统获取运行中的异常信息并记录log，生成报告。

### 休眠唤醒测试（`-k, --spec_insomnia`）

- **功能**：模拟设备休眠（灭屏）和唤醒（亮屏）过程，测试稳定性。
- **应用场景**：测试待机功耗、唤醒延迟、界面恢复是否正常。

### 滑动测试（`-S, --swap`）

- **功能**：模拟屏幕滑动操作，支持单点滑动或往返滑动。
- **关键参数**：

- `-s, --start[x,y]`：滑动起点坐标（如 `-s 500,1000`）。
- `-e, --end[x,y]`：滑动终点坐标（如 `-e 500,500`）。
- `-b, --bilateral`：开启往返滑动（默认单次滑动）。

- **应用场景**：测试列表、页面滑动的流畅度、卡顿率（需结合 `SP_daemon` 采集 FPS）。

### 点击测试（`-t, --touch[x,y]`）

- **功能**：模拟屏幕点击操作，支持单点坐标点击。
- **应用场景**：测试按钮响应速度、重复点击的稳定性（如提交按钮）。

如果确定元素的坐标

### 控件遍历测试（`-C, --component`）

- **功能**：自动遍历应用内的可交互控件（如按钮、输入框），验证功能可用性。
- **必选参数**：需指定应用包名（通过 `-C com.example.app`）。
- **注意**：需确保应用已打开至目标页面，工具会根据当前界面层级遍历控件。

### 录制与回放（`-r, --record` / `-R, --replay`）

- **功能**：

- **录制**（`-r`）：记录手动操作轨迹（如滑动、点击）到文件。
- **回放**（`-R`）：重复执行录制的操作序列。

- **应用场景**：批量执行重复测试流程，或复现特定操作导致的问题。
