什么是Skills？

- **定义**：Skills 是预定义好的**任务执行流程**或**工具调用集合**，让助手能够完成某一类专门的工作（比如生成测试用例、查询数据库、发送邮件等）。
- **类比**：就像给一个人（智能体工具）配上了“会计技能”，他就能做账；配上“测试技能”，他就能按规则生成测试用例。

##### 第一步：确定输入地址

- **动作**：询问用户文档所在的路径（本地或仓库地址）。
- **建议**：可以设置一个默认路径（如 `./原始需求文档/`），提高效率。

##### 第二步：统一文档格式为 Markdown

输入的文档可能是 **Word（.doc/.docx）**、**PDF（.pdf）** 或 **Markdown（.md）**。为统一处理，我们全部转换为 **.md** 格式。

​

📌**问题：为什么选择 Markdown？**

1. **纯文本**，易于解析和程序处理。
2. **轻量级**，可读性强，人工和机器都友好。
3. 支持标题、列表、代码块等基本格式，满足大多数文档需求。
4. 可方便地转换为 HTML、PDF 等其他格式。
5. 没有 Word/PDF 的复杂二进制结构或依赖库问题。
6. 便于版本控制（如 Git）和团队协作。

​

##### 第三步：按章节目录拆分（以功能点为核心）

- **拆分依据**：按照原文档的章节结构，但**核心是以功能点为单位**进行切割（可根据公司规范调整）。
- **拆分后**：生成多个独立的 `.md` 文件，每个文件对应一个功能点或小节。
- **图片处理**：提取原文档中的所有图片，统一存入 `images/` 目录，在 `.md` 文件中使用**相对路径**引用。

❗注意：

> **不同公司的需求文档格式可能有所差异。**这里我们以业界常见的模板为例进行讲解，大家在实际工作中可根据自身情况适当调整，或者用你们文档直接通过AI解析成标准的格式即可。在此过程中，我主要为大家讲解设计思路及实现方法。

#### **步骤3：生成测试-生成测试点**

> **在使用时，直接将要测试的模块交给AI来生成测试用例，这种方式是可行的。但当AI需要完成一系列复杂操作时，我们往往****难以快速定位和分析其中的关键点****。因此，更好的做法是：先让AI产出对应的测试点，再基于这些测试点去生成具体的测试用例。在此过程中，需要明确三个核心要素：输入、输出以及相应的规则。**

##### 第一步：生成测试点

在梳理知识点或分析测试点时，需要明确区分**公共内容**与**独立的**内容：

- **公共内容**：多个场景或模块共用的部分，暂不做考虑。
- **功能模块**：特定场景或模块独有的部分，需单独处理。
- **公共模块**：当每个页面都有的功能或者（>=2），则无需重复去写。

基于这一区分，应采用**不同的模板**分别对公共和私有内容进行系统化梳理，以确保测试点分析的全面性和清晰度。

##### 第二步：确定测试点的输入输出以及相应规则模板

1. **数据来源**：从当前项目下的 `01-需求` 文件夹中读取“规整需求文档”。
2. **模块识别规则**：

- **公共内容：**文档中编号以 **1.0.引言.md、2.0.总体描述.md、3.0.外部接口需求.md、5.0.性能需求.md、6.0.约束条件.md、7.0.验收准则.md、8.0.附录.md**，暂不做考虑分析。
- **功能模块**编号以 `4.` 开头的都是**独立功能模块，包含**（4.x）。
- **公共模块**：当每个页面都有的功能或者（>=2），则无需重复去写。

1. **测试点生成**：以功能模块为核心，基于其需求内容生成对应的测试点。
2. **输出目录**：当前项目下的 `02-测试` 文件夹中`测试点分析`文件夹。
3. **输出文件**：

- 公共模块 → `00_全局通用模块.md`（所有公共模块的测试点汇总于此）
- 每个独立功能模块 → `{功能名}.md`（其中 `{功能名}` 从需求文档中提取）

测试点模板如下：

- 页面测试点文件命名：`<功能名>.md`， 示例：`登录.md`

- 页面测试点文档模板

> 这里为什么MD文档要这样子的格式，为了方便别的工具进行导入，比如快速生成Xmind格式。

- 全局公共模块文件命名：测试点分析/00\_全局通用模块.md
- 全局公共模块文档模板

##### 第二步：制定生成规范

> 这个位置当中规则越详细生成的数据越准确。

- 在编写测试用例之前，需要预先定义清楚：重点为 **功能测试**，验证页面功能是否符合需求。
- 其他测试类型（界面测试、兼容性测试、响应式测试、性能测试、安全性测试、可用性测试）不在本次生成范围内。

|  |  |  |
| --- | --- | --- |
| **方法** | **说明** | **适用场景** |

> 测试用例应该包含哪些字段：用例编号、模块、前置条件、测试步骤、预期结果、实际结果、测试结果**、**优先级等

测试步骤是测试用例的核心

- 它是执行操作的唯一依据，必须**明确、无歧义、可重复**。
- 不规范的步骤会导致不同测试人员执行结果不一致，更难以转化为自动化脚本。

​

禁止使用“模糊描述”代替具体操作

❌ **错误示例**：

- “输入其他数据”
- “点击其他按钮”
- “输入一些无效值”

✅ **正确做法**：

- 必须明确操作对象（按钮名称、输入框标签）和操作内容。
- 若数据不重要，可描述数据的**类型/边界特征**，而非具体值

### 场景3：无需求文档录制方式

# 四、结束语

到这里，我们站在功能者的角度，测试用例已经生成成功了。

​

仅靠录制可能不够全面。如果你所在的公司已有部分简单文档（如流程说明、业务规则），可以将这些文档作为**参考知识库**，与录制数据结合：

- 录制操作流程
- 导入已有知识库内容
- 让AI在生成文档和用例时，**参考**这些已有信息，使结果更贴合公司实际业务。

​

**总体思路**

1. **统一输入格式**：将所有来源（Swagger、录制数据、抓包文件）统一转换为 **MD 格式的中间文档**。
2. **定义技能**：针对不同来源设计专用技能
3. **调用技能**：输入中间文档 → 调用技能 → 输出测试用例（MD + Excel）。
4. **查看结果**：验证用例覆盖度与格式正确性。

**接下来可以做什么？**

1. **自动化执行**：将生成的 Excel 用例导入 Postman/JMeter/Selenium 等工具，实现自动化回归。
2. **CI/CD 集成**：在代码提交或每日构建时，自动触发用例生成与执行。
3. **持续优化**：根据实际运行结果，反向修正中间文档模板，提高用例质量。

> 记住：**用例生成只是起点，自动化执行与持续反馈才是价值闭环**。
