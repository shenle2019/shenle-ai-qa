## 二、测试目标与范围

### 2.1 测试目标

1. 验证本次迭代功能是否符合需求规格说明书，核心功能无阻断性缺陷；

1. 确保系统在目标环境（如：Android 10+/iOS 14+、Chrome 90+）下兼容性达标，无闪退、卡顿等问题；

1. 验证系统性能指标（如：接口响应时间≤500ms、并发用户数≥1000）满足设计要求；

1. 识别并修复安全风险（如：SQL注入、XSS攻击、敏感数据泄露），符合行业安全规范（如：等保2.0）；

1. 保障用户体验流畅，交互逻辑符合用户习惯（如：按钮点击反馈、页面跳转逻辑）。

### 2.2 测试范围

#### 2.2.1 纳入测试的模块

|  |  |
| --- | --- |
| 模块名称 | 测试内容（核心功能/场景） |
| 用户模块 | 注册（手机号/邮箱）、登录（验证码/密码/第三方登录）、个人信息修改、密码重置 |
| 商品模块 | 商品列表查询（筛选/排序）、商品详情展示、库存更新、商品上下架 |
| 订单模块 | 下单流程（购物车结算/直接购买）、订单状态更新（待支付/已支付/取消/退款）、订单详情查询 |
| 支付模块 | 支付方式选择（微信/支付宝/银行卡）、支付接口调用、支付结果同步、退款流程 |
| 数据统计模块 | 订单数据统计（日/周/月）、用户活跃度统计、商品销量排行展示 |

#### 2.2.2 不纳入测试的范围

1. 历史版本已稳定上线、本次迭代无修改的模块（如：帮助中心静态页面）；

1. 未明确需求文档的功能（如：预留的“会员等级体系”功能，需求暂未定稿）；

1. 第三方接口的内部实现逻辑（如：微信支付接口的底层加密逻辑，仅测试调用结果正确性）；

1. 硬件设备兼容性（如：仅测试主流手机型号，不覆盖小众品牌设备）。

## 五、测试策略与类型

### 5.1 功能测试

#### 5.1.1 测试方法

1. 等价类划分：将输入数据分为有效等价类（如：合法手机号11位数字）和无效等价类（如：10位手机号、含字母的手机号），覆盖核心场景；

1. 边界值分析：针对数值型参数（如：订单金额、库存数量），测试边界值（如：金额0元、库存1件/0件、最大金额99999元）；

1. 场景法：模拟真实用户操作流程（如：“用户注册→登录→搜索商品→加入购物车→下单→支付→查看订单”全链路场景）；

1. 错误推测法：基于历史缺陷和经验，推测可能出现问题的场景（如：支付时断网、订单提交时库存不足）。

#### 5.1.2 测试重点

- 核心流程完整性：确保“下单-支付-履约”全链路无断点；

- 异常场景处理：验证系统对异常输入（如：空值、特殊字符）、异常操作（如：重复提交订单、支付超时）的容错能力；

- 数据一致性：跨模块数据同步正确性（如：支付成功后，订单状态同步更新为“已支付”，库存同步扣减）。

### 5.2 兼容性测试

#### 5.2.1 测试范围

|  |  |
| --- | --- |
| 兼容类型 | 测试内容 |
| 浏览器兼容 | Chrome 90+、Firefox 100+、Edge 100+、Safari 15+（PC端） |
| 移动端兼容 | iOS 14+（iPhone 12及以上）、Android 10+（华为/小米/OPPO/VIVO主流机型） |
| 分辨率兼容 | PC端：1920×1080、1366×768；移动端：1080×2340、750×1334 |
| 系统版本兼容 | 后端：Linux CentOS 7/8、Windows Server 2019；数据库：MySQL 5.7/8.0 |

#### 5.2.2 测试方法

- 真机测试：主流机型真机实测，验证UI显示、功能操作正确性；

- 模拟器辅助：使用Android Studio模拟器、Xcode模拟器覆盖小众版本；

- 自动化兼容测试：通过Appium框架批量执行基础功能用例，快速定位兼容性问题。

### 5.3 性能测试

#### 5.3.1 测试指标与标准

|  |  |  |  |
| --- | --- | --- | --- |
| 性能类型 | 测试指标 | 目标值 | 测试工具/方法 |
| 接口性能 | 平均响应时间 | ≤500ms | JMeter压测，单接口并发100用户 |
|  | 95%响应时间 | ≤800ms |  |
|  | 错误率 | ≤0.1% |  |
| 并发性能 | 支付接口并发用户数 | ≥1000（无超时） | JMeter模拟1000用户同时下单支付 |
|  | 系统CPU使用率 | ≤70%（峰值） | Grafana监控服务器资源 |
|  | 内存使用率 | ≤80%（持续运行2小时） |  |
| 稳定性性能 | 系统持续运行时间 | ≥72小时（无崩溃） | 长时间压测（JMeter+Grafana持续监控） |
|  | 数据库连接池使用率 | ≤80% | MySQL监控工具（如：Navicat Monitor） |

#### 5.3.2 测试场景

1. 常规负载测试：模拟日常用户量（如：500并发用户），验证系统稳定运行；

1. 峰值负载测试：模拟活动峰值（如：1000并发用户），验证系统是否满足性能目标；

1. 压力测试：逐步提升并发量（如：从1000→2000用户），定位系统瓶颈（如：数据库慢查询、服务器内存不足）；

1. 稳定性测试：72小时持续运行，验证系统是否存在内存泄漏、连接池耗尽等问题。

### 5.4 安全测试

#### 5.4.1 测试内容

|  |  |  |
| --- | --- | --- |
| 安全类型 | 测试点 | 测试方法/工具 |
| 接口安全 | SQL注入（如：订单ID参数拼接SQL语句） | OWASP ZAP扫描、手动构造恶意参数 |
|  | XSS攻击（如：用户昵称输入`<script>`标签） | 输入特殊字符，验证页面是否过滤 |
|  | 接口未授权访问（如：直接访问他人订单详情接口） | 修改请求头中的用户ID，验证是否返回数据 |
| 数据安全 | 敏感数据明文传输（如：密码、银行卡号未加密） | Wireshark抓包，查看数据传输格式 |
|  | 数据库敏感数据明文存储（如：用户密码未哈希） | 查看数据库表结构，验证密码存储方式 |
| 服务器安全 | 服务器端口开放过多（如：不必要的8080端口暴露） | Nessus扫描、nmap端口探测 |
|  | 弱口令（如：数据库账号密码为admin/123456） | 暴力破解工具测试、人工核查 |

#### 5.4.2 安全标准

- 符合《信息安全技术 网络安全等级保护基本要求》（GB/T 22239-2019）三级标准；

- 敏感数据传输需采用HTTPS加密，存储需采用MD5/SHA256哈希+盐值加密；

- 接口需添加鉴权机制（如：Token令牌、签名验证），防止未授权访问。

### 5.5 用户体验测试

#### 5.5.1 测试内容

1. UI一致性：页面布局、按钮样式、字体大小符合设计稿，无错位、遮挡；

1. 交互流畅性：按钮点击有反馈（如：颜色变化、加载动画），页面跳转无白屏（≤200ms）；

1. 操作便捷性：核心流程步骤≤3步（如：从“商品详情”到“支付完成”≤3步），支持快捷操作（如：一键结算）；

1. 提示友好性：错误提示明确（如：“手机号格式错误，请输入11位数字”而非“参数错误”），引导用户修正。

#### 5.5.2 测试方法

- 参照UI设计稿逐页比对；

- 模拟真实用户操作，记录操作痛点；

- 邀请5-10名目标用户进行 usability测试，收集反馈。

## 七、缺陷管理

### 7.1 缺陷等级定义

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| 缺陷等级 | 定义 | 示例 | 修复优先级 | 验证要求 |
| P0（阻断） | 核心功能无法使用，导致测试无法继续，或上线后会造成严重业务损失 | 支付接口调用失败，所有用户无法支付；系统启动后闪退 | 紧急（2小时内响应，24小时内修复） | 修复后需全量回归核心流程 |
| P1（严重） | 核心功能存在缺陷，但有替代方案，或上线后会影响部分用户体验/数据准确性 | 订单详情页显示错误（如：金额显示为0）；部分用户登录时验证码收不到 | 高（4小时内响应，48小时内修复） | 修复后回归对应模块及关联功能 |
| P2（一般） | 非核心功能缺陷，不影响主流程，上线后对用户体验影响较小 | 商品列表页排序功能异常（如：按价格排序无效）；帮助中心某篇文章链接失效 | 中（1个工作日内响应，3个工作日内修复） | 修复后回归对应功能点 |
| P3（优化） | UI细节、交互体验优化，无功能问题，不影响系统使用 | 按钮点击后反馈动画延迟；某页面字体与设计稿略有差异 | 低（2个工作日内响应，迭代内修复或延后） | 修复后视觉/交互验证 |

### 7.2 缺陷提交规范

缺陷报告需包含以下字段，确保信息完整：

1. 缺陷标题：简洁明确（如：“支付成功后，订单状态未同步更新为‘已支付’”）；

1. 所属模块：如“订单模块-订单状态管理”；

1. 缺陷等级：按7.1定义选择（P0/P1/P2/P3）；

1. 复现步骤：清晰描述操作步骤（如：1. 登录账号XXX；2. 下单商品XXX；3. 选择支付宝支付并完成付款；4. 查看订单状态）；

1. 预期结果：如“订单状态应更新为‘已支付’”；

1. 实际结果：如“订单状态仍显示为‘待支付’”；
