# 概念熟悉：服务器架构与中间件概念

## **. 服务器架构基础**

### **1.1 常见架构类型**

|  |  |  |
| --- | --- | --- |
| **架构类型** | **特点** | **适用场景** |
| **单体架构** | 所有功能集中在一个应用内 | 小型项目、快速验证阶段 |
| **垂直架构** | 按业务拆分为多个独立应用 | 中大型企业级系统 |
| **分布式架构** | 服务、数据、计算资源分散在多台服务器 | 高并发、高可用性需求场景 |
| **微服务架构** | 细粒度服务拆分，独立部署与扩展 | 复杂业务系统、云原生环境 |

**关键问题**：

- **数据一致性**：分布式环境下如何保证事务？
- **性能瓶颈**：单点数据库无法支撑高并发读写。
- **扩展性**：如何动态扩容存储与计算资源？

​

### **1.2 分布式架构的挑战**

**示例场景：电商平台订单表**

- **数据量爆炸**：每日百万级订单 → 单表查询性能下降。
- **硬件瓶颈**：单机磁盘 I/O、CPU 无法支撑。
- **可用性风险**：数据库宕机导致全站不可用。

**传统解决方案的不足**：

- 手动分表：业务代码侵入性强，维护成本高。
- 读写分离：主从同步延迟导致数据不一致。

​

## **2. 中间件核心概念**

### **2.1 什么是中间件？**

**定义**：

中间件（Middleware）是位于操作系统和应用程序之间的软件层，**封装通用功能**，简化分布式系统开发。

**核心作用**：

- **解耦**：隔离业务代码与底层技术细节（如分片、事务）。
- **复用**：提供通用能力（如路由、缓存、负载均衡）。
- **标准化**：统一接口，降低系统间交互复杂度。

​

### **2.2 中间件的分类**

|  |  |  |
| --- | --- | --- |
| **类别** | **典型产品** | **核心功能** |
| **数据中间件** | ShardingSphere、MyCAT | 数据库分片、读写分离、事务管理 |
| **消息中间件** | Kafka、RabbitMQ | 异步通信、削峰填谷 |
| **缓存中间件** | Redis、Memcached | 热点数据缓存、降低数据库压力 |
| **服务治理中间件** | Spring Cloud Alibaba | 服务注册发现、熔断限流  ​ |

### **2.3 中间件的核心价值**

**以 ShardingSphere 为例**：

1. **透明化分片**：

1. 业务代码无需感知分库分表逻辑。
2. 示例：`SELECT * FROM t_order` → 自动路由到物理表 `t_order_0`、`t_order_1`。

1. **负载均衡**：

1. 动态分配查询请求到多个数据源。

1. **弹性扩展**：

1. 动态添加数据节点，无需停机。

​

除此之外，我们还有很多常用中间件:

1. **缓存中间件：Redis**

1. 核心功能与数据结构
2. 高可用架构（主从、哨兵、集群）
3. 典型应用场景与实战案例

1. **消息中间件：MQ（以 RabbitMQ 为例）**

1. 消息队列的核心价值
2. 核心概念与工作模式
3. 异步解耦实战：订单系统与库存系统

1. **Web 中间件：Nginx**

1. 反向代理与负载均衡
2. 动静分离与高并发优化
3. 配置示例与性能调优

### **综合实践：电商系统架构设计**

## redis性能测试注意事项:

**缓存预热** : 如果程序初次运行，此时由于数据尚未加载到缓存，则程序的响应时间会明显变长。

注意：性能测试的时候 出现 非常不稳定的现象，程序刚启动，它的性能 明显 低于 已经运行一段时间的。

如何测试？

1. 测试 缓存没有的情况， 系统性能是怎么样的？ 以及 多久才能恢复到正常的性能
2. 测试 缓存已经加载的情况， 系统运行了一段时间，各种业务场景都执行过几轮之后

​

**缓存雪崩**: redis故障，从而导致数据丢失。

​

redis 目前架构来说，不能保障 100% 数据不丢失 ，我们需要关注，当前系统是否能够允许缓存出现问题。

​

重点在于我们需要知道 多少秒内，我们能够恢复 redis缓存服务。 如果缓存失效，我们会出现大量请求直接访问数据库，从而出现数据库问题。

​

**缓存击穿**: 如果查询的目标是不存在于系统中的数据，则缓存必然失效

​

缓存大量Miss，可能： 高并发请求大量 怼到数据库,数据库 处理不过来

​

这上述三类场景是我们在性能测试中必须要注重的系统崩溃的场景.

## Redis性能测试

在开启性能测试前，我们需要了解一个概念：不同的硬件设备， 会导致 Redis的性能有很大的区别。

redis是个软件，既然是软件它必然会【吃内存 、吃CPU】

最常用的方式： `redis-benchmark -q -n 100000`

​

说明 ：

redis-benchmark 是一个官方提供的Redis性能测试工具，它可以用来测试Redis服务器的性能，包括但不限于每秒操作数（operations per second, 简称OPS）、读写延迟等。

使用 redis-benchmark 的基本命令格式如下：

redis-benchmark [选项] [命令参数]

例如，以下命令可以测试使用50个并发连接，总共100000个请求的SET和GET操作：

redis-benchmark -c 50 -n 100000 -t SET,GET

这里的 `-c` 参数代表并发连接数，`-n` 代表总请求数，`-t` 代表要测试的命令类型。

|  |  |  |
| --- | --- | --- |
| 参数 | 描述 | 默认值 |
| -h | 指定服务器主机名 | 127.0.0.1 |
| -p | 指定服务器端口 | 6379 |
| -s | 指定服务器socket | (无) |
| -a | 指定密码 | (无) |
| -c | 指定并发连接数 | 50 |
| -n | 指定请求数 | 100000 |
| -d | 以字节的形式指定SET/GET值的数据大小 | 3 |
| -k | 1=保持连接 0=重新连接 | 1 |
| -r | SET/GET/INCR 使用随机key, SADD使用随机值 | (无) |
| -P | 通过管道传输请求 | 1 |
| -q | 强制退出redis。仅显示query/sec值 | (无) |
| -l | 生成循环，永久执行测试 | (无) |
| -t | 仅运行以逗号分隔的测试命令列表 | (无) |
| -I | Idle模式。仅打开N个idle连接并等待 | (无) |

注意：Redis 自己的性能测试，并不等于 你的软件去操作redis也能达到这个性能

响应时间长 原因分析

原因1：持久化问题

### 面试:测试redis有什么印象深刻的问题吗？

例如 用户信息保存场景 -- 采用字符串 string 类型 `set u1001 "{userid:1001,uname:xm,...}"`,每一次查询 必须从redis 查询所有的内容,增加 网络消耗，增加处理的资源占用.

描述： 开发对用户信息做一个缓存, 测试，发现速度没有明显提升？

因为开发存放的是 把大量信息 用一个 key存进了 redis中，

set user1 [{用户1信息},{用户2信息}...] 导致-- 每次取单个用户，需要全部加载数据。

然后再去循环把数据拿出来。 加载，浪费时间，因为取全量数据，所以拿数据的速度非常慢

发现 数据保存，需要 合理的数据类型保存，这样才能防止人为事故

尽量采用： user1 :{} ,user2: {} 通过用户的唯一值去找数据 一个key 数据库的一行信息

前端发起请求 key = 用户id\_username

总之就是一个原则： 一个key 下面不要有过大的value

采用 hash ,类似 python 嵌套的 字典,可以 将 用户信息 分为多个key进行存放,尽量避免让开发使用复杂的命令

注意：在redis中，标记为 O(1) 命令，代表速度快 ，O（n)、 O(logn) 速度较慢

如果你看到慢查询日志 里边大量的命令，都是 非 O(1) 那就说明这个命令比较复杂，建议替换

## MQ是什么？

本质来说MQ 和 数据库 也是类似的。负责的都是都是 数据 存/取。

​

所谓缓存技术： 特点快、内存、针对查询场景

​

传统的数据库：特点事务支持、持久存储、数据管理场景

​

MQ 消息队列服务 -- 特点针对 数据更改场景、功能比其他两者都要弱【发数据、取数据】

数据的临时中转地 【新增+删除+极其少量的查询功能】

​

MQ 服务 比 数据库操作快的原因： 而是因为 操作更简单、没那么多约束

最重要的高性能原因： MQ操作是顺序读写为主、数据库 是随机读写磁盘

​

sudo yum install erlang

sudo yum install rabbitmq-server

sudo systemctl enable rabbitmq-server

sudo rabbitmq-plugins enable rabbitmq\_management
